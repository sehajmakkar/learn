## The problem: one app server

Snip's app server is still alone. When it crashes, every <Term t="redirect">redirect</Term> fails, and every deploy means a few seconds of
errors while it restarts. Snip promised redirects would almost never fail, so the fix is the same as for the database:
**more than one copy**, so any one can fail or be restarted while the others answer.

Two copies need something in front of them to decide which one gets each request. That's a **load balancer**.

## The load balancer

A load balancer is the one address the outside world talks to. It receives each request and passes it to one of
the app servers behind it:

It does three jobs:

- **Spreads requests.** The simplest rule is round robin: first request to server 1, next to server 2, and so on.
  "Fewest open connections" is a common alternative when requests vary in cost. <L id="03.06" /> covers the options.
- **Checks health.** Every few seconds it asks each server a simple question, usually an HTTP request to a path like
  `/health`. A server that fails a few checks in a row stops getting traffic until it recovers. This is what turns
  "one server crashed" from an outage into a non-event.
- **Hides the servers.** Users only know the load balancer's address, so you can add, remove and replace servers
  behind it without anyone noticing.

That last point also gives Snip **deploys without downtime**: take one server out of rotation, update it, check its
health, put it back, and repeat for the next. At every moment at least two servers are answering.

<Analogy>
  **A restaurant host.** Diners don't pick their own table; the host at the door looks at which waiters are free and seats them. If a waiter goes home sick, the host just stops seating people in that section. Diners never need to know who's working tonight.
</Analogy>

## The catch: state

This all works only if **any server can handle any request**. Here's what goes wrong if one doesn't. Say the app keeps
logged-in sessions in its own memory: after you log in, server 1 remembers "this cookie belongs to Ana". Now step
through Ana's next two requests:

Anything a server keeps in its own memory or on its own disk between requests is **state**: sessions, uploaded files
waiting to be processed, counters, an in-memory list of rate limits. With state on the servers, they're no longer
interchangeable, and losing one loses its state.

There are two ways out.

**Sticky sessions.** Tell the load balancer to always send the same user to the same server, usually with a cookie of
its own. It's quick to set up, but it treats the symptom: load spreads unevenly, and when a server dies, everyone
stuck to it still loses their session.

**Stateless servers.** Move the state out of the app servers into something they all share:

| State | Where it goes instead |
| --- | --- |
| Sessions | A shared store like Redis or the database, or a signed token the browser holds itself |
| Uploaded files | Object storage (S3 or similar), not the server's disk |
| Counters, rate limits | Redis or the database |
| Cached data | A shared <Term t="cache">cache</Term> (<L id="02.04" />) |

Now each server is **stateless**: it keeps nothing between requests that another server would need. Any server can
answer any request, a crash loses nothing, and adding capacity means starting another copy. This is the version Snip
uses. A Snip redirect was stateless from the start (look up the code, answer); only the logged-in dashboard needed
fixing.

## The load balancer is a single point of failure too

Putting everything behind one load balancer just moves the problem. In practice you either run a pair of them,
where a standby takes over the shared address if the active one fails, or use a cloud provider's managed load
balancer, which is already run as many machines behind the scenes. Either way, it's worth saying in an interview.

    processes should be "stateless and share-nothing": anything that needs to persist goes in a backing service such

    such as Memcached or Redis, for session data.

<Mistakes>
  <ul>
    <li>**Writing to the local disk.** Uploads and generated files on one server's disk vanish for every other server, and when that server is replaced.</li>
    <li>**Reaching for sticky sessions.** They hide the state problem instead of fixing it, and still lose sessions when a server dies.</li>
    <li>**A health check that always says yes.** If `/health` returns 200 even when the database connection is broken, the load balancer keeps sending traffic to a server that can't do its job.</li>
  </ul>
</Mistakes>

## Recap

<Recap>
  <ul>
    <li>Several app servers behind a load balancer remove the app as a single point of failure.</li>
    <li>The load balancer spreads requests, health-checks servers and hides them, which also allows deploys without downtime.</li>
    <li>It only works if servers are stateless: sessions, files and counters live in shared stores.</li>
    <li>Run the load balancer as a pair, or use a managed one, so it isn't the new single point of failure.</li>
  </ul>
</Recap>

## Interview questions

<InterviewCard
  q={{ q: "What does it mean for a web server to be stateless, and why does it matter for scaling?", level: "Junior", frequency: 3, importance: "Must-know", kind: "Concept" }}
  followUps={["Where would you keep user sessions?", "What are sticky sessions, and why are they usually a bad idea?"]}
>
  <p>A stateless server keeps nothing between requests that another server would need: no sessions in memory, no files on local disk. All of that lives in shared stores like a database, Redis or object storage, or in a signed token the client sends.</p>
  <p>It matters because then any server can handle any request. A load balancer can spread traffic freely, a crashed server loses nothing, deploys can replace servers one at a time, and adding capacity is just starting more copies.</p>
</InterviewCard>

<InterviewCard
  q={{ q: "How does a load balancer know a server is unhealthy, and what happens next?", level: "Mid", frequency: 2, importance: "Good to know", kind: "Concept" }}
  followUps={["What should a health check actually test?", "What happens if every server fails its health check at once?"]}
>
  <p>It sends a health check to each server every few seconds, typically an HTTP request to an endpoint like /health, and marks a server unhealthy after several failures in a row. It stops routing new requests to that server and keeps checking; once it passes again for a few checks, it goes back into rotation.</p>
  <p>The check should test what the server needs to do its job, such as being able to reach the database, without being so heavy that the checks themselves cause load.</p>
</InterviewCard>
