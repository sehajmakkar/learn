## The problem: Snip's cache is now a system of its own

Snip's four Redis nodes from <L id="05.03" /> were enough for 100,000 cache reads a second. A year later the targets
are:

- **300,000 reads a second** at peak, almost all redirects, plus a few thousand writes (new links, edits, deletes).
- **40 million links** in the working set.
- **p99 under 2 ms** for a cache read, so the cache stays far faster than the database.
- **Losing a node mustn't overload Postgres**, which is sized for about 1% of reads.

Treat it like any design (<L id="01.07" />): estimate, choose how keys are placed and found, then decide what happens
when things fail.

## Sizing

**Memory.** A cached link is a key, a URL and the cache's own bookkeeping per entry: say 500 bytes in all. 40 million ×
500 bytes is **20 GB**. Leave room for growth and for memory fragmentation, and plan for about **32 GB** of primaries.

**Throughput.** Snip's load tests show a node comfortably serving 50,000 reads a second at the latency target. 300,000
÷ 50,000 is **6 nodes** at full load. To leave headroom, and so that losing one node moves only a small share of keys,
Snip runs **12 primaries** of about 4 GB each, each with **one replica**.

Running more, smaller nodes has a real benefit: when one fails, a twelfth of the keys are affected, not a quarter.

## Finding the right node

Every request must reach the node that owns its key. There are three ways to arrange that:

| Approach | How a key finds its node | Trade-off |
| --- | --- | --- |
| **Client-side hashing** | Each app server's client library hashes the key onto a ring (<L id="05.03" />) | No extra hop; every client must agree on the node list |
| **A proxy** | Apps talk to a local proxy (such as mcrouter or twemproxy), which routes | One place for routing and config; one more hop |
| **A cluster-aware store** | The nodes know the layout and redirect clients that ask the wrong one | Self-managing; clients must support it |

**Redis Cluster** is the third kind. It divides the key space into **16,384 hash slots**: a key's slot is
`CRC16(key) mod 16384`, and each primary owns a range of slots. A client that asks the wrong node gets `-MOVED 3999
10.0.0.7:6379` and updates its map. While a slot is being moved to another node, the client may get `ASK`, meaning
"try that node for this one request". Slots are fixed logical partitions, exactly like Snip's 256 logical <Term t="sharding">shards</Term>
(<L id="05.04" />): adding a node moves whole slots, not individual keys.

**Hash tags** let you keep related keys together: only the part inside `{...}` is hashed, so `{x7Kp}:url` and
`{x7Kp}:owner` land on the same node and can be read in one command. Use them sparingly, since one popular tag puts
all its keys on one node.

## Replicas and failover

Each primary copies its writes to a replica **asynchronously**. If a primary dies, the replica is promoted. Because
copying is asynchronous, the last few writes before a crash can be lost, and the Redis Cluster specification says so
plainly: there are "small windows where acknowledged writes can be lost".

For a cache, that's acceptable: the database is the source of truth, and a lost entry is just a miss. A lost
**delete** is worse, since the promoted replica may still hold a value that was invalidated. That's another reason
every entry has a TTL (<L id="06.04" />).

Replicas can also serve reads, which adds read capacity, at the price of reading slightly behind the primary.

## When a node fails

Without a replica, or during the seconds before a replica takes over, a node's keys are unreachable. What should
clients do?

- **Treat it as a miss and go to the database.** Simple, but a twelfth of Snip's cached traffic, 25,000 reads a
  second, suddenly hits a database sized for 3,000. It can cascade.
- **Rehash onto the remaining nodes.** With a ring, the failed node's keys spread to its neighbours, which start cold.
  A single <Term t="hot-key">hot key</Term> can account for a big share of a node's traffic, so the neighbour that inherits it can be
  overloaded in turn.
- **Send them to a small spare pool.** Facebook's answer, the **Gutter** pool: about 1% of servers, idle normally,
  that take over failed servers' requests with short-lived entries. Misses there go to the database once, and then
  become hits (below).

Snip uses replicas for failover, and limits the misses any one app server can send to Postgres at once (<L id="03.11" />),
so a slow failover degrades latency instead of taking the database down.

## The client matters as much as the servers

- **Timeouts.** A cache read that takes 50 ms is worse than none. Give cache calls a tight timeout (a few
  milliseconds), and treat a timeout like a failed node, not as a reason to wait.
- **Batch, but watch the tail.** Reading 20 keys in one multi-get is far cheaper than 20 round trips, but a request
  that waits for 10 nodes is as slow as the slowest of them (<L id="03.12" />).
- **Hot keys.** Spread them with a small <Term t="in-process-cache">in-process cache</Term> and suffixed copies (<L id="05.02" />).
- **<Term t="request-coalescing">Coalescing</Term>.** Collapse concurrent misses for the same key (<L id="06.05" />).

## More than one region

If Snip serves from Virginia and Frankfurt, each region gets **its own cache**, filled from its own database replica,
because a cache read across an ocean costs more than a local database read. The hard part is <Term t="cache-invalidation">invalidation</Term>: an edit in
Virginia must delete the entry in Frankfurt's cache too, and not before Frankfurt's database replica has the new row,
or a miss there will refill the old value. Driving deletes from each region's own replication stream solves both: a
region deletes a key when its database applies the change (<L id="06.04" />).

<Mistakes>
  <ul>
    <li>**Few, huge nodes.** Each failure takes out a big share of the keys. More, smaller nodes fail more gently.</li>
    <li>**Failing over to the database.** A cache outage becomes a database outage. Cap misses, coalesce, or use spares.</li>
    <li>**Loose timeouts on cache calls.** A slow cache is worse than none; time out in milliseconds.</li>
    <li>**Reading another region's cache.** The round trip beats the point of caching. Cache per region and invalidate each.</li>
  </ul>
</Mistakes>

## Recap

<Recap>
  <ul>
    <li>Size the tier from the working set (memory) and the peak read rate (nodes), then add headroom.</li>
    <li>Keys find nodes by client-side hashing, a proxy, or a cluster-aware store like Redis Cluster's 16,384 slots.</li>
    <li>Replicas give fast failover; asynchronous copying can lose writes, which a cache can usually tolerate.</li>
    <li>Plan the failure path: cap and coalesce misses, avoid overloading neighbours, and cache per region with per-region invalidation.</li>
  </ul>
</Recap>

## Interview questions

<InterviewCard
  q={{ q: "Design a distributed cache.", level: "Senior", frequency: 3, importance: "Must-know", kind: "Design" }}
  followUps={["How do you handle a node failure without overloading the database?", "How do you handle a hot key?", "How does a client find the node for a key?"]}
>
  <p>I'd start from the numbers: working set size for memory, peak operations per second for node count, plus headroom, preferring more smaller nodes so a failure affects a small share of keys. Keys are placed with consistent hashing or fixed hash slots, so adding a node moves only a fraction; clients either hash themselves, go through a proxy, or follow redirects from a cluster-aware store. Each node is in-memory with an eviction policy such as approximate LRU, and every entry has a TTL.</p>
  <p>For availability, each primary gets an asynchronously replicated replica that's promoted on failure; losing the last few writes is acceptable because the database is the source of truth. The failure path matters most: clients use tight timeouts, coalesce misses per key, cap concurrent misses to the database, and optionally fail over to a small spare pool. Hot keys get local caching and replication across several nodes. Across regions, each region has its own cache, invalidated from that region's replication stream.</p>
</InterviewCard>
