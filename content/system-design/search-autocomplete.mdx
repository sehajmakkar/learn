## The prompt

"Design search autocomplete" (Google's search box, a shop's search bar) is mostly a **data pipeline** question. The
serving path is a lookup; the real design is how suggestions are counted, ranked, filtered and shipped to the
servers that answer.

  Snip Bio's search box suggests searches as people type: after `su`, show the five most popular searches starting

## 1. Requirements

**Functional:** return the top 5 suggestions for a prefix, ranked by popularity; reflect trending searches within
minutes; never suggest offensive or private queries.

**Non-functional:** under 100 ms end to end, so a few milliseconds at the server; very high availability (a broken
autocomplete is noticed immediately, though search still works without it).

## 2. Estimates

- **Requests:** 10 million × 5 searches × about 6 requests per search after debouncing ≈ 300 million a day, about
  3,500 a second and **15,000 at peak**. Several times the search traffic itself.
- **Table size:** suppose 10 million distinct queries clear the popularity threshold. Prefixes up to 10 characters,
  heavily shared, come to perhaps 50 million; × 5 suggestions × about 30 bytes ≈ **7.5 GB**. That fits in memory on
  each serving node.
- **Logs:** 50 million searches a day is a few GB a day: an ordinary batch job.

## 3. Entities and API

```text
SearchLog    { query, user_id_hash, at, country }               raw, kept 30 days (14.11)

PrefixTable  { prefix → [(query, score)] × 5 }                   versioned snapshot
```

## 5. Deep dives

<DeepDive title="Answering a prefix in a few milliseconds">
  <Option grade="bad" name="Query the search logs at request time">
    `WHERE query LIKE 'su%' GROUP BY query ORDER BY count(*) DESC` scans millions of rows per keystroke.
  </Option>
  <Option grade="good" name="A trie with the top completions at each node">
    The lookup walks the prefix and returns the stored list (<L id="10.06" />). Fast, but updating weights in place
    is awkward, and the structure lives in one process's memory.
  </Option>
  <Option grade="great" name="A precomputed prefix table, built offline and served from memory">
    The build job writes prefix → top 5 directly, so serving is a hash lookup; every server holds a full copy (7.5 GB)
    and any can answer. If the table outgrows memory, shard it by hash of prefix, not by first letter, since "s"
    holds far more than "x".
  </Option>
</DeepDive>

```ts
export function buildPrefixTable(counts: Map<string, number>, k = 5, maxPrefix = 10) {
  const table = new Map<string, [string, number][]>();
  for (const [query, n] of counts) {
    for (let len = 1; len <= Math.min(query.length, maxPrefix); len++) {
      const prefix = query.slice(0, len);
      const top = table.get(prefix) ?? [];
      top.push([query, n]);
      top.sort((a, b) => b[1] - a[1] || a[0].localeCompare(b[0]));
      if (top.length > k) top.pop();
      table.set(prefix, top);
    }
  }
  return table; // written to a snapshot: prefix -> top k
}

/** Blend this week into the running score so old spikes fade: halve the past every week. */
export function decay(previous: Map<string, number>, thisWeek: Map<string, number>, keep = 0.5) {
  const out = new Map<string, number>();
  for (const [q, n] of previous) out.set(q, n * keep);
  for (const [q, n] of thisWeek) out.set(q, (out.get(q) ?? 0) + n);
  return out;
}
```

<DeepDive title="Keeping suggestions fresh">
  <Option grade="bad" name="All-time counts">
    Last February's spike for "super bowl" stays at the top of `su` all year.
  </Option>
  <Option grade="good" name="Weekly rebuilds with decay">
    Each week's counts are added to half of the previous score, so a spike fades within weeks.
  </Option>
  <Option grade="great" name="Decayed weekly table, plus a trending layer">
    The weekly table gives stable ranking; a streaming top-k over the last hour (<L id="11.04" />), in event-time
    windows (<L id="11.02" />), adds what's spiking now. The suggest server merges the two per prefix.
  </Option>
</DeepDive>

Tested with six queries over three weeks, k = 3. In week 1, `su` suggested "super bowl" (2,000), "summer sale" and
"summer shoes". In week 2, "super bowl" fell to 30 searches; its decayed score of 1,030 dropped it below "summer sale"
(1,400). By week 3, "sun cream", rising from 120 to 500 searches a week, had overtaken it as well: `su` showed
"summer sale", "sun cream", "summer shoes". The six queries produced 42 prefix entries.

**Filtering.** Before a query enters the table: drop anything on a blocklist (offensive, defamatory, or names a
creator has asked to remove), and drop queries searched by fewer than, say, 50 distinct users, so nothing someone
typed privately (a phone number, a name) is ever suggested to others. These are rules in the build, run before
anything is served.

**The client.** Debounce about 100 ms, cancel requests for stale prefixes, cache by prefix in the browser, and filter
already-fetched suggestions locally as the user keeps typing (<L id="10.06" />). With a few minutes of caching at the
CDN, most one- and two-letter prefixes never reach the servers.

## 6. Wrap-up

What breaks first: **build time and memory** as distinct queries grow, handled by the popularity threshold and by
limiting prefixes to 10 characters; then **regional differences**, handled by building one table per locale.

<Mistakes>
  <ul>
    <li>**Computing suggestions at request time.** Precompute top-k per prefix.</li>
    <li>**Sharding by first letter.** Prefixes are wildly uneven; hash them.</li>
    <li>**No popularity threshold.** Rare queries can reveal what someone typed privately.</li>
    <li>**Replacing the table in place.** Load a new version beside the old one, switch, and keep rollback.</li>
  </ul>
</Mistakes>
