## The prompt

"Design a <Term t="rate-limit">rate limiter</Term>" usually means a **distributed** one: many <Term t="api">API</Term> servers, one set of limits. The algorithm is a
small part of the answer; the rest is where state lives, how rules change, and what the limiter does when it breaks.

  Snip's public API runs on 40 gateway servers and peaks at 200,000 requests a second from 2 million API keys. Each
  plan has limits ("basic: 10 requests a second, bursts of 20; 100 link creations a minute"), and unauthenticated
  traffic is limited by IP. The limiter may add at most a couple of milliseconds to a request.
</DesignIt>

## 1. Requirements

**Functional**

- Limit by API key, IP address and route, with limits that depend on the customer's plan.
- Reject excess requests with **429 Too Many Requests**, a `Retry-After` header, and headers saying how much quota
  is left.
- Change limits and add rules without deploying the API.

**Non-functional**

- Adds under 2 ms at p99.
- Limits hold across all 40 servers, give or take a few percent.
- The limiter failing must not take the API down.

## 2. Estimates

- **State:** 2 million keys × about 3 rules each = 6 million buckets. At about 100 bytes each with Redis overhead,
  that's **600 MB**: it fits in memory, comfortably.
- **Operations:** 200,000 requests × 2 rules on average = 400,000 checks a second. If one Redis primary handles about
  50,000 scripted checks a second within the latency target (measure your own), that's **8 primaries**, plus
  replicas.

So the counter store is a small Redis cluster. The cost to design around is the **round trip** on every request.

## 3. Entities and API

```text
Rule    { name, match: (api_key | ip | route), per_plan: { rate, burst }, mode: enforce | shadow }
Bucket  { rule:key → tokens, updated_at }        in Redis, sharded by key

check(request) → { allowed, remaining, retry_after }      called by the gateway, in process

HTTP/1.1 429 Too Many Requests
Retry-After: 1
X-RateLimit-Limit: 10
X-RateLimit-Remaining: 0
```

## 5. Deep dives

<DeepDive title="Where do the counts live?">
  <Option grade="bad" name="In each gateway's memory">
    No round trip, but with 40 servers a key gets up to 40 times its limit, and the true limit changes whenever the
    fleet resizes.
  </Option>
  <Option grade="good" name="In Redis, read then write">
    Shared, but two gateways can both read 9 of 10, both allow, and both write 10: under concurrency the limit leaks.
  </Option>
  <Option grade="great" name="In Redis, one atomic script per check">
    The script reads the bucket, refills it for the elapsed time, takes a token and writes it back as one step, so
    concurrent checks can't interleave. Keys are spread across primaries by hash (<L id="06.06" />), and the script
    uses the Redis server's clock, not 40 different gateway clocks.
  </Option>
</DeepDive>

<DeepDive title="One request, several rules">
  <Option grade="bad" name="Check each rule in turn, spending as you go">
    A request allowed by the key's limit but rejected by the route limit has already spent a token from the key's
    bucket. Rejected requests eat the customer's quota.
  </Option>
  <Option grade="good" name="Use only the strictest rule">
    Simpler, but different rules protect different things; dropping one leaves a gap.
  </Option>
  <Option grade="great" name="Check every rule, then spend from all of them only if all allow">
    Done inside one script, so it's atomic too. The response reports the lowest remaining quota and the longest
    wait.
  </Option>
</DeepDive>

The decision logic, run here in process with an in-memory map in place of Redis:

```ts
type Req = { apiKey: string; ip: string; route: string };
type Rule = { name: string; match: (r: Req) => string | null; perSecond: number; burst: number };
type Bucket = { tokens: number; at: number };

export class Limiter {
  private buckets = new Map<string, Bucket>();
  constructor(private rules: Rule[]) {}

  check(req: Req, now: number) {
    let retryAfter = 0;
    const touched: Bucket[] = [];
    for (const rule of this.rules) {
      const key = rule.match(req);
      if (key === null) continue; // the rule doesn't apply to this request
      const b = this.buckets.get(`${rule.name}:${key}`) ?? { tokens: rule.burst, at: now };
      b.tokens = Math.min(rule.burst, b.tokens + ((now - b.at) / 1000) * rule.perSecond);
      b.at = now;
      this.buckets.set(`${rule.name}:${key}`, b);
      if (b.tokens < 1) retryAfter = Math.max(retryAfter, Math.ceil((1 - b.tokens) / rule.perSecond));
      touched.push(b);
    }
    if (retryAfter > 0) return { allowed: false, retryAfter };
    for (const b of touched) b.tokens -= 1; // spend only when every rule allows it
    return { allowed: true, remaining: Math.min(...touched.map((b) => Math.floor(b.tokens))) };
  }
}
```

Tested with a key rule of 5 a second (bursts of 10) and a creation rule of 1 a second per IP (bursts of 3): 12
requests at once gave 10 allowed and 2 rejected with `retryAfter: 1`; one second later the next request was allowed
with 4 remaining. Twenty link creations at once from one IP gave 3 allowed and 17 rejected, and afterwards the
key's own bucket still had 6 tokens: the 17 rejected requests hadn't spent any.

<DeepDive title="When the limiter is slow or down">
  <Option grade="bad" name="Wait for Redis, and reject if it fails">
    A slow Redis now slows every API call, and an outage of the limiter becomes an outage of the API (<L id="08.01" />).
  </Option>
  <Option grade="good" name="A short timeout, then fail open">
    Give the call a few milliseconds; if it fails, allow the request. Customers notice nothing, and the API's own
    concurrency limits still protect it.
  </Option>
  <Option grade="great" name="Fail open to local limits, and keep hot keys local">
    On failure, fall back to a local bucket per server at the limit divided by the number of servers: rough, but not
    unlimited. The very busiest keys get a local pre-check too, so one huge customer doesn't make a hot key in Redis
    (<L id="05.02" />).
  </Option>
</DeepDive>

**Changing rules safely.** A new rule starts in **shadow mode**: the limiter evaluates it and logs what it would
have rejected, without rejecting anything. Once the logs show it catches abuse and not good customers, it's switched
to enforce. Rules are versioned, so a bad change is rolled back in seconds (<L id="14.05" />).

## 6. Wrap-up

What breaks first is usually the **hot key**: one large customer's bucket, checked 20,000 times a second, all on
one Redis primary. After that, cost: if the counters dominate the bill, approximate local counting synced every
second (<L id="14.04" />) removes most of the round trips for limits that tolerate a brief overshoot.

<Mistakes>
  <ul>
    <li>**Per-server counters for a global limit.** The real limit becomes the limit times the number of servers.</li>
    <li>**Read-modify-write without atomicity.** Concurrent checks leak through; use one script.</li>
    <li>**Failing closed by default.** A limiter outage shouldn't become an API outage.</li>
    <li>**Enforcing new rules immediately.** Run them in shadow mode first.</li>
  </ul>
</Mistakes>

## Recap

<Recap>
  <ul>
    <li>A distributed limiter is a library in the gateway, rules pushed from config, and counts in a sharded Redis tier.</li>
    <li>Each check is one atomic script: refill, test every matching rule, spend only if all allow.</li>
    <li>Respond with 429, Retry-After and quota headers.</li>
    <li>Fail open with a short timeout, fall back to local limits, and keep hot keys local.</li>
