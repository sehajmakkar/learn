## The prompt

"Design a unique ID generator" looks like a one-liner (use a UUID) until the interviewer adds constraints: 64 bits,
sortable by time, very fast, and no single machine that everything depends on.

  Every service at Snip needs IDs for new rows: clicks, events, messages. Design a way to generate them: unique
  across all services and both regions, 64-bit integers, roughly ordered by creation time, at up to 500,000 a second
  overall, with no single point of failure and under a millisecond to get one.

## 1. Requirements

- **Unique**, everywhere, forever.
- **64 bits**, so they fit a `bigint` column and are cheap to index.
- **Roughly time-ordered** ("k-sorted"): IDs made later are usually larger, so new rows land at the end of a B-tree
  index (<L id="04.02" />) and IDs sort by time without a separate column.
- **Fast and available**: 500,000 a second, under a millisecond, no single point of failure.
- **Not required:** being unguessable (these aren't Snip's short codes) or strictly sequential.

## 2. Options

<DeepDive title="Which scheme?">
  <Option grade="bad" name="One database's auto-increment sequence">
    Unique and ordered, but every insert in every service depends on one machine, and it's a bottleneck for both
    regions.
  </Option>
  <Option grade="good" name="Ticket servers or blocks of IDs; or UUIDs">
    Flickr's two ticket servers hand out odd and even numbers; a service can take a block of 1,000 at a time to cut
    round trips. Still a dependency, and blocks break time order. UUIDv4 needs no coordination but is 128 bits and
    random, which scatters index inserts; **UUIDv7** fixes the order, and is the right answer if 128 bits is
    acceptable (<L id="05.05" />).
  </Option>
  <Option grade="great" name="Snowflake: timestamp, worker number, sequence">
    Each generator makes IDs alone from its clock, its worker number and a counter. 64 bits, time-ordered, no
    network call per ID.
  </Option>
</DeepDive>

```text
 1 bit  | 41 bits                       | 10 bits        | 12 bits
 unused | milliseconds since 2025-01-01 | worker number  | sequence within the millisecond

 41 bits of milliseconds ≈ 69 years · 1,024 workers · 4,096 IDs per worker per millisecond
```

One worker can make about 4 million IDs a second, so 500,000 a second needs a handful. The real limits are the
1,024 worker numbers and the clock.

## 4. Deep dives

<DeepDive title="Giving each generator a unique worker number">
  <Option grade="bad" name="Set it by hand in config">
    Works until someone copies a config, or autoscaling starts two copies of the same one. Duplicate worker numbers
    mean duplicate IDs, silently.
  </Option>
  <Option grade="good" name="Derive it from the machine's IP address or name">
    No coordination, but 10 bits from a hash of an address collide: with 40 machines, the chance that two share a
    number is about 50%, and with 100 it's about 99%. Containers reuse addresses, too.
  </Option>
  <Option grade="great" name="Lease it from a coordination store">
    A process claims a free number with an expiry and renews it; if renewal fails, it stops before the lease
    expires. A process that stalled or lost its network can't keep using a number someone else now holds
    (<L id="08.07" />).
  </Option>
</DeepDive>

```sql
CREATE TABLE worker_ids (id int PRIMARY KEY, holder text, expires_at timestamptz NOT NULL DEFAULT '-infinity');
INSERT INTO worker_ids (id) SELECT g FROM generate_series(0, 1023) g;
```

```ts
export async function claimWorkerId(db: pg.Pool, holder: string, leaseSeconds = 30): Promise<number | null> {
  const { rows } = await db.query(
    `UPDATE worker_ids SET holder = $1, expires_at = now() + make_interval(secs => $2)
     WHERE id = (SELECT id FROM worker_ids WHERE expires_at < now()
                 ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED)
     RETURNING id`,
    [holder, leaseSeconds],
  );
  return rows[0]?.id ?? null;
}

export async function renewWorkerId(db: pg.Pool, id: number, holder: string, leaseSeconds = 30) {
  const { rowCount } = await db.query(
    `UPDATE worker_ids SET expires_at = now() + make_interval(secs => $3)
     WHERE id = $1 AND holder = $2 AND expires_at > now()`,
    [id, holder, leaseSeconds],
  );
  return rowCount === 1; // false: the lease is gone, so stop generating IDs at once
}
```

Tested on Postgres 16 with 2-second leases: 20 processes claiming at the same moment got 20 different numbers.
Renewal by the holder succeeded and by any other name failed. After the lease ran out, the old holder's renewal
failed, and a new process claimed the freed number. The lease time comes from the database's clock, so the
processes' own clocks don't decide who holds what.

<DeepDive title="When the clock goes backwards">
  <Option grade="bad" name="Ignore it">
    NTP steps the clock back 50 ms; the generator reuses those 50 milliseconds with the same worker number and
    sequences that start at 0 again: duplicate IDs.
  </Option>
  <Option grade="good" name="Refuse to generate until the clock catches up">
    Snowflake's own rule. Remember the last timestamp used; if the clock reads earlier, wait or return an error.
    Correct, but a large jump stalls the process.
  </Option>
  <Option grade="great" name="Refuse, and bound the damage">
    Wait out small steps (a few milliseconds); for large ones, stop, alert and let the process give up its lease and
    claim a new number. Configure time sync to slew (adjust gradually) rather than step, and keep the lease longer
    than the largest step you'd tolerate, so a restarted process can't reuse its old number in the repeated time.
  </Option>
</DeepDive>

**Library or service?** A library has no network hop and no new service to run; it needs the lease table and
disciplined clocks on every machine. A central ID service (a few instances, each with its own worker number) suits
clients in many languages, at the cost of a call per ID or per block of IDs. Snip uses the library.

## 5. Wrap-up

What breaks first: **worker numbers**, if thousands of short-lived processes each hold one (10 bits is 1,024);
widen the worker field and narrow the sequence. Then **ordering across machines**: IDs are only roughly ordered,
since two machines' clocks differ by a few milliseconds, so never use them to decide which of two events happened
first (<L id="08.05" />).

<Mistakes>
  <ul>
    <li>**Worker numbers in config files.** Lease them, and stop when the lease is lost.</li>
    <li>**Trusting the clock.** Check each timestamp against the last one used.</li>
    <li>**Treating IDs as a global order.** They're roughly ordered; machines' clocks differ.</li>
    <li>**Random 128-bit keys on a hot table without thinking.** Prefer time-ordered IDs for index locality.</li>
  </ul>
</Mistakes>

## Recap

<Recap>
  <ul>
    <li>Snowflake IDs pack a millisecond timestamp, a worker number and a sequence into 64 bits: about 69 years, 1,024 workers, 4,096 IDs per millisecond each.</li>
    <li>Generation is local; the only shared piece is the lease on each worker number.</li>
    <li>A lost lease, or a backwards clock, means stop generating.</li>
    <li>If 128 bits is fine, UUIDv7 gives time order with no coordination at all.</li>
  </ul>
</Recap>

>
  <p>I'd confirm the constraints: 64 bits, roughly time-ordered, high throughput, no single point of failure. That rules out a single database sequence, and UUIDv4 is 128 bits and random, though UUIDv7 would do if 128 bits were acceptable. So a Snowflake layout: 41 bits of milliseconds from a custom epoch, about 69 years; 10 bits of worker number, 1,024 workers; and 12 bits of sequence, 4,096 IDs per millisecond per worker. Generation is a library in each process, with no network call per ID.</p>
  <p>Worker numbers are leased from a coordination store with an expiry and renewed regularly; if renewal fails, the process stops before the lease runs out, so two live processes never share a number. The generator remembers the last timestamp and refuses to issue IDs if the clock goes backwards, waiting out small steps and alerting on large ones. IDs are only roughly ordered across machines, so they're not used to order events precisely.</p>
