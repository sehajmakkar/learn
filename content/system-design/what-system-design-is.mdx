## The core idea

When you write code, you decide how one program works: its functions, its classes, its data structures. **System
design** is one level up. You decide which programs exist, where each one runs, where the data lives, and how they
talk to each other, so that the whole thing does its job for the number of people using it.

A design is a set of answers to questions like:

- Where is the data stored, and how many copies are there?
- What happens when one machine dies in the middle of a request?
- Which parts get slow first when traffic grows ten times, and what do we do about it?
- What does all of this cost to run, and who has to keep it running?

<Analogy>
  **A building, not a brick.** Writing code is laying bricks well. System design is the architect's drawing: where the rooms go, where the stairs and fire exits are, how water and power reach every floor. A beautiful brick can't save a building with no fire exit, and a good drawing still needs good bricks.
</Analogy>

## What changes as a system grows

Small systems and large ones fail in different ways. As Snip grows, four things change:

| What grows | What it forces you to think about |
| --- | --- |
| **Traffic** | One machine can't serve every request, so you need more machines and a way to spread work across them. |
| **Data** | It no longer fits on one disk, or one database can't keep up, so you split it or copy it. |
| **Failures** | With hundreds of machines, something is always broken. The design has to keep working anyway. |
| **People** | Many teams work on the system at once, so its parts need clear boundaries and contracts. |

None of these are problems on day one. A good designer adds each piece of machinery when a real need appears, and
can say what that need is. You'll see this in <L id="01.08" />.

## What interviews test

A system design interview is usually 45 to 60 minutes. You get a vague prompt ("design a link shortener") and a
whiteboard. There's no single right answer, and the interviewer knows that. They're watching how you think:

| They're listening for | What it looks like |
| --- | --- |
| **Clarifying the problem** | You ask what the system must do and how big it is before drawing anything. |
| **A design that works** | Your boxes and arrows actually serve the main use cases, end to end. |
| **Depth where it matters** | You can go into detail on the hard parts: the data model, the busiest path, what breaks first. |
| **Trade-offs** | You say what each choice costs, not just what it buys, and why it fits these requirements. |
| **Communication** | You think out loud, keep the interviewer with you, and adjust when they push back. |

The bar rises with seniority. A junior candidate is expected to reach a working design with some guidance; a senior
one is expected to drive the conversation and pick the deep dives themselves. Every design lesson in this course ends
with what's expected at each level.

## How this course is built

The course follows the way people actually get good at this:

1. **Part 1** gives you the approach: requirements, the numbers to know, estimation, trade-offs and one framework
   you'll use for every design.
2. **Part 2** teaches the building blocks one at a time: <Term t="cache">caches</Term>, queues, replication, <Term t="sharding">sharding</Term> and the rest. Each
   starts from a system that breaks without it and ends with real companies that use it.
3. **Part 3** applies the framework to 22 classic designs. You try each one yourself first, then compare.
4. **Part 4** reads real case studies from the companies' own write-ups.

Snip runs through all of it, picking up a cache, a <Term t="load-balancer">load balancer</Term>, a <Term t="message-queue">queue</Term> and more as each one becomes necessary.

<Mistakes>
  <ul>
    <li>**Starting to draw before asking questions.** "Design Twitter" could mean the timeline, search, or direct messages. Pin down what matters first (<L id="01.02" />).</li>
    <li>**Designing for Google's scale by default.** If the numbers say one database is enough, adding ten machines is a worse design, not a better one.</li>
    <li>**Going quiet.** The interviewer can only credit what they hear. Narrate your reasoning, including the options you rejected.</li>
  </ul>

  <p>I start by clarifying: which features matter most, roughly how many users and how much data, and which qualities matter (speed, availability, consistency). I write those down.   <p>Once that works, I pick the riskiest or busiest parts and go deep on them, comparing options and saying what each costs. I finish by naming the bottlenecks and failure points I'd watch, and how the design would grow.</p>
