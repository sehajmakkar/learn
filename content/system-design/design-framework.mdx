## Why a framework

Open-ended questions are easy to get lost in. You go deep on the database before you've decided what the <Term t="api">API</Term> is, or
run out of time before anyone has seen a working design. A framework is a fixed order of steps that keeps you
moving, makes sure you cover the basics, and leaves time for the interesting parts.

Every design lesson in this course uses the same six steps, so by the end of Part 3 they'll be habit.

<Analogy>
  **A pilot's checklist.** Experienced pilots still run through the same checklist before every flight. It isn't because they'd forget how to fly; it's so that their attention is free for the things that are actually different about today's flight.
</Analogy>

The times are a guide, not a rule. If the interviewer wants to spend twenty minutes on one deep dive, follow them.

## 1. Requirements

Write down three or so core features, an out-of-scope list, and the non-functional requirements that matter, with
numbers (<L id="01.02" />). For Snip: create a short link, <Term t="redirect">redirect</Term>, see click counts; 10M links a month, 100 reads per
write; fast, always-available redirects; never lose a link.

## 2. Estimates

Do the few calculations whose answers change the design (<L id="01.05" />). For Snip: about 1,000 redirects a second at
peak and 300 GB over five years. Then say what it means: "<Term t="read-heavy">read-heavy</Term>, and it fits on one database".

## 3. Core entities and API

Name the main things the system stores, then the calls clients make. Keep it short; this is the contract the rest of
the design has to satisfy.

```text
Link   { code, long_url, owner_id, created_at }
Click  { code, at, country, referrer }

POST /links          { long_url }   →  201 { code, short_url }
GET  /{code}                        →  302, Location: long_url
GET  /links/{code}/stats            →  200 { clicks, by_day }
```

## 4. High-level design

Draw the simplest set of components that serves every core requirement, and walk one request through it to prove it
works. Build it one requirement at a time: here's Snip's redirect path, the one that matters most.

You'll learn each of these components in Part 2. For now, notice that every one is justified by something in steps 1
and 2. If you can't say which requirement a box serves, it probably shouldn't be there.

## 5. Deep dives

Pick the two or three parts where the design is hardest, busiest or riskiest, and go into detail: compare options,
name what each costs (<L id="01.06" />), and choose. For Snip, good candidates are:

- **How short codes are made** so they're short, unique and hard to guess.
- **Keeping the redirect path fast and available**, including what happens when the <Term t="cache">cache</Term> or database fails.
- **Counting clicks accurately** without slowing down redirects.

At senior levels, you're expected to choose these yourself. If you're not sure what the interviewer wants, ask.

## 6. Wrap-up

Finish by stepping back: where's the bottleneck now, what fails first, and how would the design change at ten times
the traffic? This shows you see the design as something that keeps evolving, not a finished drawing.

<Mistakes>
  <ul>
    <li>**Skipping step 4 to get to the interesting parts.** A deep dive on a design that doesn't work end to end is worth little.</li>
    <li>**Treating the framework as a script.** It's a default order. If the interviewer steers you, go with them and come back to the steps you skipped if there's time.</li>
    <li>**Boxes without reasons.** Every component should trace back to a requirement or an estimate.</li>
  </ul>
</Mistakes>

## Recap

<Recap>
  <ul>
    <li>Requirements → estimates → entities and API → high-level design → deep dives → wrap-up.</li>
    <li>Get a working end-to-end design before going deep.</li>
    <li>Every box should trace back to a requirement or an estimate.</li>
    <li>Deep dives are where you show trade-off reasoning; pick the hardest or busiest parts.</li>
  </ul>
</Recap>
