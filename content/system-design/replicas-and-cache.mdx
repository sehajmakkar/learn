## The problem: reads

A large chat app starts using Snip for every link its users share, and traffic grows a hundredfold. From the
estimate in <L id="01.05" />, that's about 350 new links and 35,000 <Term t="redirect">redirects</Term> a second on average, and around
**100,000 redirects a second at peak**.

Adding app servers is easy now: they're stateless. But every redirect still asks the one database the same question,
"where does this code go?", and the graphs show the primary at 90% CPU at peak, almost all of it from those lookups.
Writes are fine. **Reads** are the problem.

There are two standard ways to take reads off a database. Most systems end up using both.

## Fix 1: read replicas

A **read replica** is a copy of the database that receives every change from the primary and applies it. The app
sends **writes to the primary** and **reads to the replicas**. Since replicas only serve reads, you can add more of
them as read traffic grows. (The standby from <L id="02.02" /> is built the same way; it just doesn't take traffic.)

The catch is that copying takes time. The primary commits a write, then sends it to each replica, which applies it a
moment later. That delay is **replication lag**: usually milliseconds, but it can grow to seconds when a replica is
busy. During it, a replica returns old data. For Snip, that breaks a requirement:

Snip promised "a new link works the moment it's created", so it needs a rule for this. The simplest one: **if a
replica says a code doesn't exist, ask the primary before answering 404.** Real codes are almost always found on the
replica, so only brand-new links (and mistyped ones) reach the primary. Other systems use "read your own writes":
for a few seconds after a user writes, send that user's reads to the primary.

## Fix 2: a cache

A **cache** keeps copies of frequently read data in memory, in a store like Redis or Memcached. Reading memory takes
about 100 ns, while a database query costs a network <Term t="round-trip">round trip</Term> plus <Term t="index">index</Term> and disk work (<L id="01.04" />), and the
cache can serve far more lookups per machine.

Snip uses the most common pattern, **cache-aside**: the app checks the cache first, and only on a miss asks the
database and saves the answer in the cache.

What makes a cache work is the **hit rate**, the share of reads it answers. At 100,000 redirects a second:

| Hit rate | Reads that reach the database |
| --- | --- |
| 80% | 20,000 a second |
| 95% | 5,000 a second |
| 99% | 1,000 a second |

Snip is close to ideal for caching. Links never change once created (editing is out of scope), so cached answers are
never wrong. And clicks are lopsided: a small share of links, the ones shared today, get most of the traffic. If 10
million links are clicked on a busy day, at 500 bytes each that's about 5 GB, which fits in one cache server's memory.

<Analogy>
  **The library's front desk.** Most visitors ask for this week's bestsellers, so the librarian keeps a few copies at the desk. Those requests are answered in seconds; only unusual requests mean a walk into the stacks. The desk shelf is small, but it handles most of the questions.
</Analogy>

## What a cache costs

- **Stale data.** The cache is a copy; when the original changes, the copy is wrong until it's updated or expires.
  Snip mostly avoids this because links don't change. When something does change (an owner deletes a link, say),
  the usual move is to **delete the cache entry**, not overwrite it, and let the next read fill it from the database.
  Give every entry an expiry time (a TTL) as a safety net.
- **Cold starts.** A cache that restarts empty sends every read to the database at once. <L id="06.05" /> covers how
  to soften that.
- **Missing keys.** Requests for codes that don't exist always miss. Someone scanning random codes goes straight past
  the cache. Caching "not found" for a short time helps.
- **One more system** to size, monitor and keep available.

## Which first?

| | Read replicas | Cache |
| --- | --- | --- |
| **Best for** | Many different queries: dashboards, searches, reports | The same small set of keys read again and again |
| **Freshness** | Behind by the replication lag | Behind until expiry or deletion |
| **App changes** | Send reads to a different address | Check cache, fill on miss, delete on change |
| **Capacity per machine** | A database server's worth | Far more simple lookups per machine |

Snip uses both: Redis for redirects, which are one key lookup repeated endlessly, and a replica for the owners'
dashboard and stats queries, which vary too much to cache well.

<Mistakes>
  <ul>
    <li>**Reading your own write from a replica.** Right after a write, a replica may not have it yet. Decide what each read can tolerate.</li>
    <li>**Updating the cache on write instead of deleting.** Two writers updating at once can leave the older value in the cache. Deleting is safer.</li>
    <li>**No expiry.** Without a TTL, a missed invalidation leaves wrong data in the cache forever.</li>
    <li>**Caching everything.** Cache the hot, repeated reads. Data that's read once wastes memory and lowers the hit rate.</li>
  </ul>
</Mistakes>

## Recap

<Recap>
  <ul>
    <li>When reads overwhelm the database, take them off it with read replicas, a cache, or both.</li>
    <li>Replicas copy every write and serve reads, but lag behind; plan for reads that need the latest data.</li>
    <li>Cache-aside: check the cache, read the database on a miss, store the answer with a TTL, delete on change.</li>
    <li>Hit rate drives everything: going from 99% to 95% sends five times as many reads to the database.</li>
  </ul>
</Recap>

## Interview questions

<InterviewCard
  q={{ q: "Your database is overloaded with reads. What are your options, and how do you choose?", level: "Mid", frequency: 3, importance: "Must-know", kind: "Scenario" }}
  followUps={["How do you handle a user reading their own write from a lagging replica?", "How would you keep the cache from serving stale data?"]}
>
  <p>First I'd check that the queries are indexed and efficient, since that's free. Then the two main tools are read replicas and a cache. Replicas are full copies that serve reads, which suits varied queries like dashboards, but they lag the primary, so reads that need the latest data go to the primary or use read-your-writes. A cache like Redis suits a small set of keys read over and over: cache-aside, with a TTL and deletion when the data changes.</p>
  <p>For a URL shortener, redirects are one key lookup with a skewed distribution and data that never changes, so a cache absorbs most of them. I'd add a replica for the analytics and dashboard queries.</p>
</InterviewCard>

<InterviewCard
  q={{ q: "What is replication lag, and how can it cause bugs?", level: "Mid", frequency: 2, importance: "Good to know", kind: "Concept" }}
  followUps={["What can make lag grow?", "How would you monitor it?"]}
>
  <p>It's the delay between a write committing on the primary and a replica applying it. It's usually milliseconds but can reach seconds or more when replicas are busy or the network is slow. During that window, reads from the replica return old data.</p>
  <p>The classic bug is a user writing something and immediately not seeing it, or seeing it appear and disappear as reads go to different replicas. Fixes include reading from the primary for a short time after a user writes, falling back to the primary when data is missing, or tracking the write's position and only using replicas that have caught up.</p>
</InterviewCard>
