## The problem: creating a link got slow

When Snip launched, creating a link was one `INSERT`. Then the paid plan added features, and each one was bolted on
to the same request. Today, `POST /links` does all of this before it answers:

| Step | Typical time | Fails when |
| --- | --- | --- |
| Insert the link | 5 ms | The database is down |
| Check the URL against the safety service (<L id="02.06" />) | 200 ms, sometimes 2 s | The service is down |
| Fetch the page's title and image for a preview | 300 ms to 5 s | The site is slow or blocks bots |
| Render a QR code image and upload it | 80 ms | Object storage is slow |
| Call the owner's webhook ("a link was created") | Whatever their server takes | Their server is down |
| Update the search index for the dashboard | 30 ms | The index is being rebuilt |

The p99 for creating a link is now over 5 seconds, and any one of five other systems being down makes it fail. The
owner wanted a short code. Everything else is something that should happen **because** a link was created, not
something the owner needs before they can carry on.

## Deciding what stays in the request

Ask of each step: **does the user need its result to continue?**

- **Yes, and it must be correct now** → do it in the request. The insert stays: without it there's no link.
- **No, but it must eventually happen** → move it to the background, reliably: the preview, the QR code, the index.
- **No, and it's someone else's system** → definitely background: the webhook. Never let a customer's slow server
  slow down your <Term t="api">API</Term>.
- **It decides whether the request is allowed** → think hard. The safety check could block the request, but Snip
  decided in <L id="02.06" /> that a few seconds of exposure beats making every owner wait.

After the move, `POST /links` does the insert and records that background work is needed, and answers in about 10 ms.
The work happens a moment later, and the dashboard shows "preview loading" until it's done.

## Jobs and events

There are two ways to describe the background work, and the difference shapes the rest of this module.

- **A job** (a command) says *do this*: "fetch the preview for x7Kp". It has one intended worker, and once it's done
  it can be forgotten. Job queues are built for this (<L id="07.05" />).
- **An event** says *this happened*: "link x7Kp was created". It has no idea who cares. The preview worker, the QR
  worker, the webhook sender and the search indexer can each react to it, and next year's new feature can too, without
  changing the code that creates links. Logs are built for this (<L id="07.02" />).

Events decouple the producer from its consumers; jobs make the intended work explicit. Snip uses both: link creation
publishes one `link.created` event, and the services that care turn it into their own jobs.

## A queue turns overload into delay

A queue doesn't make work cheaper. Workers still have to do every bit of it. What it changes is **when**. If links
arrive faster than workers can fetch previews, the queue grows instead of requests failing. That's usually what you
want for a burst, and a trap for a lasting overload.

**Little's law** connects the numbers: the average number of items waiting equals the arrival rate times the average
wait. If previews arrive at 350 a second and each sits in the queue for 2 seconds on average, about 700 are waiting at
any moment. Turn it round: a backlog of 70,000 at 350 a second means a new preview waits **200 seconds**. Queue length
alone tells you little; queue length divided by the drain rate tells you how late the work is.

So watch two numbers for every queue:

- **Age of the oldest message**: how late the work is. This is the one to alert on, because it's what users feel.
- **Depth**: how many messages are waiting. Useful for scaling workers, alarming only when it keeps growing.

And give every queue a limit. A queue that grows without bound eventually runs out of memory or disk, and then it
can't accept anything at all, turning a slow consumer into an outage for the producer. When the limit is hit, shed or
delay the least important work (<L id="03.11" />).

<Analogy>
  **A post office's sorting room.** The counter clerk takes your parcel and gives you a receipt in seconds; sorting and delivery happen later, out of sight. If parcels arrive faster than they're sorted, the pile grows and delivery slows, but the counter keeps working. Only if the sorting room fills completely does the counter have to stop taking parcels.
</Analogy>

## What you give up

- **Results arrive later**, so the product has to show work in progress ("preview loading").
- **Failures happen where nobody is watching.** A request that fails shows the user an error; a background job that
  fails needs retries, alerts and a place for messages that keep failing (<L id="07.03" />).
- **Duplicates and ordering** become your problem (<L id="07.03" />, <L id="07.04" />).
- **Tracing** a single action across a request and five background steps needs a shared ID passed along with every
  message.

<Mistakes>
  <ul>
    <li>**Calling other people's systems inside your request.** Webhooks, emails and third-party APIs belong in the background.</li>
    <li>**Unbounded queues.** A queue that can grow for ever eventually fails to accept anything. Set limits and decide what to shed.</li>
    <li>**Alerting on depth.** Depth means little on its own; the age of the oldest message is what users feel.</li>
    <li>**Moving work that decides the answer.** If the response depends on it, it can't be done later.</li>
  </ul>
</Mistakes>

## Recap

<Recap>
  <ul>
    <li>Keep in the request only what the user needs to continue; move the rest to the background.</li>
    <li>A job says "do this" to one worker; an event says "this happened" to anyone who cares.</li>
    <li>Queues turn bursts into delay, not into less work. Little's law: backlog ÷ drain rate = how late the work is.</li>
    <li>Watch the oldest message's age, bound every queue, and plan for failures nobody sees directly.</li>
  </ul>
</Recap>
