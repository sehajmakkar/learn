## The problem: links can change now

Until now, a Snip link never changed once created, so a cached copy was never wrong. Then Snip launches a paid plan,
and its most requested feature is **editing a link's destination**: a campaign link `x7Kp` that pointed at a spring
sale should point at the summer sale from Monday. Snip now has to decide what happens to the cached copy when the
database row changes.

There are two halves to this. **Reads**: who fills the cache on a miss? **Writes**: when data changes, what happens to
the cache and the database, and in what order?

## Reads: cache-aside or read-through

- **Cache-aside** (Snip since <L id="02.04" />): the app checks the cache, and on a miss reads the database and fills
  the cache itself. The cache knows nothing about the database.
- **Read-through**: the app only talks to the cache, and the cache (or a library wrapping it) loads from the database
  on a miss. The logic is the same, but it lives in one place instead of in every caller.

Both give the same results. Read-through is tidier when many services share the logic; cache-aside is simpler to
start with and works with any cache.

## Writes: four choices

| Pattern | On a write | Reads right after | Risk |
| --- | --- | --- | --- |
| **Write-around + delete** | Write the database, delete the cache entry | One miss, then fresh | A small race window (<L id="06.04" />) |
| **Write-through** | Write the database and the cache, as one step | Fresh and already cached | Slower writes; caches data that may never be read |
| **Write-behind (write-back)** | Write the cache now; the database later, in batches | Fresh from the cache | Writes lost if the cache dies before flushing |
| **Write-around, no delete** | Write the database only | Stale until the TTL expires | Staleness bounded only by the TTL |

**Write-around with delete** is the default for most systems, and it's what Snip uses for edits:

```ts
// redis is an ioredis client; db is a pg-promise database.

// Reading: cache-aside
async function destination(code: string): Promise<string | null> {
  const hit = await redis.get(`link:${code}`);
  if (hit !== null) return hit;
  const row = await db.oneOrNone("SELECT long_url FROM links WHERE code = $1", [code]);
  if (row) await redis.set(`link:${code}`, row.long_url, "EX", 3600);
  return row?.long_url ?? null;
}

// Editing: update the database first, then delete the cached copy
async function editDestination(code: string, longUrl: string) {
  await db.none("UPDATE links SET long_url = $2 WHERE code = $1", [code, longUrl]);
  await redis.del(`link:${code}`);
}
```

## Why delete, and why in that order

**Delete, don't overwrite.** Suppose two edits to `x7Kp` happen at almost the same moment, and each writer sets the
cache to its new value after updating the database. The database ends with whichever update committed last, but the
cache ends with whichever `SET` arrived last, and those needn't match:

If both writers **delete** instead, the order doesn't matter: the entry is gone either way, and the next read fills it
from the database, which has the right answer. Deletes are also safe to repeat, so a retried delete can't do harm.

**Database first, then cache.** Delete the cache first and a read can slip in between, find nothing, read the old row
from the database and put it back in the cache, before your update commits. Updating the database first shrinks that
window to a much rarer case, which <L id="06.04" /> covers. And if the delete fails after the update succeeds, the TTL
is the safety net, which is one reason every entry has one.

<Analogy>
  **The office noticeboard.** When a meeting moves, you could rewrite the notice (but two people rewriting it at once can leave the wrong time up), or you can update the calendar and simply take the notice down. The next person who wants to know checks the calendar and pins up a fresh notice. Taking it down is hard to get wrong.
</Analogy>

## Write-through: always warm, always paying

With write-through, every write goes to the database and the cache together, so reads after a write are hits. It
suits data that's read soon after it's written. The costs: every write pays for two stores, and you cache things that
may never be read. In practice "write-through" is usually still **database first, then cache**, so the two-writer race
above still applies unless the cache rejects older versions (<L id="06.04" />).

Snip doesn't use it for links: most links are created and then clicked a handful of times, and an edit is rare.

## Write-behind: fast, until the cache dies

With write-behind, the app writes only to the cache and the cache, or a worker, copies changes to the database later,
in batches. Writes are as fast as the cache, and many updates to the same key collapse into one database write.

The danger is in the gap: anything written but not yet flushed exists only in the cache's memory. Snip considered it
for click counts, with `INCR clicks:x7Kp` on every redirect and a worker writing the totals to Postgres every few
seconds. It's fast, but a Redis node crashing would lose up to a flush interval of clicks for every code on that node.
Snip keeps its click queue (<L id="02.06" />), which holds events durably until workers have counted them, because
owners pay for accurate counts. Write-behind fits data where losing the last few seconds is acceptable: view
counters, "last seen" times, <Term t="rate-limit">rate-limit</Term> counters.

<Mistakes>
  <ul>
    <li>**Overwriting the cache on write.** Two concurrent writers can leave the older value cached. Delete instead.</li>
    <li>**Deleting before updating.** A read in between refills the cache with the old value.</li>
    <li>**Write-behind for data you can't lose.** Unflushed writes live only in memory. Use it for counters and hints, not money or links.</li>
    <li>**Forgetting other cached shapes of the same data.** A list or query result that includes the row is stale too.</li>
  </ul>
</Mistakes>

## Recap

<Recap>
  <ul>
    <li>Cache-aside and read-through differ only in who loads on a miss: the app or the cache.</li>
    <li>For writes, the safe default is: update the database, then delete the cache entry, with a TTL as a backstop.</li>
    <li>Write-through keeps the cache warm at the cost of slower writes; write-behind makes writes fast but can lose them.</li>
    <li>Every cached form of the data (single rows, lists, query results) needs its own plan for changes.</li>
  </ul>
</Recap>
