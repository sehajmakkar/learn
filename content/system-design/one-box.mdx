## Launch day

Snip goes live. A few hundred people create links in the first week, and those links are opened a few thousand times.
Everything runs on **one rented server**: the Snip app, the database, and the files that make up the web page.

## Why one box is a good start

It's easy to sneer at a single server, but at this size it's the best design available:

- **Fast.** The app talks to the database over a local socket, not a network. No hop costs half a millisecond.
- **Cheap.** One modest server costs a few dollars a month.
- **Simple to understand.** One place to look at logs, one place to deploy, one thing to back up.
- **Easy to change.** With no other teams and no other services, you can rename a table on a Tuesday afternoon.

At launch the most important job is finding out whether anyone wants Snip. Every hour spent on infrastructure nobody
needs yet is an hour not spent on that.

<Analogy>
  **A food truck.** One person takes orders, cooks and hands over the food, all in one small space. It's fast and cheap, and perfect for testing whether people like the menu. Nobody opens a restaurant with three kitchens to find that out.
</Analogy>

## What breaks first

The single box works until one of these starts to hurt. Usually they arrive in roughly this order:

| Problem | What happens | What Snip will do about it |
| --- | --- | --- |
| **One machine to fail** | If the server dies, or its provider has an outage, every Snip link on the internet stops working. | Spare copies of each part (<L id="02.02" />, <L id="02.03" />) |
| **Deploys mean downtime** | Restarting the app to ship a change drops every request for those seconds. | Several app servers, updated one at a time (<L id="02.03" />) |
| **Parts fight over resources** | A slow analytics query eats the CPU and memory that <Term t="redirect">redirects</Term> need, so redirects slow down. | The database on its own machine (<L id="02.02" />) |
| **It runs out of room** | Traffic outgrows the CPU, or data outgrows the disk. | A bigger machine first, then more machines (<L id="02.02" />, <L id="02.04" />) |

The first row is the big one. A machine that's up 99.9% of the time is still down for about **nine hours a year**
(<L id="01.03" />), and Snip promised that redirects would almost never fail. The server becomes what's called a
**single point of failure**: one part whose failure takes the whole system down with it. Most of this module is about
removing them one by one.

## Backups are not redundancy

Even on one box, back up the database to somewhere **off the machine** (another provider's object storage is
typical) and test that you can restore it. That protects the data: if the disk dies, you lose at most the hours since
the last backup.

It doesn't protect <Term t="availability">availability</Term>. Restoring a backup onto a new server takes minutes to hours, and every redirect fails
until it's done. Backups answer "will we lose links?"; spare copies that are already running answer "will links keep
working?". Snip needs both, but at launch, backups come first.

<Mistakes>
  <ul>
    <li>**Starting with ten boxes.** The single server is the right launch design. Name what would make you change it.</li>
    <li>**Confusing backups with availability.** A backup brings data back after a while; it doesn't keep the system answering.</li>
    <li>**Keeping the only backup on the same machine.** If the disk or the server goes, the backup goes with it.</li>
  </ul>
</Mistakes>

## Recap

<Recap>
  <ul>
    <li>Snip launches with the app, database and files on one server: fast, cheap and simple.</li>
    <li>The first problems are one machine to fail, downtime on deploys, parts competing for resources, and running out of room.</li>
    <li>A single point of failure is a part whose failure takes everything down. This module removes them one at a time.</li>
    <li>Back up off the machine from day one. Backups protect data, not availability.</li>
  </ul>
</Recap>

## Interview questions

<InterviewCard
  q={{ q: "Your whole app runs on one server. What are the risks, and what would you change first?", level: "Junior", frequency: 2, importance: "Must-know", kind: "Scenario" }}
  followUps={["What's the difference between a backup and a replica?", "How would you deploy without downtime?"]}
>
  <p>The server is a single point of failure: if it crashes, or its host has an outage, everything is down. Deploys restart the only copy of the app, so users see errors while it comes back. The app and database compete for the same CPU, memory and disk, so a heavy query can slow every request. And there's a ceiling on how much one machine can do.</p>
  <p>First I'd make sure there are tested backups stored off the machine, since losing data is the worst outcome. Then I'd move the database to its own server, run at least two app servers behind a load balancer so one can fail or be redeployed without downtime, and add a standby database copy.</p>
</InterviewCard>
