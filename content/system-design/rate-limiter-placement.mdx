## The problem: 40 servers, one limit

Snip's limit is "100 link creations per minute per <Term t="api">API</Term> key". But requests from one key are spread across 40 app
servers by the load balancer. If each server keeps its own count, the key really gets 4,000 a minute. Where the
counting happens, and what it's keyed on, matters as much as the algorithm.

## The layers

| Where | Protects against | Knows |
| --- | --- | --- |
| **Edge / CDN** | Floods and abuse before they reach you | IP address, URL, headers |
| **API gateway** | Per-key and per-plan quotas, across all services | API key, user, plan, route |
| **Each service** | Overload of its own dependencies, expensive operations | Everything about the request |
| **Client** | Its own retries and bursts | Its own behaviour |

Most systems use several. Snip limits by IP at the CDN (stopping floods of redirects or link creation from one
address), by API key and plan in the gateway (100 link creations a minute on the basic plan), and inside the link
service on the database's capacity (a cap on concurrent writes, <L id="03.11" />).

## Sharing counts across servers

For a global "100 per minute per key", the count has to be shared. The usual store is **Redis**, with the check done
atomically on the server so two app servers can't both read 99 and both allow:

- A fixed or <Term t="sliding-window">sliding window counter</Term>: `INCR` the current window's key and set an expiry, in one script, compare with
  the limit.
- A <Term t="token-bucket">token bucket</Term>: a short script that reads the bucket, refills it for the elapsed time, takes a token and writes it
  back, all as one atomic step.

That adds a network round trip (around half a millisecond, <L id="01.04" />) to every limited request, and Redis
becomes a dependency of the API.

## Local limits: no round trip

Alternatives trade precision for speed:

- **Divide the limit.** With 40 servers, each allows 100 ÷ 40 per key. No coordination, but uneven load balancing makes
  it inaccurate, and it changes whenever the fleet resizes.
- **Local buckets, synced periodically.** Each server counts locally and reconciles with a shared store every second
  or so. Limits are approximately right, overshooting briefly.

For abuse protection, approximate is fine; for billing quotas ("10,000 API calls a month"), use the shared, exact
counter.

## What to key on

- **API key or user**: the normal choice for authenticated APIs. Fair and hard to evade.
- **IP address**: for unauthenticated traffic. Many users can share one IP (offices, mobile carriers), and attackers
  can rotate through many, so set it generously and combine it with other signals.
- **Route or cost**: creating a link costs far more than reading one; weight requests by cost, or give expensive
  routes their own limit.
- **Hot keys**: one enormous customer's counter in Redis is a hot key (<L id="05.02" />); a local pre-check before the
  shared one keeps it off the shard.

## When the limiter is down

If Redis is unreachable, should requests be allowed (**fail open**) or rejected (**fail closed**)? For most APIs, fail
open: a brief window without per-key limits is better than rejecting every customer, and the service's own
concurrency limits still protect it. Fail closed only where the limit protects something critical, such as a costly
third-party quota.

<Analogy>
  **Security at a festival.** The perimeter fence stops crowds and anyone obviously unwelcome (the edge). The wristband check at each stage limits how often a ticket holder can enter VIP areas, and every stage shares the same list (the gateway with a shared counter). And each bar has its own cap on how many it can serve at once (the service), whatever the wristbands say.
</Analogy>

<Mistakes>
  <ul>
    <li>**Per-server counters for global limits.** Share the count, or divide the limit deliberately.</li>
    <li>**Read-then-write checks.** Two servers race past the limit; make the check atomic in the store.</li>
    <li>**Keying only on IP.** Shared IPs punish innocent users; prefer API keys and users where you can.</li>
    <li>**Failing closed by accident.** Decide what happens when the limiter's store is down.</li>
  </ul>
</Mistakes>

## Recap

<Recap>
  <ul>
    <li>Enforce limits in layers: IP floods at the edge, per-key quotas at the gateway, capacity in each service.</li>
    <li>Global limits need a shared, atomic counter (often Redis); local limits are faster but approximate.</li>
    <li>Key on API key or user where possible, weight by cost, and watch for hot keys.</li>
    <li>Decide in advance whether to fail open or closed when the limiter is unavailable.</li>
  </ul>
</Recap>

>
  <p>Enforce at the API gateway, keyed by API key and route, with a token bucket or sliding window counter stored in Redis. Each check runs as one atomic script that reads, updates and decides, so concurrent servers can't both pass the limit, with keys expiring after the window. Responses return 429 with Retry-After and remaining-quota headers. Coarse IP-based limits sit at the edge to absorb floods, and services keep their own concurrency limits.</p>
  <p>To avoid a round trip per request, servers can hold local token buckets for a share of the limit and sync with Redis periodically, accepting slight overshoot for abuse protection but not for billing quotas. Very hot keys get a local pre-check. If Redis is unavailable I'd usually fail open, relying on per-service concurrency limits for safety.</p>
