## Forward and reverse proxies

A **proxy** is a server that passes requests along on someone's behalf. Which side it works for gives it its name:

- A **forward proxy** works for **clients**. A company's office proxy sends employees' requests out to the internet,
  filtering or logging them on the way. The websites see the proxy, not the employees.
- A **reverse proxy** works for **servers**. Clients send requests to it thinking it's the site; it passes them to
  the real servers behind it. The clients see the proxy, not the servers.

Every load balancer from <L id="03.06" /> that reads HTTP is a reverse proxy. Common software for the job includes
nginx, HAProxy and Envoy, and every cloud provider sells a managed one.

## Jobs a reverse proxy does well

Because every request passes through it, a reverse proxy is a natural home for work that's the **same for every
request**, so each application doesn't have to do it:

| Job | What it means |
| --- | --- |
| **<Term t="tls">TLS</Term> termination** | Decrypt once at the edge; certificates live in one place. |
| **Load balancing and <Term t="health-check">health checks</Term>** | <L id="03.06" />. |
| **Compression** | Gzip or Brotli responses on the way out. |
| **<Term t="cache">Caching</Term>** | Keep copies of cacheable responses, like a small <Term t="cdn">CDN</Term> in your own datacenter. |
| **Connection handling** | Hold thousands of slow client connections and keep a small pool of fast ones to the app. |
| **Request limits** | Reject huge bodies, slow uploads and malformed requests before they reach the app. |
| **Request IDs and logs** | Tag each request with an ID and log it uniformly. |

## API gateways

An **API gateway** is a reverse proxy that also handles the cross-cutting jobs of an **API**:

- **Authentication**: check the API key or token once, and pass the caller's identity to the services behind.
- **Rate limiting**: each key gets so many requests a minute; the rest get `429` (designed fully in <L id="14.03" />).
- **Routing to services**: `/links/*` to the links service, `/stats/*` to the stats service, so clients see one API
  even when there are many services behind it.
- **Request shaping**: version routing, adding or stripping headers, sometimes combining several calls into one.
- **Usage metering**: counting calls per key for billing and dashboards.

## What doesn't belong in the gateway

A gateway sees every request, so it's tempting to put logic there. Resist:

- **Business logic.** "Free accounts can't create custom codes" belongs in the links service. Logic in the gateway is
  hidden from the team that owns the feature and is shared by every route, so every change is risky.
- **Slow work.** Everything the gateway does adds latency to every request. Keep checks to in-memory lookups.
- **Being a single point of failure.** Run several instances behind a layer 4 or managed load balancer, like any other
  stateless tier.

A good rule: the gateway handles **who you are and how much you may call**; services handle **what you may do**.

    reason was connection reuse: NGINX's connection pools are per worker process, so connections to origins were
    scattered and reused less. Pingora shares pools across threads. Cloudflare reported about 70% less CPU and 67% less
    memory for the same traffic, a third as many new connections per second, and a 5 ms lower median time to first
    byte.

<Mistakes>
  <ul>
    <li>**Business rules in the gateway.** They end up far from the team that owns them, and every change risks every route.</li>
    <li>**Putting the busiest path through every layer.** Snip's redirects skip the gateway; check which features actually need it.</li>
    <li>**One gateway instance.** It's on the path of every API request; run it redundantly.</li>

## Recap

<Recap>
  <ul>
    <li>A forward proxy acts for clients; a reverse proxy acts for servers. Layer 7 load balancers are reverse proxies.</li>
    <li>Reverse proxies do per-request chores: TLS, compression, caching, connection handling, limits, logging.</li>
    <li>An API gateway adds API concerns: authentication, rate limiting, routing to services, metering.</li>
    <li>Keep business logic and slow work out of it, and run it redundantly.</li>
  </ul>
</Recap>
