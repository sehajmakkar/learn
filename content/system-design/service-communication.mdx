## A function call that crosses a network

As Snip grows, its team splits the app into services: a **links** service that owns links, a **redirect** service on
the hot path, and a **stats** service that owns counts. Now, when the dashboard needs a link and its stats, one
service calls another over the network.

It looks like a function call. It isn't. A local call either returns or throws. A network call goes through many
steps, and **any of them can fail**: the request may not arrive, the server may crash halfway, the reply may be lost.
The nastiest case is when the caller hears nothing at all:

Every design for service calls has to answer: **what do we do when the outcome is unknown?** The next two lessons
(<L id="03.09" /> and <L id="03.10" />) are the standard answers: retry carefully, and make retries safe.

## Sync or async?

There are two basic ways for one service to involve another:

- **Synchronous request–response** (HTTP, gRPC): call and wait for the answer. Simple to reason about, and the only
  option when you need the answer to continue. But the caller is now only as available and as fast as everything it
  calls.
- **Asynchronous messages** (a <Term t="message-queue">queue</Term> or event log, <L id="02.06" />): publish "link x7Kp was deleted" and carry on.
  Whoever cares (stats, search, billing) reacts in their own time. The publisher doesn't depend on them being up, at
  the cost of results arriving later.

A useful default: **ask synchronously when you need the answer now; announce asynchronously when others need to know
something happened.** Snip's dashboard asks the links service for a link (sync). When a link is deleted, the links
service publishes an event, and stats and the redirect <Term t="cache">cache</Term> react to it (async).

## Chains multiply

Each synchronous hop adds its latency and its failure chance:

| Calls in a chain, each 99.9% available and 5 ms at p50 | Availability | Typical latency |
| --- | --- | --- |
| 1 | 99.9% | 5 ms |
| 3 | 99.7% | 15 ms |
| 10 | 99.0% | 50 ms |

And the slowest call in any chain sets the pace (<L id="03.12" />). So keep synchronous chains short: fetch in
parallel where you can, cache answers that rarely change, and move anything that doesn't need an answer to async
events.

## Finding each other

Services run on many machines that come and go. A caller needs to find a healthy instance:

- **<Term t="dns">DNS</Term> or a virtual address**: call `links.internal`, which resolves to a <Term t="load-balancer">load balancer</Term> or a set of instances.
  Simple; updates are only as fast as DNS caching allows.
- **A service registry**: instances register themselves and send heartbeats; callers (or their proxies) ask the
  registry for the current list and balance across it themselves.
- **A service mesh**: a small proxy runs next to every service instance (a "sidecar") and handles discovery, load
  balancing, retries, timeouts, encryption between services and metrics, so each service just calls `localhost`.
  It gives consistent behaviour everywhere, at the cost of an extra hop per call and a lot of infrastructure to run.

<Analogy>
  **Asking a colleague versus posting in the team channel.** If you need an answer before you can continue, you call them and wait (sync), and you're stuck if they're out. If you're just letting people know something happened, you post it in the channel (async) and get on with your day; each person reads it when they can.
</Analogy>

<Mistakes>
  <ul>
    <li>**Treating a remote call like a local one.** It can be slow, fail, or leave you not knowing what happened. Plan for all three.</li>
    <li>**Long synchronous chains.** Each hop multiplies failure and adds latency. Parallelise, cache, or go async.</li>
    <li>**Calls with no timeout.** One stuck dependency can tie up every thread in the caller. <L id="03.09" /> covers this.</li>
  </ul>
</Mistakes>

## Recap

<Recap>
  <ul>
    <li>A network call has many steps that can fail; a timeout leaves the outcome unknown.</li>
    <li>Ask synchronously when you need the answer; announce asynchronously when others need to know.</li>
    <li>Synchronous chains multiply failures and add up latency. Keep them short.</li>
    <li>Services find each other via DNS, a registry, or a service mesh of sidecar proxies.</li>
  </ul>
</Recap>

  <p>Synchronously when the caller needs the answer to continue, such as fetching data to render a response or validating something before accepting a request.   <p>Synchronous calls couple availability and latency: a chain of services that are each 99.9% available is less available than any one of them, and the slowest call sets the pace.
