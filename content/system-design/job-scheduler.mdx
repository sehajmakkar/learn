## The prompt

"Design a distributed job scheduler" asks for cron that doesn't live on one machine. A crontab on one server is
simple and a single point of failure; three servers running the same crontab run every job three times. The design
is about running each job **once, on time**, across many machines that can fail.

## 1. Requirements

**Functional:** create, pause and delete schedules (cron expressions, fixed intervals, one-time); run each at its
time on a worker; retry failures; show history per schedule.

**Non-functional:**

- Runs start within a few seconds of their scheduled time.
- A run never executes twice at the same time, and normally runs once.
- No single point of failure.
- 10 million schedules; tens of thousands of runs a second at peak.

## 2. Estimates

- **Average rate:** if a typical schedule runs hourly, 10 million schedules is about **2,800 runs a second**.
- **The spike:** people write `0 * * * *`. If a third of hourly schedules are due at minute 0, that's 3.3 million runs
  in one minute, about **55,000 a second**, then quiet. The spike, not the average, sizes the system.
- **History:** 240 million runs a day at about 200 bytes is 48 GB a day; kept 30 days, **1.4 TB**, partitioned by day.

## 5. Deep dives

<DeepDive title="Finding what's due">
  <Option grade="bad" name="Scan every schedule every second">
    10 million rows a second to find a few thousand due ones.
  </Option>
  <Option grade="good" name="An index on next_run_at, polled with SKIP LOCKED">
    `WHERE next_run_at <= now() ORDER BY next_run_at LIMIT 100` reads only due rows, and several schedulers poll at
    once without blocking each other (<L id="07.05" />).
  </Option>
  <Option grade="great" name="The index, sharded, with the next minute held in memory">
    Partition schedules by hash of ID across database shards, each polled by its own schedulers. For tight timing,
    each scheduler also loads the coming minute's due rows into an in-memory timer and fires them on the second,
    claiming each just before it runs.
  </Option>
</DeepDive>

<DeepDive title="Never running a job twice at once">
  <Option grade="bad" name="One scheduler, or several with no coordination">
    One is a single point of failure; several each run everything, so every job runs N times.
  </Option>
  <Option grade="good" name="Elect a leader; only it schedules">
    Correct with a proper lease (<L id="08.07" />), but one machine does all the work, and failover leaves a gap.
  </Option>
  <Option grade="great" name="Claim each row with a lease and a fence; record runs uniquely by slot">
    Any scheduler can claim any due row. The lease frees the row if its holder dies; the fence number, incremented on
    every claim, rejects a late finish from a holder that lost its lease (<L id="08.08" />); and the run's unique
    (schedule, slot) key makes a duplicate enqueue a no-op. Jobs themselves are idempotent, because at-least-once is
    still the honest guarantee (<L id="07.03" />).
  </Option>
</DeepDive>

```ts
export async function claimDue(db: pg.Pool, owner: string, limit = 10, leaseSeconds = 30) {
  const { rows } = await db.query(
    `UPDATE schedules SET owner = $1, lease_until = now() + make_interval(secs => $3), fence = fence + 1
     WHERE id IN (SELECT id FROM schedules
                  WHERE next_run_at <= now() AND (lease_until IS NULL OR lease_until < now())
                  ORDER BY next_run_at LIMIT $2 FOR UPDATE SKIP LOCKED)
     RETURNING id, next_run_at, fence`,
    [owner, limit, leaseSeconds],
  );
  return rows as { id: number; next_run_at: Date; fence: number }[];
}

export async function finish(db: pg.Pool, id: number, fence: number) {
  // Move to the next slot after now, skipping any missed while the scheduler was down.
  const { rowCount } = await db.query(
    `UPDATE schedules
     SET next_run_at = next_run_at + every * (floor(extract(epoch FROM now() - next_run_at) / extract(epoch FROM every)) + 1),
         owner = NULL, lease_until = NULL
     WHERE id = $1 AND fence = $2`,
    [id, fence],
  );
  return rowCount === 1; // false: our lease expired and someone else has the job now
}
```

Tested on Postgres 16 with 100 due schedules of "every minute" and four schedulers claiming in batches of 10 at the
same time: all 100 were claimed, each by exactly one scheduler. With 2-second leases and nobody finishing, a fifth
scheduler reclaimed all 100 once the leases expired. The original holder's finish for schedule 1 was then rejected,
because its fence was stale; the new holder's finish succeeded, cleared the lease and set the next run about a minute
ahead.

<DeepDive title="Runs missed during an outage">
  <Option grade="bad" name="Run every missed slot when you come back">
    After a 10-minute outage, every per-minute job runs ten times at once: a self-inflicted spike, and usually
    pointless (ten copies of the same report).
  </Option>
  <Option grade="good" name="Skip to the next slot">
    No spike, but a daily billing job that missed 09:00 doesn't run until tomorrow.
  </Option>
  <Option grade="great" name="A policy per schedule, defaulting to 'run once now, then resume'">
    Most jobs want "run once to catch up, then carry on"; a few want every slot (each day's invoices); some want to
    skip. The schedule stores which, and the scheduler applies it.
  </Option>
</DeepDive>

Tested: a per-minute schedule left 10 minutes 30 seconds overdue was claimed and run once, and `finish` set its next
run about 30 seconds ahead, at the next whole slot, instead of queueing ten catch-up runs.

**The top of the hour.** When a third of all hourly jobs are due at minute 0, spread them: for schedules that don't
care about the exact minute ("hourly"), pick the minute from a hash of the schedule ID, so load is even across the
hour. Keep the exact spec for the ones that do care, and size workers for that smaller spike.

**Executors.** Long jobs send heartbeats that extend their lease; a job whose heartbeats stop is presumed dead and
retried. Each job has a timeout, retries with exponential backoff and jitter, and a dead-letter queue after the last
attempt. A schedule that hasn't succeeded within twice its interval raises an alert: the most dangerous failure of a
scheduler is a job that silently stops running.

## 6. Wrap-up

What breaks first: **the database** behind the schedules, at tens of thousands of claims a second during a spike, so
schedules are sharded and claims are batched; then **time zones**: "09:00 daily" in a zone with daylight saving time
happens twice, or not at all, once a year, so next run times are computed with a time zone library, never by adding
24 hours.

<Mistakes>
  <ul>
    <li>**The same crontab on several machines.** Every job runs once per machine.</li>
    <li>**Leases without fencing.** A paused holder wakes up and acts on work it lost.</li>
    <li>**Catching up every missed slot.** Choose a policy per job; default to running once.</li>
    <li>**No alert for silence.** A job that stops running fails without a single error.</li>

## Recap

<Recap>
  <ul>
    <li>Schedules live in a table indexed by next run time; schedulers claim due rows with SKIP LOCKED.</li>
    <li>Leases free work from dead schedulers; fence numbers stop late finishes; unique runs per slot stop duplicates.</li>
    <li>Choose missed-run policies per job, and spread "hourly" jobs across the hour.</li>
    <li>Executors heartbeat, time out, retry with backoff, and alert when a schedule stops succeeding.</li>
  </ul>
</Recap>

>
  <p>Schedules are rows with a cron spec, time zone and next_run_at, indexed on next_run_at and sharded by ID. Several stateless schedulers poll each shard every second, claiming due rows with FOR UPDATE SKIP LOCKED, setting a lease and incrementing a fence number. Each claim records a run unique by schedule and slot and enqueues it; executors heartbeat to extend the lease, time out, and retry with backoff into a dead-letter queue.</p>
  <p>If a scheduler dies, its lease expires and another claims the row; if it was only paused, its finish is rejected because the fence moved on. Jobs are still idempotent, since delivery is at least once. Missed runs follow a per-schedule policy, usually run once then resume. The top-of-hour spike is spread by hashing flexible hourly jobs across the hour, and an alert fires when a schedule hasn't succeeded within twice its interval.</p>
