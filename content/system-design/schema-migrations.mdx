## The problem: the table never stops

Snip wants to rename `links.long_url` to `target_url`, and add a `title` column. On a laptop that's two statements and
a second. On a 600-million-row table taking thousands of reads a second, the wrong statement can **lock the table**
while the database rewrites every row, and every redirect waits behind it.

Two things make schema changes risky in production:

- **Locks.** Some changes need an exclusive lock on the table; some rewrite the whole table while holding it.
- **Old and new code at once.** During a deploy, servers running the previous version and the new version both talk
  to the same database. Every intermediate state of the schema has to work for both.

## Know which changes are cheap

What locks and what doesn't varies by database and version, so check your database's documentation. The usual
shape, for Postgres:

| Change | Typically |
| --- | --- |
| Add a nullable column, no default | Instant: only the table's description changes |
| Add an index | Blocks writes for the whole build, unless built `CONCURRENTLY` |
| Change a column's type | Often rewrites the whole table under an exclusive lock |
| Add a `NOT NULL` constraint | Scans the table to check every row |
| Rename a column | Instant for the database, but breaks every running app that uses the old name |

Two habits avoid most outages: build indexes **concurrently**, and set a short **<Term t="lock-timeout">lock timeout</Term>** on migration
sessions. Even an instant change must first acquire its lock; if a long query holds the table, the migration waits,
and every new query queues behind the waiting migration. A lock timeout makes the migration give up and retry instead
of freezing the table.

## Expand and contract

A rename looks atomic, but code that reads `long_url` breaks the moment it's gone. The safe method splits the change
into steps, each compatible with the code before and after it:

<Flow
  title="Renaming long_url to target_url without downtime"
  steps={[
    { label: "Expand", detail: "Add target_url, nullable. Old code ignores it." },
    { label: "Dual write", detail: "Deploy code that writes both columns." },
    { label: "Backfill", detail: "Copy old rows' values, in small batches." },
    { label: "Switch reads", detail: "Deploy code that reads target_url." },
    { label: "Stop old writes", detail: "Deploy code that writes only target_url." },
    { label: "Contract", detail: "Drop long_url once nothing uses it." },
  ]}
/>

Each step can be deployed, watched and rolled back on its own. It's slower than one `ALTER`, and it's the only way that
never breaks a running request.

**Backfilling** 600 million rows deserves care of its own: update in batches of a few thousand rows by <Term t="primary-key">primary key</Term>
range, pause between batches, watch replication lag (<L id="04.07" />), and make the job resumable. One giant
`UPDATE` would hold locks for hours, bloat the table (<L id="04.05" />) and leave replicas far behind.

The same pattern moves data between **tables** or even **databases**: write to both, backfill, compare, switch reads,
switch writes, remove the old.

<Analogy>
  **Renaming a street.** You don't take the old signs down the night the council votes. First, new signs go up next to the old ones; post is delivered to either name; maps update; and only years later, when nobody uses the old name, do the old signs come down.
</Analogy>

<Mistakes>
  <ul>
    <li>**Rename or drop in one step.** Running code still uses the old name. Expand, migrate, then contract.</li>
    <li>**One huge backfill UPDATE.** Batch it, throttle it, watch replica lag, and make it resumable.</li>
    <li>**Creating an index without CONCURRENTLY.** Writes to the table stop for the whole build.</li>
    <li>**No lock timeout.** A migration stuck waiting for a lock blocks every query behind it.</li>
  </ul>
</Mistakes>

## Recap

<Recap>
  <ul>
    <li>Some schema changes lock or rewrite whole tables; know which, and check your database's docs.</li>
    <li>Build indexes concurrently and give migrations a short lock timeout.</li>
    <li>Expand and contract: add, dual write, backfill, switch reads, switch writes, remove.</li>
    <li>Backfill in small, throttled, resumable batches.</li>
  </ul>
</Recap>
