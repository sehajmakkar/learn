## The problem: an expensive read on every page

Snip's dashboard lists an owner's links with each one's **total clicks**, and lets them sort by it. In the <Term t="normalisation">normalised</Term>
model, totals live only in `clicks_daily`: one row per link per day. To sort Ana's 8,000 links by total clicks, the
database must add up every daily row for all 8,000 links (millions of rows) on every page load.

The answer is the same every time until the next batch of clicks arrives. Computing it again and again is wasted
work. **Denormalisation** stores the answer:

```sql
ALTER TABLE links ADD COLUMN total_clicks bigint NOT NULL DEFAULT 0;
CREATE INDEX links_owner_clicks ON links (owner_id, total_clicks DESC);
```

Now "Ana's links by clicks" is one <Term t="index">index</Term> range read. The price: the same fact (how many times x7Kp was clicked) is
stored in two places, and they must agree.

## Three ways to keep the copy right

**1. Update it in the same <Term t="transaction">transaction</Term>.** Whatever writes the source also updates the copy, atomically:

```sql
BEGIN;
INSERT INTO clicks_daily (code, day, clicks) VALUES ('x7Kp', '2026-11-04', 1840)
  ON CONFLICT (code, day) DO UPDATE SET clicks = clicks_daily.clicks + EXCLUDED.clicks;
UPDATE links SET total_clicks = total_clicks + 1840 WHERE code = 'x7Kp';
COMMIT;
```

Always consistent, which is why Snip's stats workers (<L id="02.06" />) do exactly this. It only works when both
live in the same database, and every write now does more work.

**2. Update it from events, asynchronously.** The source publishes "x7Kp got 1,840 clicks"; a consumer updates the
copy, maybe in another database or a search index. Works across systems; the copy lags, and the consumer must cope
with duplicates (<L id="07.03" />).

**3. Recompute it periodically.** A job (or a materialised view) rebuilds the totals every few minutes. Simplest to
get right, staleness up to the interval, and the rebuild itself costs work.

Whichever you choose, add a **reconciliation** job that recomputes a sample (or all) of the copies from the source now
and then and reports differences. Copies drift, through bugs, manual fixes or <Term t="partial-failure">partial failures</Term>, and you want to find
out from a report, not from a customer.

<Analogy>
  **A bank balance.** The bank could add up every transaction since you opened the account each time you check your balance. Instead it keeps a running balance, updated with every transaction, and the statement (the source of truth) is reconciled against it regularly. The balance is denormalised, and it's what everyone actually looks at.
</Analogy>

## When it's worth it

Denormalise when **all** of these hold:

- The read is **frequent** or on a **hot path**, and measurably slow or expensive without the copy.
- The copy can be kept correct with one of the methods above, at a write cost you can afford.
- You know which copy is the **source of truth** if they ever disagree.

Common, well-worn cases: counters (likes, followers, clicks), the latest item (a conversation's last message for the
inbox view), names copied onto records for display, and whole read-optimised tables in partition-keyed stores, where
copying data into one table per query is the normal pattern (<L id="04.10" />).

<Mistakes>
  <ul>
    <li>**Denormalising before measuring.** Joins and aggregates on indexed data are often fast enough. Copy when a real query is slow.</li>
    <li>**No named source of truth.** When copies disagree, you need to know which one wins.</li>
    <li>**No reconciliation.** Every copy drifts eventually; check them on a schedule.</li>
  </ul>
</Mistakes>

## Recap

<Recap>
  <ul>
    <li>Denormalisation stores a derived fact again so a hot read is cheap.</li>
    <li>Keep copies right by updating in the same transaction, from events, or by periodic recompute.</li>
    <li>Name the source of truth, and reconcile copies against it regularly.</li>
    <li>Worth it for frequent, expensive reads where the write cost is affordable.</li>
  </ul>
</Recap>
