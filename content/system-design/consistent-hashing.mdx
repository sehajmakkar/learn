## The problem: hash mod N moves almost everything

At peak, Snip's redirects make about 100,000 cache reads a second, spread over four Redis nodes. Each code goes to node
`hash(code) mod 4`. The cache is running hot, so you add a fifth node, and the formula becomes `hash(code) mod 5`.

For most codes, `mod 5` gives a different answer from `mod 4`. **About 80% of keys now map to a different node**,
where they aren't cached. For the next few minutes, 80% of redirects miss and fall through to the database shards:
tens of thousands of extra queries a second, the moment you tried to add capacity. Removing a node (or losing one) does
the same.

Only a fifth of the keys *needed* to move, the share the new node should take. **Consistent hashing** moves roughly
that share and no more.

## The ring

Picture the output of the hash function, 0 to 2³²−1, bent into a circle.

1. **Place each server on the ring** by hashing its name: `hash("redis-A")` gives its position.
2. **Place each key on the ring** by hashing it: `hash("x7Kp")`.
3. **A key belongs to the first server clockwise from it.**

Now add server E. It lands at one point on the ring and takes over only the keys between itself and the server before
it, keys that used to belong to the next server along. **Every other key stays where it was.** Remove a server, and
only its keys move, to the next server clockwise.

## Virtual nodes

With one point per server, the arcs between servers are random lengths, so one server may own three times the keys of
another. And when a server leaves, all its keys go to a single neighbour, which suddenly has double the load.

The fix is **virtual nodes**: put each server on the ring many times (`redis-A#0`, `redis-A#1`, … `redis-A#199`). With
hundreds of points each, every server owns many small arcs scattered round the ring, so loads even out, and a
departing server's keys spread across all the others. A bigger machine can simply get more virtual nodes.

With 10,000 keys, the lab shows the pattern clearly. `mod N` moves about 80% of keys going from four servers to five.
The ring with one point per server moves far fewer, but its busiest server can hold nearly twice the average. With 200
virtual nodes, adding a fifth server moves about 21% of keys (a fair share is 20%), and the busiest server is within a
few percent of the average.

<Analogy>
  **Seats round a table.** Guests sit down, and each guest is served by the waiter standing next clockwise. When a new waiter joins, they step in between two others and take over only the guests in that gap. Nobody else at the table changes waiter. Giving each waiter several spots round the table keeps their workloads even.
</Analogy>

## A small implementation

A ring is a sorted array of positions. Finding a key's server is a binary search for the first position at or after
the key's hash, wrapping to the start.

```ts
import { createHash } from "node:crypto";

// 32-bit position on the ring, from the first 4 bytes of an MD5 hash
const position = (s: string) => createHash("md5").update(s).digest().readUInt32BE(0);

export class HashRing {
  private points: { at: number; node: string }[] = [];

  constructor(private vnodes = 200) {}

  add(node: string) {
    for (let v = 0; v < this.vnodes; v++) this.points.push({ at: position(`${node}#${v}`), node });
    this.points.sort((a, b) => a.at - b.at);
  }

  remove(node: string) {
    this.points = this.points.filter((p) => p.node !== node);
  }

  /** The node that owns `key`: the first point clockwise from the key's position. */
  get(key: string): string {
    if (this.points.length === 0) throw new Error("empty ring");
    const h = position(key);
    let lo = 0;
    let hi = this.points.length;
    while (lo < hi) {
      const mid = (lo + hi) >> 1;
      if (this.points[mid].at < h) lo = mid + 1;
      else hi = mid;
    }
    return this.points[lo % this.points.length].node;
  }
}
```

```ts
const ring = new HashRing();
["redis-A", "redis-B", "redis-C", "redis-D"].forEach((n) => ring.add(n));
ring.get("x7Kp"); // → "redis-B", and the same answer on every app server
```

Every client that builds the ring from the same list of nodes gets the same answers, with no coordination. The hash
doesn't need to be secure, only fast and evenly spread; MD5 is used here because it's built into Node.

## Replicas: walk further round

To keep N copies of each key, walk clockwise from the key and take the first N **distinct physical servers**, skipping
virtual nodes of a server you already have. If one fails, the next server along already holds a copy. This is how
Dynamo-style databases place replicas (<L id="08.04" />).

## Where it's used, and the alternatives

Consistent hashing shows up wherever many clients must agree, without asking anyone, which server owns a key: cache
clusters (<L id="06.06" />), distributed databases, and load balancers that send the same user or object to the same
backend (<L id="03.06" />).

Two related techniques are worth recognising. **Rendezvous hashing** scores every server for a key (hash of key plus
server) and picks the highest: simple, with no ring to store, at the cost of checking every server per lookup.
**Bounded loads** caps each server at a little above the average; a key whose server is full moves on clockwise to the
next one with room, which keeps hot spots from overloading one server.

<Mistakes>
  <ul>
    <li>**`hash(key) mod N` for anything that grows.** Changing N remaps almost every key.</li>
    <li>**One point per server.** Load is uneven and a failure dumps everything on one neighbour. Use hundreds of virtual nodes.</li>
    <li>**Clients with different server lists.** Each builds a different ring and they disagree about where keys live. Distribute membership from one source.</li>
  </ul>
</Mistakes>

## Recap

<Recap>
  <ul>
    <li>hash mod N moves about (N−1)/N of keys when N changes; consistent hashing moves about 1/N.</li>
    <li>Servers and keys are hashed onto a ring; each key belongs to the first server clockwise.</li>
    <li>Virtual nodes even out load, spread a failed server's keys, and weight bigger machines.</li>
    <li>Replicas go to the next distinct servers clockwise; bounded loads and rendezvous hashing are close relatives.</li>
  </ul>
</Recap>
