## Start from the questions, not the products

"Which database should we use?" is the wrong first question. Answer these first, per kind of data, and the choice
usually follows:

| Question | Why it matters |
| --- | --- |
| **What are the top queries?** | By key? By range? Ad hoc? Full text? Aggregates over billions of rows? |
| **What are the numbers?** | Reads and writes per second, total size, growth (<L id="01.05" />). |
| **What guarantees?** | Multi-row <Term t="transaction">transactions</Term>? Strong consistency, or is a little lag fine? Can any data ever be lost? |
| **How will it change?** | New queries every month (favour flexible) or one fixed pattern (favour specialised)? |
| **Who runs it?** | What your team already knows, and whether a managed service exists, often outweigh benchmarks. |

## A sensible default

For most products, the default is a **relational database** (Postgres or MySQL), run as a managed service, plus a
cache. It handles relations, transactions, constraints and new queries, and with the ladder from <L id="04.08" /> it
scales much further than most products ever need.

Then add a specialised store when a specific kind of data **earns** it:

- **Write volume or size beyond one database**, with simple access by key: key-value or wide-column.
- **Full-text search** or many-field filtering: a search <Term t="index">index</Term>, fed from the main database.
- **Analytics over huge event volumes**: a <Term t="columnar-store">columnar store</Term>, fed by a pipeline.
- **Relationships many hops deep**, queried constantly: a graph database.
- **Large files**: object storage, with only metadata in the database.

Every extra store is another system to run, secure, back up and keep consistent with the others (the data moves
between them asynchronously, so they disagree briefly). That cost is why the list stops at four.

<Analogy>
  **Furnishing a kitchen.** A good knife, a pan and a pot cover most cooking. You buy a rice cooker if you eat rice every day, not because restaurants have one. Every gadget takes counter space and cleaning, so each one should earn its place.
</Analogy>

<Mistakes>
  <ul>
    <li>**Choosing by popularity or benchmark.** Choose from your queries, numbers and guarantees.</li>
    <li>**Ignoring operations.** The database your team can run, back up and debug at 3 a.m. is worth a lot of benchmark points.</li>
    <li>**Collecting stores.** Each one adds work and a consistency boundary. Add one when it's earned.</li>
  </ul>
</Mistakes>

## Recap

<Recap>
  <ul>
    <li>Choose per kind of data, from its top queries, numbers, guarantees and how it will change.</li>
    <li>Default to a managed relational database plus a cache; it goes a long way.</li>
    <li>Add search, columnar, key-value or graph stores when a specific need earns them.</li>
    <li>Every store adds operational work and data that must be kept in step.</li>
  </ul>
</Recap>

## Interview questions

  q={{ q: "How do you decide which database to use for a new system?", level: "Mid", frequency: 3, importance: "Must-know", kind: "Concept" }}

>
  <p>I start from the data, not the product: what the main queries are, the read and write rates and size, the guarantees needed such as transactions and consistency, and how much the queries will change. Then I weigh what the team already runs well and whether there's a managed option.</p>
  <p>For most systems that leads to a relational database with a cache as the source of truth. I'd add a specialised store only for a specific need, like a search index for full text, a columnar store for analytics, or a wide-column or key-value store when a dataset's write volume outgrows one database, and feed it from the source of truth through change events.</p>
