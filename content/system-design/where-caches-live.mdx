## The problem: "add a cache" isn't one decision

By the end of Module 05, Snip already has caches in three places: a CDN for its static files, a tiny in-process cache
on each app server for viral codes, and a Redis cluster for every redirect. They weren't planned as a set; each was
added when something hurt. Now the team wants to know: **where should a copy of a link live, and why there and not
somewhere else?**

Follow one redirect for `snip.link/x7Kp` from a phone in Sydney. Every hop it passes is a place that could answer it:

## The layers, compared

| Layer | Typical cost of a hit | Shared by | Who can clear it |
| --- | --- | --- | --- |
| **Browser** | Nothing: no request is sent | One user | Only expiry: you can't reach into someone's browser |
| **CDN edge** | A few ms, nearby | Everyone near that edge | You, by <Term t="purge">purging</Term>, or expiry |
| **Reverse proxy** | Under a ms, inside the datacenter | Everyone reaching that datacenter | You |
| **In-process (app memory)** | About 100 ns | Requests on one app server | Each server separately |
| **Shared cache (Redis, Memcached)** | About 0.5 ms round trip | Every app server | You, with one delete |
| **Database buffer cache** | A query's CPU, no disk | Every query | The database, automatically |

Two things change as you move outwards, towards the user. Hits get **cheaper** and save more work, because a hit at the
edge skips everything behind it. But you get **less control**: a copy in a browser stays until it expires, whatever
you do. That's why the outer layers suit data that's the same for everyone and rarely changes (fingerprinted files,
<L id="02.05" />), and the inner layers suit data that changes or is personal.

## Local or shared?

The biggest design choice inside the datacenter is whether the app keeps its own copy in memory or asks a shared cache.

| | In-process cache | Shared cache (Redis) |
| --- | --- | --- |
| **Speed** | Fastest: no network | One round trip |
| **Hit rate** | Each server warms its own copy, so lower | One copy serves everyone, so higher |
| **After a deploy** | Every new server starts empty | Stays warm |
| **Consistency** | 40 servers, 40 copies that can disagree | One copy |
| **Memory** | Takes memory from the app | Its own machines |

The common answer is **both**, as two levels: a small in-process cache with a short <Term t="ttl">TTL</Term> (seconds) for the hottest keys,
in front of a large shared cache with a longer one. The in-process level absorbs viral traffic (<L id="05.02" />); the
shared level gives a high hit rate and survives deploys. The short TTL bounds how long the 40 local copies can
disagree.

<Analogy>
  **Where you keep your keys.** Your pocket is fastest, but it's yours alone and holds little. The hook by the front door is shared by the household. The spare with a neighbour is slow to fetch but survives you losing everything else. Each place is right for some things, and you'd be unwise to rely on only one.
</Analogy>

## The danger: a cache you can't live without

A cache that's down should make Snip slower, not stop it. But at 100,000 redirects a second with a 99% hit rate, the
database sees 1,000 reads a second, and it was sized for that. If Redis disappears, it sees 100,000, a hundred times
its normal load, and falls over. The cache has stopped being an optimisation and become **part of the capacity**.

Ways to stay honest about it:

- **Know the number.** Work out what the database would see with the cache empty, and decide whether you can survive it.
- **Protect the database anyway.** Limit how many cache misses can reach it at once (<L id="03.11" />), and coalesce
  them (<L id="06.05" />), so a cold cache means slow requests rather than a dead database.
- **Warm before serving.** Bring new cache nodes or regions into use gradually, filled from a warm copy.
- **Test it.** Turn the cache off in a test environment, or empty one node in production, and watch what happens.

<Mistakes>
  <ul>
    <li>**Caching personal data in shared layers.** Anything per-user belongs in-process, in Redis under a per-user key, or nowhere: never in a CDN or proxy cache shared between users.</li>
    <li>**Long TTLs on layers you can't clear.** A browser copy can't be recalled. Keep browser lifetimes short for anything that can change.</li>
    <li>**Forgetting the layers you didn't add.** The database and OS already cache. Measure before adding a layer that duplicates them.</li>
    <li>**Treating the cache as optional when it isn't.** If the database can't survive a cold cache, plan for that day.</li>
  </ul>
</Mistakes>

## Recap

<Recap>
  <ul>
    <li>Caches can sit in the browser, a CDN, a proxy, the app's memory, a shared store and the database.</li>
    <li>Outer layers save more work per hit but are harder to clear; inner layers are easier to keep correct.</li>
    <li>In-process caches are fastest but start cold and disagree; shared caches are one copy for everyone. Use both, as two levels.</li>
    <li>Know what the database would face with the cache empty, and protect it.</li>
  </ul>
</Recap>

  <p>From the user inwards: the browser's HTTP cache, a CDN at the edge, a reverse proxy, an in-process cache inside each application server, a shared cache such as Redis or Memcached, and the database's own buffer cache. Hits further out save more work but are harder to invalidate, because I can't clear a browser and purging a CDN takes time.</p>
  <p>I decide by asking who shares the data and how fresh it must be. Public, rarely changing content goes to the CDN with long lifetimes. Shared data that changes goes in a shared cache with explicit invalidation. Very hot keys get a small in-process cache with a TTL of seconds in front. I'd also check that the database can survive the cache being empty, and limit or coalesce misses so a cold cache degrades instead of cascading.</p>
