## The problem: committed means committed

When Snip's database says a new link is committed, Snip hands out the short code. If the power fails a millisecond
later, the link must still exist when the server comes back. That's **durability**.

The obvious approach, writing the changed rows straight into their places in the data files before answering, has two
problems. It's **slow**: one transaction may touch pages scattered across several files and indexes, and random
writes are the expensive kind. And it's **fragile**: a crash halfway through writing an 8 KB page can leave it half
old, half new.

## Write the log first

The **write-ahead log** (WAL) fixes both. Every change is first described in a record appended to the end of a log
file. The rule is in the name: **the log is written before the data**.

After a crash, the database starts from the last **checkpoint** (a point where every change up to there was in the
data files) and **replays** the log from there, redoing every committed change. Changes from <Term t="transaction">transactions</Term> that never
committed are discarded. Half-written pages are repaired from the log too.

Why it's fast: the commit waits only for a **sequential append** to one file, the cheapest kind of disk write. The
scattered, random page writes happen later, in the background, and many commits' worth of changes to the same page
are written once. Busy databases also **group commit**: one flush covers every transaction that committed in the same
millisecond or so.

<Analogy>
  **A ship's logbook.** The crew doesn't redraw the whole chart after every turn; they jot "14:02, turned 10° east" in the logbook, which is quick. If the chart gets damaged, they can rebuild it from the last clean copy plus every entry since. The logbook is written first, always.
</Analogy>

## One log, three more jobs

Once you have an ordered record of every change, it turns out to be useful well beyond crash recovery:

- **Replication.** Send the log to another server and have it replay the records: that's a replica (<L id="04.07" />).
- **Point-in-time recovery.** Take a full **base backup** now and then, and archive every WAL file since. To recover
  to "10:42 yesterday, just before someone ran the bad `DELETE`", restore the base backup and replay the archived log
  up to 10:41.
- **Change data capture.** Read the log to stream every change to other systems: search <Term t="index">indexes</Term>, caches, analytics
  (<L id="07.06" />).

## The log is only as good as your backups

The WAL protects against crashes, not against mistakes, lost disks or lost machines. Those need **backups stored
elsewhere, which you have actually restored**. A backup system that has never been tested is a hope, not a backup.

<Mistakes>
  <ul>
    <li>**Turning off fsync for speed.** Commits get faster and a power cut can lose or corrupt data. Use group commit, or accept the risk knowingly for data you can rebuild.</li>
    <li>**Untested backups.** Restore regularly into a scratch environment and check the result; alert when backups fail.</li>
    <li>**Treating replicas as backups.** A mistake like a bad DELETE replicates instantly. You need point-in-time recovery too.</li>
  </ul>
</Mistakes>

## Recap

<Recap>
  <ul>
    <li>A commit is durable once its WAL record is flushed; data pages are written later at checkpoints.</li>
    <li>After a crash, replaying the log from the last checkpoint restores every committed change.</li>
    <li>Sequential log appends and group commit make this fast.</li>
    <li>The same log drives replication, point-in-time recovery and change data capture. Backups still need testing.</li>
  </ul>
</Recap>
