## The problem: work in the wrong place

Two jobs are still done **while the user waits**, and both hurt.

**Counting clicks.** Every redirect runs `UPDATE links SET clicks = clicks + 1` before answering. At 100,000
redirects a second that's 100,000 writes a second on the primary, which was built for about 350. Worse, a viral link
gets thousands of updates a second **to the same row**, and each one waits for the one before it to release the row.
Redirects for that link slow to a crawl at exactly the moment it matters most.

**Checking new links.** Snip checks every new long URL against an outside service that lists malware and phishing
sites. It usually answers in 200 ms, sometimes takes two seconds, and now and then is down. While the check runs, the
owner waits. When the service is down, nobody can create links.

Neither job's result is needed to answer the request. The redirect only needs the long URL; the owner only needs the
short code.

## The idea: do it later

Put the work on a **queue** and answer straight away. A queue is a list of messages that keeps them safely until
something takes them off. Separate programs called **workers** take messages from the queue and do the work at their
own pace.

The link check works the same way, with a twist that's worth saying out loud. The link is saved and **works
immediately** (a requirement), and a check message goes on a second queue. Within seconds a worker checks it; if the
URL is dangerous, the worker disables the link and deletes its <Term t="cache">cache</Term> entry. The cost of that choice: a bad link can
work for a few seconds. The alternative, making every owner wait for the check and blocking creation when the service
is down, was judged worse. A stricter product could choose differently.

<Analogy>
  **A restaurant's order slips.** The waiter doesn't stand in the kitchen while your food cooks. They clip an order slip on the rail and go back to the tables. Cooks take slips in order, and if a rush comes in, the slips just pile up a little until the kitchen catches up. Nobody is turned away at the door because the grill is busy.
</Analogy>

## What a queue buys

- **Fast requests.** The user waits for the append, not the work.
- **Smoothed spikes.** If clicks jump tenfold for an hour, the queue grows and workers catch up afterwards. The
  database sees a steady stream instead of the spike.
- **Isolation from failures.** When the link-check service is down, messages wait in the queue and are retried later.
  Link creation keeps working.
- **Separate scaling.** Add workers when the queue grows, without touching the app servers.

## What it costs

- **Results arrive later.** Counts are seconds behind, and a link is checked a moment after it starts working. Only
  move work whose result can wait.
- **Duplicates.** Most queues guarantee each message is delivered **<Term t="at-least-once">at least once</Term>**, not exactly once. If a worker
  adds a batch to the counts and then crashes before telling the queue it's done, the batch is delivered again and
  counted twice. Workers need to be safe to repeat, for example by recording which batches they've applied. That's
  <L id="07.03" />.
- **Order isn't guaranteed** unless you design for it (<L id="07.04" />).
- **Something new to watch.** Track how many messages are waiting and how old the oldest one is. A growing queue
  means workers can't keep up. Messages that fail again and again go to a separate **dead-letter queue** so they
  don't block the rest.

## Which work should be async?

| Snip task | Sync or async | Why |
| --- | --- | --- |
| Redirect | Sync | The user is waiting for the answer. |
| Create a link | Sync | The owner needs the short code now. |
| Count a click | Async | Counts may lag a minute; doing it inline is the bottleneck. |
| Check a URL for malware | Async | Slow, unreliable outside service; a few seconds' delay is acceptable. |
| Email a weekly stats report | Async, on a schedule | Nobody is waiting; it can run at 3 a.m. |

A good rule: if the user can't continue without the result, do it now. If they can, it's a candidate for the queue.

<Mistakes>
  <ul>
    <li>**Queuing work the user needs.** If the next screen needs the result, a queue just adds delay and complexity.</li>
    <li>**Assuming exactly-once.** Plan for every message being processed twice, and make that harmless.</li>
    <li>**Not watching the queue.** A queue hides problems until it's hours behind. Alert on its depth and on the age of the oldest message.</li>
  </ul>
</Mistakes>

## Recap

<Recap>
  <ul>
    <li>Work whose result the user doesn't need right away can go on a queue and be done by workers.</li>
    <li>Snip queues click events and batches them, turning 100,000 row updates a second into a few writes per link.</li>
    <li>Queues give fast requests, smoothed spikes and isolation from failing services.</li>
    <li>They cost delay, duplicates (at-least-once delivery) and a new thing to monitor.</li>
  </ul>
</Recap>

## Interview questions

<InterviewCard
  q={{ q: "When would you use a message queue in a design? What problems does it introduce?", level: "Mid", frequency: 3, importance: "Must-know", kind: "Concept" }}
  followUps={["What does at-least-once delivery mean for your workers?", "What would you monitor on a queue?"]}
>
  <p>When work doesn't have to finish before the user gets a response: sending email, processing uploads, updating counters, calling slow or unreliable outside services. The request adds a message and returns, and workers process messages at their own pace. That keeps requests fast, absorbs spikes, lets the work be retried when a dependency is down, and lets workers scale separately.</p>
  <p>The costs: results are delayed, most queues deliver at least once so workers must be idempotent, ordering isn't guaranteed by default, and you need to monitor queue depth and message age and handle messages that keep failing, usually with a dead-letter queue.</p>
</InterviewCard>

<InterviewCard
  q={{ q: "How would you count clicks on a link that suddenly gets 50,000 clicks a second?", level: "Mid", frequency: 2, importance: "Good to know", kind: "Design" }}
  followUps={["How accurate do the counts need to be?", "How would you avoid double counting if a worker crashes?"]}
>
  <p>Not by updating one database row per click: every update would contend for the same row lock, and the redirect would wait on it. I'd have the redirect path publish a click event to a queue or log and return immediately. Workers consume events in batches, aggregate counts per link in memory, and write one increment per link per batch.</p>
  <p>That turns 50,000 writes a second into a handful, at the cost of counts lagging by seconds. To avoid double counting on retries, the worker records which batch or offset it has applied in the same transaction as the counts.</p>
</InterviewCard>
