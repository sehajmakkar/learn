## The problem: a bug in last month's numbers

A bug in Snip's click consumer counted clicks from link previews (chat apps fetching a link to show a thumbnail) as
real clicks. It ran for three weeks. Owners' charts, totals, unique visitors and top referrers are all inflated by
different amounts. If the only thing Snip stored was the counts, the true numbers would be gone for good.

## Raw events are the truth; everything else is derived

Separate two kinds of data:

- **Raw events**: every click as it happened (code, time, country, referrer, user agent, visitor hash). Append-only,
  never edited. Large, but cheap to keep compressed in object storage (<L id="09.04" />), partitioned by day.
- **Derived data**: everything computed from them. Per-minute counts, daily unique-visitor <Term t="sketch">sketches</Term>, top referrers,
  latency <Term t="histogram">histograms</Term>. Small, fast to query, and **replaceable**.

Because derived data can always be recomputed from raw events, a bug in a derivation is fixable: correct the code,
recompute the affected period, swap the results in. Snip fixed the preview bug by filtering previews by user agent and
recomputing three weeks of rollups from the archive overnight.

## Rollups

A **rollup** <Term t="pre-aggregation">pre-aggregates</Term> raw events at a coarser grain: one row per (link, country, minute) instead of one per
click. Analytics stores do this at ingestion; Apache Druid, for example, combines rows with identical dimensions and
truncated timestamps into one, which can cut row counts by orders of magnitude. The documentation is clear about the
cost: you lose the ability to query individual events.

So choose rollup dimensions deliberately, and keep the raw events somewhere, so a question nobody anticipated ("clicks
from Android in Brazil on Tuesday") can still be answered, slowly, from the archive.

Snip's tiers:

| Data | Kept for | Where |
| --- | --- | --- |
| Raw click events | 13 months | Compressed daily files in object storage |
| Per-minute rollups | 30 days | Analytics database |
| Per-hour rollups and hourly <Term t="hyperloglog">HyperLogLog</Term> sketches | 2 years | Analytics database |
| Per-day totals | For the link's lifetime | Postgres |

## Batch or stream?

- **Batch** processing runs over a bounded chunk of data (yesterday's files), producing complete, correct results,
  late.
- **Stream** processing handles events as they arrive (<L id="11.02" />), producing fresh results that may need
  correcting as late data turns up.

The **Lambda architecture** runs both: a stream path for fresh, approximate numbers and a batch path that periodically
recomputes correct ones and overwrites them. Jay Kreps pointed out its main cost: you
implement your logic twice, in two different systems, and keeping code that must produce the same result in two
complex distributed systems in sync is really hard.

His alternative, sometimes called the **Kappa architecture**: keep the raw events in a log (or an archive that can be
replayed as one), run **one** stream processing job, and when the logic changes, start a second instance of the new
version from the beginning of the retained data, let it catch up, and switch readers to its output. One code path; a
recompute is a replay.

Snip uses that shape: one streaming job produces the rollups; the raw archive can be replayed through a new version
of the same job to rebuild any period. A nightly batch job still exists, but runs the same code over the archive, only
to reconcile and catch the stragglers that arrived too late for the stream (<L id="11.02" />).

<Analogy>
  **Receipts and the monthly budget.** The budget spreadsheet is handy and small, but if you discover you'd been categorising coffee as groceries, you can only fix it if you kept the receipts. </Analogy>

<Mistakes>
  <ul>
    <li>**Storing only aggregates.** A bug or a new question can't be fixed or answered. Keep raw events, cheaply.</li>
    <li>**Treating derived data as precious.** It should be rebuildable; test that you can rebuild it.</li>
    <li>**Two code paths for the same logic.** Batch and stream versions drift. Prefer one job that can replay.</li>
    <li>**Rolling up away dimensions you'll need.** Choose dimensions from real questions, and keep raw data for the rest.</li>
  </ul>
</Mistakes>

## Recap

<Recap>
  <ul>
    <li>Raw events are the source of truth; counts, sketches and rollups are derived and replaceable.</li>
    <li>Rollups shrink data by orders of magnitude but lose individual events; keep the raw archive.</li>
    <li>Lambda runs batch and stream side by side at the cost of two code paths; replaying the log through one job avoids that.</li>
    <li>Tier retention: raw for months in cheap storage, fine rollups briefly, coarse rollups for years.</li>
  </ul>
</Recap>
