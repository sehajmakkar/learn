## The prompt

"Design a URL shortener." It's the most common opening question because it's small enough to finish in an
interview and still has real decisions in it: how codes are made, how redirects stay fast, where clicks are counted,
and what happens when the machine fails. This version stays at Snip's launch scale; <L id="15.02" /> takes it to a
hundred times that.

## 1. Requirements

**Functional**

- Create a short link for a long URL, optionally with a custom alias (`snip.example/spring-sale`) and an expiry date.
- Redirect anyone who opens the short link.
- Show the owner a click count per link.

**Non-functional**

- Redirects under 50 ms at the server for 99% of requests, available 99.99% of the time.
- A link, once created, is never lost.
- Codes can't be guessed or enumerated: some links point at private documents.
- Click counts can lag by a few seconds.

**Out of scope:** user accounts beyond an <Term t="api">API</Term> key, detailed analytics, editing a link's destination.

## 2. Estimates

From <L id="01.05" />: 10 million links a month is about **4 writes a second** on average and 10 at peak; with 100
redirects per link, about **350 reads a second** and 1,000 at peak; and 600 million links of 500 bytes each over
five years is **300 GB**.

**What it decides:** one ordinary Postgres server handles this with room to spare. The design doesn't need sharding,
a queue or a cache cluster. It does need a second copy of the data, because 99.99% is about 4 minutes of downtime a
month (<L id="14.02" />), and one machine can't promise that on its own.

## 3. Entities and API

```text
Link   { code (primary key), long_url, owner_id, created_at, expires_at? }
Clicks { code, day, count }

POST /links        { long_url, alias?, expires_at? }   Idempotency-Key: …   →  201 { code, short_url }
GET  /{code}                                                                 →  302 Location: long_url
GET  /links/{code}/stats                                                     →  200 { clicks, by_day }
```

The create call takes an idempotency key (<L id="03.10" />) so a retried request doesn't make a second link. The
redirect answers **302**, not 301: a 301 is cached by browsers, so later clicks never reach Snip and are never
counted, and the destination can never change (<L id="01.06" />).

## 5. Deep dives

<DeepDive title="How are short codes made?">
  <Option grade="bad" name="A counter, written in base62">
    Short and never collides, but **guessable**: anyone can walk `x7Kp`, `x7Kq`, `x7Kr` and find every link,
    including private ones, and the codes reveal how many links Snip has.
  </Option>
  <Option grade="good" name="A hash of the long URL, cut to 7 characters">
    Not guessable, and the same URL gets the same code. But truncated hashes still collide and need a retry scheme, and
    two users shortening the same URL now share one link, with one expiry and one click count.
  </Option>
  <Option grade="great" name="Random base62 codes, with the primary key catching collisions">
    62⁷ is about 3.5 trillion codes. With 600 million links, a new random code collides about 0.02% of the time, and
    the database already checks uniqueness for free: insert, and on a conflict, draw again (<L id="05.05" />). Custom
    aliases go in the same column, so they're checked the same way.
  </Option>
</DeepDive>

```ts
import { randomInt } from "node:crypto";

const ALPHABET = "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz";

export function randomCode(length = 7) {
  let code = "";
  for (let i = 0; i < length; i++) code += ALPHABET[randomInt(62)]; // randomInt avoids modulo bias
  return code;
}

export async function createLink(db: pg.Pool, longUrl: string, ownerId: number, draw = randomCode) {
  for (let attempt = 0; attempt < 5; attempt++) {
    const { rows } = await db.query(
      `INSERT INTO links (code, long_url, owner_id) VALUES ($1, $2, $3)
       ON CONFLICT (code) DO NOTHING RETURNING code`,
      [draw(), longUrl, ownerId],
    );
    if (rows.length) return rows[0].code as string; // no row back: the code was taken, draw again
  }
  throw new Error("no free code after 5 attempts");
}
```

Tested on Postgres 16: 10,000 links were created in about 0.7 seconds on one connection. With the first draw forced
to an existing code, the insert returned no row and the second draw succeeded; with every draw forced to a taken
code, the function gave up after five attempts instead of looping forever. The redirect's lookup by code used the
primary key index.

<DeepDive title="Keeping the redirect fast">
  <Option grade="bad" name="Look up the long URL by scanning, or by an unindexed column">
    Fine with a thousand links, and seconds per redirect with hundreds of millions.
  </Option>
  <Option grade="good" name="A primary key lookup on the code">
    One index lookup, typically well under a millisecond on a warm database, and enough for 1,000 reads a second.
  </Option>
  <Option grade="great" name="The primary key, plus a small in-process cache for hot codes">
    Clicks are skewed: a few links get most of them. An LRU cache of the 100,000 hottest codes (<L id="06.03" />)
    answers most redirects from memory with no database round trip. Give entries a short TTL, such as a minute, so a
    blocked or expired link stops working quickly.
  </Option>
</DeepDive>

<DeepDive title="Counting clicks without slowing redirects">
  <Option grade="bad" name="UPDATE links SET clicks = clicks + 1 on every redirect">
    Turns every read into a write, and a popular link's row becomes a lock that every redirect for it waits on.
  </Option>
  <Option grade="good" name="Insert a row per click">
    Appends don't fight over one row, and you keep each click's details. But at 350 a second that's 30 million rows a
    day, which will soon dwarf the links table.
  </Option>
  <Option grade="great" name="Count in memory, write totals every few seconds">
    Each app process keeps a map of code → count and flushes it with one upsert every few seconds. The requirements
    allow counts to lag, and a crash loses a few seconds of counts, never a link. If detailed analytics arrive later,
    the same flush can write events to a queue instead (<L id="02.06" />).
  </Option>
</DeepDive>

**Expiry and aliases.** An expired link is checked on read (`expires_at < now()` answers 404) and deleted later by a
nightly job, so expiry never needs a timer per link. Aliases need a reserved list (`api`, `login`, `admin`) and the
same character rules as codes.

## 6. Wrap-up: what breaks first

- **The machine.** The standby is promoted when the primary fails, by a tool like Patroni or a managed database's
  failover, in about a minute (<L id="04.07" />). That's most of a month's 99.99% budget, which is why the next step
  is two app servers behind a load balancer (<L id="02.03" />).
- **Growth.** At a hundred times the traffic, 30 TB and 100,000 redirects a second don't fit on one machine. That's
  <L id="15.02" />.

<Mistakes>
  <ul>
    <li>**Reaching for a distributed design at 10 writes a second.** Do the estimate; one database is enough here.</li>
    <li>**Answering with a 301 by default.** It hides clicks and freezes the destination; say why you chose either code.</li>
    <li>**Counting clicks on the redirect path.** Batch the counts.</li>
    <li>**No plan for the machine failing.** "Never lose a link" needs replication and backups.</li>
  </ul>
</Mistakes>
