## The problem: one reader can't keep up

Snip's clicks topic receives 100,000 events a second at peak. One click-counter process can apply perhaps 20,000 a
second. Adding a second process that reads the same events would just count everything twice. Snip needs a way to
**split the stream** between readers, while keeping the guarantee that matters: events about one link are processed in
the order they happened.

## Partitions

A topic is divided into **partitions**, each its own ordered log. When a producer appends an event, it picks a
partition from the event's **key**: in Kafka, events with the same key are written to the same partition, and a
consumer of that partition always reads its events in the order they were written.

Snip keys click events by **link code** and gives the topic 32 partitions. Every click for `x7Kp` lands in the same
partition, in order. Across partitions there's no order at all: a click on `x7Kp` and one on `b2Qe` may be processed
in either order, and that's fine, because nothing depends on it.

## Consumer groups

Readers that share the work join a **consumer group**. Each partition is consumed by exactly one member of the group
at a time, so the group divides the partitions among its members:

| Click counters in the group | Partitions each | Note |
| --- | --- | --- |
| 1 | 32 | One process does everything |
| 8 | 4 | Each reads its own four partitions |
| 32 | 1 | Maximum parallelism |
| 40 | 1 (8 idle) | More members than partitions: the extra ones have nothing to read |

That last row is why **the partition count caps parallelism**, and why it's chosen generously up front, like logical
shards (<L id="05.01" />). Adding partitions later changes which partition a key maps to, breaking per-key order for
the keys that move.

When a member joins, leaves or dies, the group **rebalances**: partitions are reassigned, and the new owner continues
from the last saved <Term t="consumer-offset">offset</Term>. Anything the old owner processed but hadn't saved is processed again, which is why
<L id="07.03" /> matters.

Different groups are independent. The fraud detector is its own group, also spread over the same 32 partitions, with
its own offsets.

## The order you actually get

Per-key order holds only if everything along the way preserves it:

- **The key has to be the thing whose order matters.** Snip's link events (`created`, `edited`, `deleted`) are keyed
  by code, so an edit can't overtake the creation. Keyed by owner, they'd still be in order per owner, which also
  works. Keyed randomly, they wouldn't be in order at all.
- **The producer mustn't reorder.** A producer with several requests in flight that retries one can, unless it's
  configured to preserve order (Kafka's idempotent producer does).
- **The consumer mustn't reorder.** Handing a partition's events to a thread pool processes them out of order. Run
  events for the same key one after another; parallelise across keys.
- **Retries mustn't reorder.** The hard one, below.

## A failing message: block, skip or set aside

Event 1,042 in partition 7 makes the click counter throw an error. Because the consumer's progress is one offset per
partition, it has three choices:

1. **Retry in place until it works.** Order is kept, but partition 7 stops completely. Fine for a brief outage of a
   database; disastrous for a malformed event that will never succeed.
2. **Skip it.** Partition 7 carries on, and the event is lost.
3. **Set it aside.** Write it to a **retry topic** that's consumed later, after a delay, and move on. After a few
   failed retries it goes to a **dead-letter topic** for a person to look at. Partition 7 keeps flowing.

Option 3 is the usual answer for independent events like clicks. But it breaks order for that key: if `x7Kp`'s
`edited` event is set aside and its `deleted` event goes through, the retry later "un-deletes" it. For events where
order matters, either retry in place (and alert fast), or, when one event for a key is set aside, set aside the rest of
that key's events too until it's resolved.

<Analogy>
  **Supermarket checkouts.** Each customer is assigned to one till, and each till serves its queue in order. More tills means more customers served at once, but there's no point having more cashiers than tills. And if one customer's card keeps being declined, the cashier asks them to step aside so the rest of the queue can move.
</Analogy>

## Hot partitions

Keying by code means a viral link puts all its clicks on one partition, and one consumer. At 50,000 clicks a second
on `x7Kp` (<L id="05.02" />), partition 12 falls behind while the other 31 are idle. Fixes, as with any hot key:

- **Pre-aggregate before the log.** Each app server counts clicks per code for a second and sends one event with a
  count, turning 50,000 events into 40.
- **Use a finer key** when strict per-link order isn't needed. Click events aren't edits; Snip could key them by code
  plus a random suffix of 0 to 7, spreading one link over eight partitions, and sum later.

<Mistakes>
  <ul>
    <li>**Too few partitions.** They cap consumer parallelism, and adding more later moves keys between partitions.</li>
    <li>**Keying by something other than what needs ordering.** Order holds only per key.</li>
    <li>**Parallel processing inside a partition.** It quietly discards the ordering you chose the key for.</li>
    <li>**Retrying a poison message in place for ever.** The whole partition stops. Set it aside after a few attempts.</li>
  </ul>
</Mistakes>

## Recap

<Recap>
  <ul>
    <li>A topic is split into partitions by key; order is guaranteed only within a partition.</li>
    <li>A consumer group gives each partition to one member, so partitions cap parallelism.</li>
    <li>Rebalances and retries reprocess events: consumers must be idempotent.</li>
    <li>For failures, choose between blocking (keeps order) and retry topics with a dead-letter topic (keeps flowing); hot keys need pre-aggregation or finer keys.</li>
  </ul>
</Recap>

  <p>Kafka orders events only within a partition. Producers choose the partition from a key, so all events for one key go to one partition in order.   <p>To keep order end to end, I key by the entity whose order matters, configure the producer not to reorder on retries, and process events for the same key sequentially inside the consumer. If a consumer dies, the group rebalances and another consumer resumes from the last committed offset, so processing must be idempotent. For failing messages I'd retry briefly in place, then move them to retry topics with delays and finally a dead-letter topic, accepting that this breaks per-key order unless I also hold back later events for that key.</p>
