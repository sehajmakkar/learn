## The problem: distance

All of Snip's servers are in one datacenter in Virginia. For a user in Sydney, every round trip crosses the Pacific
and back, taking on the order of 200 ms, and no faster server can change that: it's the speed of light in fibre
(<L id="01.04" />).

Opening Snip's dashboard takes several round trips before anything appears: one to set up the connection, one or two
for encryption, one for the HTML, then more for the scripts, styles and images it refers to. From Sydney, that adds up
to a second or more of waiting. Meanwhile, most of the bytes are **static files**, identical for every user: the
JavaScript bundle, the CSS, the logo, the fonts.

## A CDN

A **CDN** (content delivery network) is a large set of servers, called **edge servers**, spread across many cities.
Each one keeps copies of files, and users are sent to one close to them. Snip's own servers become the **origin**:
the place the CDN fetches a file from when it doesn't have it yet.

That gives Snip three things at once:

- **Speed** for users far from Virginia: most files come from a few milliseconds away.
- **Less load on the origin**: it serves each file once per edge, not once per user.
- **A shield.** CDNs are built to absorb huge traffic spikes, including attacks, before they reach the origin.

<Analogy>
  **Local warehouses.** An online shop with one central warehouse ships everything across the country, slowly. Shops that stock their bestsellers in small warehouses near each city deliver those overnight, and only send the unusual orders from the centre. A CDN is the network of local warehouses for files.
</Analogy>

## Headers decide what's cached

The CDN keeps what your responses tell it to keep, through the `Cache-Control` header. Snip uses three rules:

| Response | Header | Why |
| --- | --- | --- |
| Scripts, styles, images with a fingerprint in the name (`app.3f9a.js`) | `public, max-age=31536000, immutable` | The name changes whenever the content does, so a copy can be kept for a year. |
| The HTML page | `no-cache` (keep it, but check with the origin first) | It names the current script files, so it must always be fresh. |
| A logged-in dashboard or anything personal | `private, no-store` | Never keep one user's data where another user could be served it. |

The first row is the key trick. Instead of asking the CDN to throw away old copies when you deploy (slow, and
easy to get wrong), you give every new version a **new file name**. The new HTML points at `app.8c21.js`, which no
edge has yet, so they all fetch it. The old file can stay cached forever; nobody asks for it anymore.

## Should the edge serve redirects too?

Snip's busiest traffic isn't files; it's <Term t="redirect">redirects</Term>. Could the CDN cache those, so a Sydney redirect never crosses the
Pacific? It can, with a `Cache-Control` header on the 302. That's the same trade-off as the 301 in <L id="01.06" />:
clicks answered at the edge never reach Snip, so click counts would have to come from the CDN's logs instead. Some CDNs
also run small programs at the edge that could look the code up and record the click there.

Snip keeps redirects at the origin for now: its requirement is 50 ms **at the server**, the cache from
<L id="02.04" /> already meets it, and accurate counting matters more than the last 100 ms for distant users. It's a
reasonable next step if Snip goes global, and a good one to mention in an interview.

## What a CDN costs

- **Money per gigabyte** served, on top of what you already pay.
- **Staleness.** Anything cached at the edge is out of your hands until it expires. Fingerprinted file names avoid
  most of the pain.
- **Leaks, if headers are wrong.** Caching a personalised page at the edge can show one user's data to others. Mark
  anything personal `private`.
- **Harder debugging.** "It works for me" can mean you and the user hit different edges with different copies.

<Mistakes>
  <ul>
    <li>**Caching personal pages.** A missing `private` header on a logged-in page can serve one user's data to another.</li>
    <li>**Reusing file names for new versions.** Then every deploy is a race against cached copies. Fingerprint the names.</li>
    <li>**Caching redirects without thinking about counts.** Whatever the edge answers, the origin never sees.</li>
  </ul>
</Mistakes>

## Recap

<Recap>
  <ul>
    <li>Distance costs round trips no server can speed up; a CDN puts copies of files near users.</li>
    <li>Edges fetch from the origin on a miss and keep files as long as `Cache-Control` allows.</li>
    <li>Fingerprint static file names and cache them for a year; keep HTML fresh; never cache personal data publicly.</li>
    <li>Caching redirects at the edge is possible, but those clicks bypass Snip's counting.</li>
  </ul>
</Recap>
