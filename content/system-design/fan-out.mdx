## The problem: one event, many receivers

Three new Snip features all start from one event and end at many places:

- **Several services** must react to `link.created`: previews, webhooks, search (<L id="07.01" />).
- **Team feeds.** On the team plan, each member's dashboard shows "recent links from your team". A team can have 5
  members or, for one large customer, 40,000.
- **Live counters.** An agency's dashboard shows a link's clicks ticking up in real time. During a launch, 2,000 people
  watch the same viral link while it gets 50,000 clicks a second.

Each is a kind of **fan-out**: one input becoming many outputs. They need different tools.

## 1. Many services: publish once, subscribe many

Don't make the link service call each interested service; it would need to know them all, and a slow one would slow it
down. Publish one event and let each service subscribe.

- **With a log** (<L id="07.02" />), each service is its own consumer group on the `link-events` topic, reading every
  event at its own pace.
- **With queues**, a topic copies each message into one queue per subscriber. Amazon's version is SNS in front of SQS:
  publish to an SNS topic, and each subscribed SQS queue receives its own copy, consumed and retried independently.

Either way, adding a fourth service means adding a subscriber, with no change to the publisher, and one service being
down or slow doesn't hold back the others: its own queue or offset simply falls behind.

## 2. Many people's feeds: on write or on read

When Ana creates a link, how does it get into her teammates' "recent team links"?

**Fan-out on write (push).** A worker copies the new link into a feed list for each teammate as soon as it's created.
Reading a feed is then one quick lookup of a precomputed list, the <Term t="denormalisation">denormalised</Term> shape
of <L id="04.12" />.

**Fan-out on read (pull).** Store nothing extra. When someone opens their dashboard, query "the newest links from
everyone on my team" and merge them.

| | On write | On read |
| --- | --- | --- |
| **Cost of creating a link** | One write per team member | One write |
| **Cost of opening the feed** | One lookup | A query across every teammate's links |
| **Good when** | Feeds are read far more often than written; groups are small or medium | Groups are huge, or most feeds are rarely read |
| **Breaks when** | One author has a huge audience: 40,000 writes per link | Reads are frequent and the merge is expensive |

The usual answer is **hybrid**: push to most teams, but for the few huge ones, don't fan out; merge their recent
links in at read time. It's the same "celebrity" special case as hot keys (<L id="05.02" />), and it's how large
social feeds are built (<L id="12.03" />).

## 3. Many live screens: aggregate, then push

The live counter is fan-out to **connections**: 2,000 browsers hold <Term t="websocket">WebSocket</Term> connections
(<L id="03.05" />), spread over many gateway servers, all subscribed to `x7Kp`.

Pushing every click to every screen would be 50,000 × 2,000 = 100 million messages a second, for a number no human
can read that fast. So Snip **aggregates first**: one process per link sums its clicks for a second and publishes a
single `x7Kp: 1,204,331` update. Then it fans out in two levels:

1. The update goes to each **gateway server** that has at least one subscriber to `x7Kp`: perhaps 20 servers.
2. Each gateway sends it down each of its own subscribed connections.

That's 20 messages between servers and 2,000 to browsers, once a second. Two rules keep it healthy:

- **Each receiver gets its own buffer.** A browser on a slow phone network mustn't slow the others. Give each
  connection a small outgoing buffer, and if it fills, drop the old updates, since only the latest count matters.
- **Coalesce updates.** If three updates are waiting for one slow connection, send only the newest. Numbers that
  replace each other don't need to arrive one by one.

<Analogy>
  **A company announcement.** The CEO doesn't phone 40,000 staff. The announcement goes to each office manager, who tells their own floor (two levels of fan-out). For a small team, the manager might print a copy for each desk (fan-out on write); for the whole company, it's pinned to the noticeboard for people to read when they look (fan-out on read).
</Analogy>

<Mistakes>
  <ul>
    <li>**Calling each interested service directly.** Publish once and let them subscribe, so they're decoupled and independent.</li>
    <li>**Fan-out on write for every audience size.** The largest audiences make it explode. Go hybrid.</li>
    <li>**Pushing raw events to screens.** Aggregate first; people can't read 50,000 updates a second.</li>
    <li>**One shared buffer for all receivers.** A slow receiver then slows everyone. Buffer per receiver, and drop stale updates.</li>
  </ul>
</Mistakes>

## Recap

<Recap>
  <ul>
    <li>To many services: publish once, one subscription (consumer group or queue) per service.</li>
    <li>To many feeds: push on write for normal audiences, pull on read for huge ones.</li>
    <li>To many screens: aggregate, then fan out in two levels (servers, then connections).</li>
    <li>Give each receiver its own buffer, and coalesce updates that replace each other.</li>
  </ul>
</Recap>

## Interview questions

<InterviewCard
  q={{ q: "Fan-out on write or fan-out on read for a news feed? How do you handle users with millions of followers?", level: "Senior", frequency: 3, importance: "Must-know", kind: "Design" }}
  followUps={["How would you push new posts to users who are online right now?", "What happens when a follower's feed cache is cold?"]}
>
  <p>Fan-out on write copies each new post into every follower's precomputed feed when it's created, so reading a feed is a cheap lookup, at the cost of many writes per post. Fan-out on read stores the post once and builds the feed at read time by querying the people a user follows and merging, which makes writes cheap and reads expensive. Feeds are read far more than posts are written, so push is usually the default.</p>
  <p>Accounts with millions of followers would turn one post into millions of writes, so I'd use a hybrid: push for normal accounts, and for the few very large ones, skip fan-out and merge their recent posts into the feed at read time. For users currently online, a separate real-time path pushes a notification through the gateway servers holding their WebSocket connections, with per-connection buffers so slow clients don't hold anyone up.</p>
</InterviewCard>
