## The prompt

The follow-up interviewers ask once the one-machine answer is on the board: "Now make it a hundred times bigger,
and global." The point isn't a new design, it's knowing **which part breaks first** and changing only that.

## 1. Requirements

The functional list is the same as <L id="15.01" />, plus per-link analytics by minute, country and referrer. The
non-functional list changes:

- Redirects under 50 ms at the server for 99% of requests, **from every continent**, available 99.99%.
- Links never lost; creating a link can take a few hundred milliseconds.
- Analytics at most a few minutes behind; exact totals per day, approximate unique visitors are fine.
- An edited or blocked link stops redirecting within about a minute everywhere.

## 2. Estimates

| | Value | What it decides |
| --- | --- | --- |
| Writes | 1 billion a month ≈ 400 a second, about 1,200 at peak | Fine for a few databases; the problem is storage |
| Redirects | 100 × writes ≈ 40,000 a second, about **120,000 at peak** | Caches must answer almost all of them |
| Storage | 1 billion × 500 bytes = 0.5 TB a month, **30 TB** over five years | No longer one database: shard |
| Clicks | 100,000 a second ≈ **8.6 billion a day** | A stream with pre-aggregation, not a row per click |
| Codes | 60 billion links over five years | 7 characters collide 1.7% of the time; use **8** (<L id="05.05" />) |

## 3. Entities and API

The <Term t="api">API</Term> doesn't change: the clients from <L id="15.01" /> keep working. The data gains a second home for the
dashboard and the click pipeline:

```text
links           { code, long_url, owner_id, created_at, expires_at? }   sharded by hash(code)
links_by_owner  { owner_id, created_at, code }                          sharded by owner_id
clicks (stream) { code, at, country, referrer, ua }                     partitioned by code
clicks_minute   { code, minute, clicks, by_country, by_referrer, visitors_hll }
```

## 5. Deep dives

<DeepDive title="Storing 30 TB of links">
  <Option grade="bad" name="One bigger database">
    Vertical scaling buys time (<L id="02.02" />), but a 30 TB primary means restores that take many hours and one
    machine whose failure is everyone's outage.
  </Option>
  <Option grade="good" name="Shard by hash of code, one shard per database">
    Every redirect touches exactly one shard. But growing from 8 databases to 16 means rehashing and moving most
    links (<L id="05.03" />).
  </Option>
  <Option grade="great" name="256 logical shards by hash of code, mapped to fewer databases">
    The code is hashed to one of 256 logical shards forever; a small table maps logical shards to physical databases.
    Growing means moving whole logical shards with replication and a short cutover (<L id="05.04" />), and nothing
    rehashes. The dashboard's "my links" reads a `links_by_owner` copy sharded by owner (<L id="05.01" />).
  </Option>
</DeepDive>

```ts
import { createHash } from "node:crypto";

export const LOGICAL_SHARDS = 256;

/** Which logical shard owns a code. Never change this: it would move every link. */
export function logicalShard(code: string) {
  return createHash("md5").update(code).digest().readUInt32BE(0) % LOGICAL_SHARDS;
}

/** Logical shards map to physical databases through a small table you can change. */
export const physicalFor = (code: string, map: string[]) => map[logicalShard(code)];
```

Tested with a million random codes: every logical shard received between 3,690 and 4,066 of them (the mean is about
3,906). With 8 databases holding 32 logical shards each, moving one logical shard to a ninth database changed where
its codes were read from, and nothing else: each code's logical shard stayed the same.

<DeepDive title="Answering 120,000 redirects a second">
  <Option grade="bad" name="Every redirect to the database">
    120,000 reads a second spread over shards is possible, but every one pays a cross-ocean round trip for half the
    users, and every cache miss storm lands on Postgres.
  </Option>
  <Option grade="good" name="A Redis tier in each region">
    Cache-aside (<L id="06.02" />) with 12 primaries and replicas (<L id="06.06" />) answers most reads in about a
    millisecond. But users in Sydney still cross the Pacific to reach it.
  </Option>
  <Option grade="great" name="The CDN first, then an in-process cache, then Redis">
    Redirects for popular links are cached at the edge for 60 seconds with `s-maxage`, and kept out of browsers with a
    short `max-age`, so Snip can still purge them. Edits and blocks purge by a surrogate key per link
    (<L id="06.07" />); the 60-second lifetime caps staleness if a purge is missed.
  </Option>
</DeepDive>

<DeepDive title="One link, forty million followers">
  <Option grade="bad" name="Nothing special">
    A celebrity posts a link; 50,000 redirects a second hit one code, one Redis slot and, on a miss, one shard
    (<L id="05.02" />).
  </Option>
  <Option grade="good" name="Rely on the CDN">
    The edge absorbs most of it. But each edge location and each cache expiry still sends a burst of misses.
  </Option>
  <Option grade="great" name="Edge caching, request collapsing and a local copy of hot keys">
    The CDN collapses concurrent misses for the same key into one origin request; app servers keep the very hottest
    codes in process; and the Redis client coalesces identical in-flight reads (<L id="06.05" />). Clicks for the
    code are pre-aggregated before they reach the topic, so one hot link doesn't make one hot partition.
  </Option>
</DeepDive>

<DeepDive title="Counting 8.6 billion clicks a day">
  <Option grade="bad" name="Increment a counter per click in the links table">
    100,000 writes a second, concentrated on popular rows: the click path would become the busiest part of the
    database.
  </Option>
  <Option grade="good" name="Publish every click to a topic, count in consumers">
    Off the redirect path, replayable and partitioned by code (<L id="07.04" />). But each click is a message, and a
    viral link's partition falls behind.
  </Option>
  <Option grade="great" name="Pre-aggregate, stream, roll up, and keep the raw events">
    Apps sum clicks per code per second before publishing; consumers write per-minute rollups idempotently
    (<L id="07.03" />), with HyperLogLog sketches for unique visitors (<L id="11.03" />); raw events go to object
    storage for 13 months, so a counting bug can be fixed by replaying them (<L id="11.06" />).
  </Option>
</DeepDive>

**A second region.** Redirects are served active-active from Virginia and Frankfurt, each with its own cache and
read replicas. Link creation stays in Virginia, with Frankfurt as a warm standby (<L id="14.08" />): if Virginia
fails, about a second of new links may be lost, and redirects keep working throughout.

**Abuse.** At this size Snip is a target for phishing. Destinations are checked against blocklists at creation and
re-checked in the background, new accounts get low rate limits, and a block purges the link from every cache
(<L id="14.10" />).

and the cost of the edge logs. And the first thing to say if asked: everything above is an answer to an estimate.
At 15.01's scale, none of it would be justified.

<Mistakes>
  <ul>
    <li>**Redesigning everything.** Change what the estimates say breaks: storage, read volume, clicks.</li>
    <li>**Sharding by owner.** It makes the hottest query, the redirect, need to find the owner first.</li>
    <li>**Caching without a purge path.** Blocked phishing links must stop working everywhere quickly.</li>
    <li>**A click pipeline without raw events.** Keep them, so mistakes in counting can be fixed.</li>
  </ul>
</Mistakes>

## Recap

<Recap>
  <ul>
    <li>At 100×, storage (30 TB), redirects (120,000 a second at peak) and clicks (8.6 billion a day) no longer fit one machine.</li>
    <li>Links live in 256 logical shards by hash of code; the dashboard reads a copy sharded by owner.</li>
    <li>Redirects are answered by the CDN, an in-process cache and Redis, with purges for edits and blocks.</li>
    <li>Clicks flow through a stream with pre-aggregation and rollups, while raw events are archived for replay.</li>
  </ul>
</Recap>

  <p>Redirects go through the CDN with a 60-second shared-cache lifetime and purge by tag, then an in-process cache, then Redis, then the shard. Clicks are summed per second in the app, published to a topic partitioned by code, rolled up per minute with HyperLogLog for uniques, and archived raw.
