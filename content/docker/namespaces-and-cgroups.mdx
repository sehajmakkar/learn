## The core idea

There's no such thing as a "container" inside the Linux kernel. What Docker starts is an ordinary process, with three
things set up around it:

- **Namespaces** control what the process can **see**: its own process list, network, hostname and mount points.
- **Cgroups** (control groups) control what it can **use**: how much memory and CPU, how many processes.
- **A root filesystem**, the image, becomes its `/`.

Docker also drops some privileges (Linux capabilities) and blocks risky system calls (seccomp), but namespaces and
cgroups are the heart of it.

## Namespaces: a private view

Each namespace type wraps one part of the system. A process inside sees only what's in its namespace:

| Namespace | Isolates | Inside the container you see… |
| --- | --- | --- |
| `pid` | process IDs | your app as PID 1, and only its own processes |
| `net` | network interfaces, ports, routes | its own `eth0` and `localhost` |
| `mnt` | mount points | the image's filesystem as `/` |
| `uts` | hostname | a hostname of its own |
| `ipc` | shared memory, message queues | only its own |
| `user` | user and group IDs | root inside can map to a normal user outside |

Docker gives each container its own `pid`, `net`, `mnt`, `uts` and `ipc` namespaces by default. User namespaces are
opt-in, and are how Docker's rootless mode runs containers without root on the host.

The important bit: from the host, the container's processes are still right there, with normal PIDs. Namespaces hide
the host from the container, not the container from the host.

## See it yourself: one process, two views

  <p>Output trimmed; your PIDs will differ. Inside, nginx is PID 1. On the host, the same process has a normal PID like 17525.</p>
  <p>Notice the workers run as <code>nginx</code> inside but show as <code>statd</code> from outside. Both are the same numeric user ID, 101. You can even build a namespace by hand. `unshare` runs a program in brand-new namespaces. Inside a privileged
throwaway container (so this works on any OS), ask it for a new PID namespace and run `ps` there:

<Terminal>{`
$ docker run --rm --privileged ubuntu unshare --pid --fork --mount-proc ps
  PID TTY          TIME CMD
    1 ?        00:00:00 ps
`}</Terminal>

`ps` is PID 1 and can't see a single other process, not even the container it's running in. That's the same kernel
feature Docker uses, minus the convenience.

## Cgroups: a budget

Namespaces don't limit anything. A process that can only see itself can still eat all the host's memory. Cgroups fix
that: the kernel accounts for every cgroup's memory, CPU and process count, and enforces the limits you set.

<Code lang="bash" file="limits">{`
docker run -d --name capped --memory 64m --cpus 0.5 nginx:alpine
docker stats --no-stream capped
docker exec capped cat /sys/fs/cgroup/memory.max
`}</Code>

<Terminal>{`
$ docker stats --no-stream capped
CONTAINER ID   NAME      CPU %     MEM USAGE / LIMIT   MEM %     NET I/O       BLOCK I/O     PIDS
9368b6d7002c   capped    0.00%     8.664MiB / 64MiB    13.54%    652B / 126B   0B / 8.19kB   11
$ docker exec capped cat /sys/fs/cgroup/memory.max
67108864
`}</Terminal>

`docker stats` shows the 64 MiB limit, and `67108864` is the same limit in bytes, read straight from the cgroup files
the kernel uses. (That path is for cgroup v2, which current Linux distributions and
Docker Desktop use.)

When a container hits its memory limit and can't reclaim any, the kernel's **OOM killer** ends a process in it. If
that's the main process, the container exits with code `137` (128 + signal 9, SIGKILL). Here's a Node one-liner that
allocates memory forever, run with a 32 MB limit:

<Terminal>{`
$ docker run --name hog --memory 32m node:22-slim node -e 'const a=[];while(true)a.push(Buffer.alloc(1e6,1))'
$ docker inspect --format '{{.State.Status}} {{.State.ExitCode}} OOMKilled={{.State.OOMKilled}}' hog
exited 137 OOMKilled=true
`}</Terminal>

You'll tune limits properly in <L id="03.06" />.

## PID 1 is special

Because your app is PID 1 in its namespace, it inherits a job normally done by `init`: the kernel won't apply default
signal behaviour to PID 1. If your app doesn't explicitly handle `SIGTERM`, `docker stop` sends it, nothing happens,
and after a grace period Docker gives up and sends `SIGKILL`. On Docker Engine (what servers run) the grace period is
10 seconds by default; check a container's with `docker inspect -f '{{.Config.StopTimeout}}' NAME`. The Docker Desktop
used to test this course set it to 1 second, so the problem is easy to miss on a laptop.

Two fixes: handle `SIGTERM` in your app (you should anyway, to shut down cleanly), or run with `docker run --init`,
which puts a tiny init process in front of your app to forward signals.

<Mistakes>
  <ul>
    <li>**Assuming namespaces limit resources.** They only hide things. Without cgroup limits, one container can starve the host.</li>
    <li>**Ignoring exit code 137.** It almost always means the container was killed, usually by the OOM killer. Check `docker inspect` for `OOMKilled`.</li>
    <li>**Apps that ignore SIGTERM.** Every `docker stop` waits out the whole grace period and ends with a hard kill.</li>
  </ul>
</Mistakes>

## Recap

<Recap>
  <ul>
    <li>A container is a process plus namespaces, cgroups and a root filesystem.</li>
    <li>Namespaces decide what it can see. Cgroups decide what it can use.</li>
    <li>From the host, container processes are normal processes with normal PIDs.</li>
    <li>Your app is PID 1, so it must handle SIGTERM, or run with `--init`.</li>
  </ul>
</Recap>

## Interview questions

<InterviewCard
  q={{ q: "What is a container, at the operating-system level?", level: "Mid", frequency: 3, importance: "Must-know", kind: "Concept" }}
  followUps={["Which namespaces does Docker create by default?", "What happens when a container exceeds its memory limit?"]}
>
  <p>A regular Linux process (or process tree) that the kernel isolates and constrains. Namespaces give it a private view of process IDs, network, mounts, hostname and IPC. Cgroups limit and account for its CPU, memory and process count. Its root filesystem is the image, and Docker additionally drops capabilities and applies a seccomp profile.</p>
  <p>There's no container object in the kernel; "container" is the name for that combination.</p>

<InterviewCard
  q={{ q: "docker stop takes ten seconds for one of your containers on the server, every time. Why, and how do you fix it?", level: "Mid", frequency: 2, importance: "Good to know", kind: "Debugging" }}
  followUps={["How does the shell form of CMD make this worse?"]}
>
  <p>`docker stop` sends SIGTERM, waits for the stop timeout (10 seconds by default on Docker Engine), then sends SIGKILL. The app runs as PID 1, and the kernel doesn't apply default signal handling to PID 1, so if the app doesn't install a SIGTERM handler, the signal is ignored and it only dies at the timeout.</p>
  <p>Handle SIGTERM in the app and shut down cleanly, or run with `--init` so a small init process forwards signals. Also make sure the app really is PID 1: with the shell form of CMD, a shell is PID 1 and may not pass the signal on.</p>
</InterviewCard>
