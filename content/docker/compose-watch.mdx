## The core idea

During development you want edits to show up immediately. **<Term t="compose">Compose</Term> watch** watches folders on your machine and, when
something changes, either **copies the changed files into the running container** or **rebuilds the image** and
replaces the container, depending on rules you write. Combined with a process that restarts on change inside the
container, you get hot reload.

<Analogy>
  **Live preview.** It's like editing a document with live preview: you type, and a moment later the preview updates. Watch copies the files you save into the running container (sync), and `node --watch` notices and restarts. Change the ingredients list (`package.json`) and the whole dish is cooked again from scratch (rebuild).
</Analogy>

## A dev stage

The production image compiles <Term t="typescript">TypeScript</Term> and ships only `dist`. For development, the notes <Term t="api">API</Term>'s Dockerfile now has a
`dev` stage that keeps the source and dev <Term t="dependency">dependencies</Term> and runs a watcher:

<Code lang="dockerfile" file="api/Dockerfile">{`
# Development (06.05): the build stage plus a watcher. Node 22 runs TypeScript directly by
# stripping the types, so edits restart the server with no compile step. Build with --target dev.
FROM build AS dev
ENV NODE_ENV=development
CMD ["node", "--watch", "src/server.ts"]
`}</Code>

Two Node features do the work: `node --watch` restarts the process when a file it loaded changes, and Node 22 (from
22.18) runs `.ts` files directly by stripping type annotations. The final production stage is still last in the file,
so a plain `docker build` produces the same image as before. Compose picks the dev stage with `target: dev`.

## Watch rules

<Code lang="yaml" file="compose.yaml">{`
  api:
    build:
      context: ./api
      target: dev
    develop:
      watch:
        # Source edits are copied into the running container; node --watch restarts the server.
        - action: sync
          path: ./api/src
          target: /app/src
        # New dependencies need a new image.
        - action: rebuild
          path: ./api/package.json
`}</Code>

| Action | When a matching file changes |
| --- | --- |
| `sync` | copy it into the running container at `target` |
| `rebuild` | rebuild the image and recreate the container |
| `sync+restart` | copy it in, then restart the container (for apps that only read config at startup) |
| `restart` | restart the container without copying |

## See it work

<Terminal>{`
$ docker compose watch
 ...
 Container notes-api-1 Healthy
Watch enabled
$ curl localhost:8080/healthz          # in another terminal
{"status":"ok"}
`}</Terminal>

Now edit `api/src/server.ts` so `/healthz` returns `{ status: "ok", edited: true }` and save. Watch prints:

<Terminal>{`
Syncing service "api" after 2 changes were detected
`}</Terminal>

and the API's logs show Node restarting itself:

<Terminal>{`
$ docker compose logs api --since 30s
api-1  | Restarting 'src/server.ts'
api-1  | SIGTERM received, closing
api-1  | notes-api listening on :3000 (max note length 280)
$ curl localhost:8080/healthz
{"status":"ok","edited":true}
`}</Terminal>

A change to `package.json`, like adding a dependency, triggers the other rule:

<Terminal>{`
Rebuilding service(s) ["api"] after changes were detected...
 Image notes-api Building
 Container notes-api-1 Recreate
 Container notes-api-1 Recreated
`}</Terminal>

`docker compose up --watch` does the same as `up` plus `watch`, with every service's logs in one terminal.

## Why not a bind mount?

You could bind-mount `./api` over `/app` (<L id="04.03" />). Watch avoids the traps that come with it:

- **No hidden `node_modules`.** Only `src` is synced; the image's dependencies stay put.
- **No host-built native modules** leaking into a Linux container.
- **Faster on Mac and Windows**, because only changed files cross into the VM instead of every read going through
  file sharing.
- **Dependency changes rebuild properly**, instead of a stale `node_modules` you have to fix by hand.

<Mistakes>
  <ul>
    <li>**Syncing `node_modules`.** Let the image own dependencies; rebuild when `package.json` changes.</li>
    <li>**Shipping the dev stage.** Production builds the default (last) stage, without `--target dev`.</li>
    <li>**Expecting watch to restart the app by itself.** `sync` only copies files; the process inside must notice the change, which `node --watch` does here.</li>
  </ul>
</Mistakes>


## Recap

<Recap>
  <ul>
    <li>`develop.watch` rules: `sync`, `rebuild`, `sync+restart`, `restart`.</li>
    <li>A `dev` build stage plus `node --watch` gives hot reload.</li>
    <li>`docker compose watch` or `up --watch` to run it.</li>
    <li>Fewer traps than bind-mounting the whole project.</li>
  </ul>
</Recap>

## Interview questions

  q={{ q: "How would you set up a fast local development loop for a containerised service?", level: "Mid", frequency: 2, importance: "Good to know", kind: "Design" }}
>
  <p>Use a dev build target that includes dev dependencies and runs the app with a file watcher (nodemon, `node --watch`, uvicorn `--reload`, air for Go). Then either Compose watch, syncing source into the container and rebuilding when dependency manifests change, or a bind mount of the source with a volume over the dependency directory. Keep the production stage separate and last in the Dockerfile, and run the whole stack with one `docker compose up --watch`.</p>
