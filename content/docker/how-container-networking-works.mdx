## The core idea

Every container has its own network stack: its own network card, its own address, its own list of where to send
traffic, and its own ports. In plain words, it behaves like a separate small computer plugged into a network. Docker
connects that private network to the outside world with three pieces of ordinary Linux networking:

<Flow
  title="How a container reaches the network"
  steps={[
    { label: "veth pair", detail: "A virtual cable. One end is the container's eth0, the other end sits on the host." },
    { label: "Bridge", detail: "A virtual switch on the host. Every container's cable plugs into it, so they can talk." },
    { label: "NAT out", detail: "Traffic leaving for the internet is rewritten to come from the host's IP." },
    { label: "NAT in (-p)", detail: "Published ports rewrite incoming traffic to the container's IP and port." },
  ]}
  caption="On Docker Desktop all of this happens inside the Linux VM; the idea is the same."
/>

<Analogy>
  **An office phone system.** Each container is a desk with its own phone (`eth0`), plugged into the office switchboard (the bridge). Desks can call each other directly by extension number (IP address). Outside calls all leave through the building's one public number (NAT out), and reception forwards incoming calls for a published number to the right desk (NAT in). On the default bridge there's no staff directory, so you have to know the extension.
</Analogy>

## The networks Docker gives you

<Terminal>{`
$ docker network ls
NETWORK ID     NAME      DRIVER    SCOPE
ed8a6de1e4b5   bridge    bridge    local
...            host      host      local
...            none      null      local
$ docker network inspect bridge -f '{{range .IPAM.Config}}subnet={{.Subnet}} gateway={{.Gateway}}{{end}}'
subnet=172.17.0.0/16 gateway=172.17.0.1
`}</Terminal>

Output trimmed. Containers you start without `--network` join `bridge`, the **default bridge**, and get an address
from `172.17.0.0/16`. `host` and `none` are special modes, covered in <L id="05.03" />.

## The view from inside

<Terminal>{`
$ docker run --rm alpine sh -c 'ip -4 addr show eth0 | grep inet; ip route; cat /etc/resolv.conf'
    inet 172.17.0.2/16 brd 172.17.255.255 scope global eth0
default via 172.17.0.1 dev eth0
172.17.0.0/16 dev eth0 scope link  src 172.17.0.2
nameserver 192.168.65.7
`}</Terminal>

- **`eth0`** is the container's end of the virtual cable, with its own IP.
- **`default via 172.17.0.1`**: anything not on the local subnet goes to the bridge's gateway, the host.
- **`resolv.conf`** on the default bridge is copied from the host (here, Docker Desktop's resolver). Remember this;
  it changes on user-defined networks.

## Talking to each other, and out

Containers on the same bridge can reach each other by IP. Outbound traffic is NAT'ed through the host, so the internet
just works:

<Terminal>{`
$ docker run -d --name web1 nginx:alpine
$ docker inspect -f '{{.NetworkSettings.Networks.bridge.IPAddress}}' web1
172.17.0.2
$ docker run --rm alpine wget -qO- http://172.17.0.2 | grep -o '<title>.*</title>'
<title>Welcome to nginx!</title>
$ docker run --rm alpine wget -qO- http://web1
wget: bad address 'web1'
$ docker run --rm alpine wget -qO- http://example.com | grep -o '<title>.*</title>'
<title>Example Domain</title>
`}</Terminal>

By IP it works; **by name it doesn't**. The default bridge has no <Term t="dns">DNS</Term> for container names. And IPs are handed out
fresh every time a container starts, so hard-coding them breaks on the next restart. That's why real setups use
user-defined networks (<L id="05.02" />).

## Where -p fits in

Publishing `-p 8080:80` adds a rule on the host: "traffic arriving on port 8080 → rewrite to this container's IP,
port 80". That's the NAT-in step. It's also why containers on the same network never need `-p` to reach each other:
they talk directly over the bridge.

<Mistakes>
  <ul>
    <li>**Hard-coding container IPs.** They change. Use names on a user-defined network.</li>
    <li>**Publishing ports so containers can talk.** They don't need `-p` for that, only a shared network.</li>
  </ul>
</Mistakes>

## Recap

<Recap>
  <ul>
    <li>Each container: own namespace, own `eth0`, own IP.</li>
    <li>A veth pair connects it to a bridge; NAT handles traffic out and published ports in.</li>
    <li>The default bridge has no name resolution, and IPs aren't stable.</li>
  </ul>
</Recap>

## Interview questions

<InterviewCard
  q={{ q: "Explain how Docker's default bridge networking works.", level: "Mid", frequency: 2, importance: "Good to know", kind: "Concept" }}
  followUps={["How does a published port reach the container?"]}
>
  <p>Each container gets its own network namespace. Docker creates a veth pair: one end becomes the container's `eth0`, the other attaches to a Linux bridge on the host (`docker0` for the default network). Containers get IPs from the bridge's subnet and use the bridge as their gateway. Outbound traffic is masqueraded (source-NAT) to the host's address. Published ports are destination-NAT rules that forward a host port to the container's IP and port.</p>
