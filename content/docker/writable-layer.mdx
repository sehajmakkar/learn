## The core idea

Everything a container writes, unless you say otherwise, goes into its **writable layer**. That layer belongs to the
container: it survives `stop` and `start`, and it's deleted with `docker rm`. Containers are meant to be thrown away
and replaced, so anything you want to keep has to live **outside** the container.

## Watch data disappear

<Terminal>{`
$ docker run -d --name scratch alpine sleep 1000
$ docker exec scratch sh -c 'echo "important" > /data.txt; dd if=/dev/zero of=/big bs=1M count=50'
$ docker ps -s --filter name=scratch --format 'table {{.Names}}\\t{{.Size}}'
NAMES     SIZE
scratch   52.4MB (virtual 61.8MB)
$ docker diff scratch
A /big
A /data.txt
$ docker stop scratch && docker start scratch
$ docker exec scratch cat /data.txt
important
$ docker rm -f scratch
$ docker run --rm alpine cat /data.txt
cat: can't open '/data.txt': No such file or directory
`}</Terminal>

`docker ps -s` shows the writable layer's size (52.4 MB) and, in brackets, that plus the image underneath. A stop and
start keeps the file. Removing the container deletes it, and a new container from the same image starts clean.

That's fine for a cache. It's a disaster for a database, which is exactly what happens if you run Postgres and later
recreate the container to upgrade it.

## Why not just keep the container forever?

Because you can't, in practice:

- **Deploying means replacing.** A new image version means a new container.
- **Writable layers are slow for heavy writes.** Changing a file from the image first copies it into the writable layer
  (copy-on-write), and the storage driver adds overhead that databases feel.
- **Writable layers are hard to back up**, move to another server or share between containers.

<Mistakes>
  <ul>
    <li>**Treating the writable layer as storage.** It's gone at the next deploy.</li>
    <li>**Running databases without a named volume.** Upgrades silently start empty.</li>
    <li>**Writing logs to files in the container.** They grow the layer and vanish with it; log to stdout (<L id="03.04" />).</li>
  </ul>
</Mistakes>

## Recap

<Recap>
  <ul>
    <li>Writes go to the container's writable layer by default.</li>
    <li>It survives stop/start, not `docker rm`.</li>
    <li>Data you care about goes in a volume, a bind mount, or (if temporary) tmpfs.</li>
  </ul>
</Recap>

  <p>Into the container's writable layer, a copy-on-write layer the storage driver puts on top of the image's read-only layers. It persists across stop and start but is deleted with the container. For data that must outlive the container, or that's write-heavy, use a volume or bind mount, which bypass the storage driver and live independently of any one container.</p>
