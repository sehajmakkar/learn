## The core idea

Building software needs tools that running it doesn't: compilers, dev dependencies, test frameworks. If you build in
the same <Term t="image">image</Term> you ship, all of that ships too.

A **multi-stage build** has several `FROM` lines in one Dockerfile. Each starts a new stage. Earlier stages do the
heavy work, and the final stage copies in only the results. Only the final stage becomes your image.

<Analogy>
  **A workshop and a showroom.** Furniture is made in a workshop full of saws, glue and sawdust. Customers only ever see the showroom, where the finished table stands alone. A multi-stage build works the same way: the build stage is the messy workshop with compilers and tools, and only the finished piece is carried into the clean final stage that ships.
</Analogy>

## The problem, measured

The single-stage notes API image contains TypeScript, the type definitions and the source, none of which run in
production:

## Two stages

<Code lang="dockerfile" file="Dockerfile">{`
# syntax=docker/dockerfile:1

# Stage 1: compile TypeScript. Has dev dependencies and the compiler.
FROM node:22-slim AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY tsconfig.json ./
COPY src ./src
RUN npm run build

# Stage 2: what actually ships. Production dependencies and compiled JS only.
FROM node:22-slim
ENV NODE_ENV=production
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --omit=dev
COPY --from=build /app/dist ./dist
USER node
EXPOSE 3000
CMD ["node", "dist/server.js"]
`}</Code>

What's new:

- `FROM ... AS build` names a stage so other stages can refer to it.
- `COPY --from=build /app/dist ./dist` copies files **out of another stage** instead of from the <Term t="build-context">build context</Term>.
- `npm ci --omit=dev` installs only runtime dependencies in the final stage. The notes API has none yet, so this
  installs nothing; it starts to matter once Postgres arrives in <L id="04.05" />.
- `USER node` runs the app as the unprivileged `node` user that the official image provides.

## The result

<Terminal>{`
$ docker build -t notes-api .
$ docker run --rm notes-api ls
dist
node_modules
package-lock.json
package.json
$ docker images
IMAGE              DISK USAGE   CONTENT SIZE
notes-api:naive         425MB         95.5MB
notes-api:multi         349MB         80.4MB
node:22-slim            349MB         82.6MB
`}</Terminal>

Output trimmed. The multi-stage image is essentially the base image: your app adds a few kilobytes. Everything that
was only needed to build is gone. (`node_modules` here is an empty folder npm creates; there are no runtime
dependencies yet.)

The two columns: **disk usage** is the unpacked size on your machine, **content size** is the compressed size that
gets pushed and pulled. Docker Desktop's newer image store shows both; older setups show a single `SIZE`.

## Useful tricks

**Build only one stage** with `--target`. Handy for debugging or for a test stage in <Term t="ci">CI</Term>:

<Terminal>{`
$ docker build --target build -t notes-api:build-stage .
$ docker run --rm notes-api:build-stage ls
dist
node_modules
package-lock.json
package.json
src
tsconfig.json
`}</Terminal>

**Stages run in parallel when they can.** <Term t="buildkit">BuildKit</Term> works out which steps depend on which. In the build log for this
Dockerfile, the final stage's `npm ci --omit=dev` starts before the build stage finishes compiling, because it doesn't
need anything from it:

<Terminal>{`
#9 [build 3/7] COPY package.json package-lock.json ./
#10 [stage-1 4/5] RUN npm ci --omit=dev
#11 [build 4/7] RUN npm ci
...
#14 [build 7/7] RUN npm run build
#15 [stage-1 5/5] COPY --from=build /app/dist ./dist
`}</Terminal>

**Copy from any image**, not just your stages: `COPY --from=busybox:1.36 /bin/busybox /bin/busybox`.

<Checkpoint
  title="Convert the notes API"
  solution={<p><code>COPY --from=build</code> fails with "not found": check the stage is named <code>AS build</code> and the path matches where that stage wrote its output (<code>/app/dist</code>). Permission errors at startup: files copied in are owned by root but readable, which is fine; the app only needs to read them.</p>}
>
  <p>Rewrite your Dockerfile as two stages, rebuild, and confirm with <code>docker run --rm notes-api ls</code> that <code>src</code> and <code>tsconfig.json</code> are gone. Check that <code>docker exec</code> into a running container and <code>whoami</code> prints <code>node</code>.</p>
</Checkpoint>

<Mistakes>
  <ul>
    <li>**Copying the whole build stage**: `COPY --from=build /app /app` brings the compiler right back. Copy only outputs.</li>
    <li>**Installing dev dependencies in the final stage.** Use `--omit=dev`, or copy a pruned `node_modules` from a build stage.</li>
    <li>**Forgetting stage names are case-sensitive and must be unique.**</li>
  </ul>
</Mistakes>


## Recap

<Recap>
  <ul>
    <li>Each `FROM` starts a stage; only the last stage becomes the image.</li>
    <li>`COPY --from=stage` moves just the outputs across.</li>
    <li>Build tools and dev dependencies stay behind, so the image is smaller and has less to attack.</li>
    <li>`--target` builds a single stage.</li>
  </ul>
</Recap>

  q={{ q: "What are multi-stage builds and why use them?", level: "Mid", frequency: 3, importance: "Must-know", kind: "Concept" }}
  followUps={["How would you add a test stage that CI runs but production doesn't ship?"]}
>
  <p>A Dockerfile with several `FROM` stages, where later stages copy specific files from earlier ones with `COPY --from`. You compile or bundle in a stage that has the full toolchain, then copy only the artifacts into a minimal runtime stage.</p>
  <p>The shipped image is smaller, pulls faster, and has a smaller attack surface because compilers, dev dependencies and source code aren't in it. It also replaces the old pattern of separate build and runtime Dockerfiles glued together with scripts.</p>
