## The core idea

A secret is anything that grants access: passwords, API tokens, private keys. There are two moments a container setup
needs them, and each has a leak-free mechanism:

- **At build time** (say, a token to install private packages): **build secrets**, mounted for one `RUN` step and never
  written to a layer.
- **At run time** (say, the database password): **secret files**, mounted into the container, read by the app, and
  absent from `docker inspect`.

## The build-time leak

A common first attempt passes a token as a build argument and deletes the file in the same step:

<Code lang="dockerfile" file="Dockerfile (don't)">{`
FROM alpine
ARG NPM_TOKEN
RUN echo "//registry.npmjs.org/:_authToken=\${NPM_TOKEN}" > /root/.npmrc && echo "pretend npm install" && rm /root/.npmrc
`}</Code>

The file never reaches a layer. The token still leaks, into the image's history:

<Terminal>{`
$ docker build --build-arg NPM_TOKEN=npm_SuperSecret123 -t leak:arg .
 1 warning found (use docker --debug to expand):
 - SecretsUsedInArgOrEnv: Do not use ARG or ENV instructions for sensitive data (ARG "NPM_TOKEN") (line 2)
$ docker history --no-trunc leak:arg | grep -o 'NPM_TOKEN=[^ ]*'
NPM_TOKEN=npm_SuperSecret123
`}</Terminal>

Output trimmed. BuildKit even warns you. Anyone who can pull the image can read the token.

## Build secrets

BuildKit can mount a file into a single `RUN` step:

<Code lang="dockerfile" file="Dockerfile">{`
# syntax=docker/dockerfile:1
FROM alpine
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc cat /root/.npmrc | sed "s/=.*/=***/" && echo "pretend npm install"
RUN ls -la /root/.npmrc
`}</Code>

<Terminal>{`
$ docker build --secret id=npmrc,src=./npmrc -t leak:secret .
#7 [2/3] RUN --mount=type=secret,id=npmrc,target=/root/.npmrc cat /root/.npmrc | sed "s/=.*/=***/" ...
#7 0.104 //registry.npmjs.org/:_authToken=***
#7 0.104 pretend npm install
#8 [3/3] RUN ls -la /root/.npmrc
#8 0.109 ls: /root/.npmrc: No such file or directory
$ docker history --no-trunc leak:secret | grep -c SuperSecret
0
`}</Terminal>

The step that needed the token could read it. The next step can't see it, and it appears nowhere in the history. In
CI, the `docker/build-push-action` passes the same thing with its `secrets:` input.

## Run-time secrets as files

Environment variables are readable by anyone with Docker access:

<Terminal>{`
$ docker run -d --name envleak -e DB_PASSWORD=hunter2 alpine sleep 60
$ docker inspect -f '{{.Config.Env}}' envleak
[DB_PASSWORD=hunter2 PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin]
`}</Terminal>

Compose can mount a secret as a file at `/run/secrets/NAME` instead:

<Code lang="yaml" file="compose.prod.yaml">{`
services:
  api:
    environment:
      DATABASE_URL: postgres://notes@db:5432/notes
      DATABASE_PASSWORD_FILE: /run/secrets/db_password
    secrets: [db_password]

  db:
    image: postgres:18
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets: [db_password]

secrets:
  db_password:
    file: ./secrets/db_password.txt
`}</Code>

The **`_FILE` convention** is widely supported: official images for Postgres, MySQL and others accept
`POSTGRES_PASSWORD_FILE` in place of `POSTGRES_PASSWORD`. The notes API now does the same with
`DATABASE_PASSWORD_FILE`: the URL has no password, and the app reads it from the file at startup.

<Terminal>{`
$ openssl rand -base64 24 > secrets/db_password.txt
$ docker compose -f compose.prod.yaml exec api ls -l /run/secrets/
-rw-r--r-- 1 node node 33 Nov  2 21:08 db_password
$ docker inspect -f '{{range .Config.Env}}{{println .}}{{end}}' notes-prod-api-1 | grep DATABASE
DATABASE_URL=postgres://notes@db:5432/notes
DATABASE_PASSWORD_FILE=/run/secrets/db_password
`}</Terminal>

`docker inspect` shows only the path. The password is in a file only the container can read.

<Aside title="A bug this caught">
  The first version of the notes API passed the file's contents as a separate `password` option next to the connection
  string. node-postgres lets the connection string's (missing) password override it, and the API failed with
  `client password must be a string`. It now writes the password into the URL instead. Secret plumbing is code: test it
  the way production runs it.
</Aside>

Compose secrets from `file:` are a bind mount of that file. That's a clear improvement over env vars, not a vault: the
file still sits on the server's disk, so protect it (`chmod 600`, never commit it). Kubernetes Secrets, Docker Swarm
secrets and cloud secret managers build on the same "mounted file" idea with storage and access control behind it.

  title="Find the leak, then fix it"
  solution={<p>If the secret build fails with "secret npmrc not found", the <code>id</code> in <code>--secret id=...</code> must match the <code>id</code> in the <code>--mount</code>.</p>}

  <p>Build the <code>ARG</code> version and find the token with <code>docker history --no-trunc</code>. Rebuild with a secret mount and confirm it's gone. Then run the production stack with a generated <code>secrets/db_password.txt</code> and show that <code>docker inspect</code> on the API reveals no password.</p>
</Checkpoint>

<Mistakes>
  <ul>
    <li>**Secrets in `ARG` or `ENV`.** Both end up in the image.</li>
    <li>**`COPY` then `rm` a secret.** It stays in the earlier layer.</li>
    <li>**Committing the secrets folder.** The project's `.gitignore` ignores everything in `secrets/` except a placeholder.</li>
    <li>**Logging config on startup.** Easy way to print a password into logs. Log which settings are set, not their values.</li>
  </ul>
</Mistakes>

## Recap

<Recap>
  <ul>
    <li>Build time: `RUN --mount=type=secret` with `docker build --secret`.</li>
    <li>Run time: secret files at `/run/secrets/NAME`, and the `_FILE` convention.</li>
    <li>`ARG`, `ENV`, `COPY`+`rm` and plain env vars all leak.</li>
    <li>If a secret leaked into an image, rotate it.</li>
  </ul>
</Recap>

## Interview questions

<InterviewCard
  q={{ q: "How do you handle secrets in Docker, at build time and at runtime?", level: "Senior", frequency: 3, importance: "Must-know", kind: "Design" }}
  followUps={["Why are environment variables considered weak for secrets?"]}
>
  <p>At build time, use BuildKit secret mounts (`RUN --mount=type=secret`, `docker build --secret`): the secret is available to one step and never stored in a layer or history. Never use `ARG`, `ENV` or `COPY` for secrets. At runtime, mount secrets as files (Compose or Swarm secrets, Kubernetes Secrets, or a secrets manager's agent) and have the app read them, using `_FILE` variables where images support them.</p>
  <p>Environment variables are visible through `docker inspect` and `/proc`, inherited by child processes, and often dumped by crash reporters and debug pages. And if a secret ever lands in an image, rotate it; deleting the image doesn't recall copies.</p>
</InterviewCard>
