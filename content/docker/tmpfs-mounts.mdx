## The core idea

A **tmpfs mount** is a directory that lives in memory. It's fast, it's never written to disk, and it disappears when
the container stops. You won't use it often, but it solves two problems neatly: scratch space for files that must
never be persisted, and making a **read-only** container work.

<Analogy>
  **A whiteboard.** tmpfs is a whiteboard in the room: quick to write on, wiped when you leave, and nothing written on it ever reaches the filing cabinet (the disk). Perfect for rough work, and for anything you'd rather never be stored.
</Analogy>

## Read-only containers

`--read-only` makes the container's whole filesystem read-only. An attacker who gets in can't drop files, modify
binaries or plant a backdoor that survives. But many programs need to write *somewhere*, usually `/tmp`:

<Terminal>{`
$ docker run --rm --read-only alpine touch /tmp/x
touch: /tmp/x: Read-only file system
$ docker run --rm --read-only --tmpfs /tmp:size=16m alpine sh -c 'touch /tmp/x && df -h /tmp'
Filesystem                Size      Used Available Use% Mounted on
tmpfs                    16.0M         0     16.0M   0% /tmp
`}</Terminal>

Everything is read-only except a 16 MB in-memory `/tmp`. Add a tmpfs for each path the app really needs to write, and
a <Term t="volume">volume</Term> for anything it needs to keep. You'll apply this to the notes <Term t="api">API</Term> in <L id="07.01" />.

## Syntax and limits

<Code lang="bash" file="tmpfs">{`
# Short form, options after the colon
docker run --tmpfs /tmp:size=64m,mode=1777 ...

# Long form
docker run --mount type=tmpfs,dst=/cache,tmpfs-size=8m ...
`}</Code>

The size is a hard cap:

<Terminal>{`
$ docker run --rm --mount type=tmpfs,dst=/cache,tmpfs-size=8m alpine \\
    sh -c 'dd if=/dev/zero of=/cache/f bs=1M count=20'
dd: error writing '/cache/f': No space left on device
`}</Terminal>

Always set one. Without it, a tmpfs can grow to half of the host's (or Docker Desktop VM's) memory:

<Terminal>{`
$ docker run --rm --memory 64m --tmpfs /scratch alpine df -h /scratch
tmpfs                     3.8G         0      3.8G   0% /scratch
`}</Terminal>

Even inside a container limited to 64 MB, the tmpfs *reports* 3.8 GB. Files written there count against the
container's memory limit, so filling it can get the container <Term t="oom-killer">OOM-killed</Term> (<L id="03.06" />).

| | Volume | <Term t="bind-mount">Bind mount</Term> | tmpfs |
| --- | --- | --- | --- |
| Stored on | disk, managed by Docker | disk, your path | memory |
| Survives the container | yes | yes | no |
| Shared between containers | yes | yes | no |
| Typical use | databases, uploads | dev code, config | scratch, <Term t="secret">secrets</Term>, read-only roots |

  <p>Run the notes API with <code>--read-only</code>. Does it start? (It only writes to Postgres and stdout.) Then run <code>nginx:alpine</code> with <code>--read-only</code> and read the errors: add <code>--tmpfs</code> mounts for the paths it complains about until it serves pages.</p>
</Checkpoint>

<Mistakes>
  <ul>
    <li>**No size on a tmpfs.** It can eat the container's memory budget and trigger an OOM kill.</li>
    <li>**Expecting tmpfs data after a restart.** It's gone the moment the container stops.</li>
  </ul>
</Mistakes>


## Recap

<Recap>
  <ul>
    <li>tmpfs = in-memory directory, gone when the container stops.</li>
    <li>Pair `--read-only` with tmpfs mounts for the paths an app must write.</li>
    <li>Always set a size; usage counts against the memory limit.</li>
  </ul>
</Recap>
