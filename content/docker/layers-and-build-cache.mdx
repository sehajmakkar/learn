## The core idea

An <Term t="image">image</Term> isn't one big file. It's a stack of read-only **layers**, each holding the files one step of your Dockerfile
added or changed. When you rebuild, Docker reuses every step whose inputs haven't changed and only runs the rest.

So fast builds come down to one habit: **put the things that change least at the top of the Dockerfile**. The rest of
this lesson is why that works, and how to see it happen.

<Analogy>
  **Save points in a video game.** Every Dockerfile step is a save point. When you rebuild, Docker loads the last save point before anything changed and replays the level from there. Change something near the start and you replay almost everything; change something near the end and you're done in seconds. That's why the things that change least go at the top.
</Analogy>

## Every step leaves a record

Here's a typical first Dockerfile for a Node <Term t="api">API</Term>:

<Code lang="dockerfile" file="Dockerfile">{`
FROM node:22-slim
WORKDIR /app
COPY . .
RUN npm ci
CMD ["node", "src/index.js"]
`}</Code>

`FROM` brings in the base image's layers. `COPY` and `RUN` change files, so each adds a new layer on top. `CMD` only
changes the image's settings (which command to start), so it adds no files at all.

You can list an image's layers with `docker history`:

<Terminal>{`
$ docker build -t my-api .
$ docker history my-api
IMAGE          CREATED                  CREATED BY                                      SIZE
a9ded8c2f9c7   Less than a second ago   CMD ["node" "src/index.js"]                     0B
<missing>      Less than a second ago   RUN /bin/sh -c npm ci # buildkit                9.68MB
<missing>      1 second ago             COPY . . # buildkit                             61.4kB
<missing>      2 minutes ago            WORKDIR /app                                    8.19kB
<missing>      5 days ago               CMD ["node"]                                    0B
<missing>      5 days ago               ENTRYPOINT ["docker-entrypoint.sh"]             0B
...
`}</Terminal>

Read it bottom to top: that's the order the layers stack. Lines from "5 days ago" come from `node:22-slim`. Of the
layers you added, `npm ci` is by far the biggest (here, one <Term t="dependency">dependency</Term>: Express), and it's the slow one to rebuild.

Layers are also shared. If ten images on your machine start `FROM node:22-slim`, those base layers are stored once,
and `docker pull` only downloads layers you don't already have.

## How Docker decides a step is cached

Before running a step, Docker asks: have I run exactly this before, on top of exactly the same layers? What
"exactly this" means depends on the instruction:

| Instruction | Reused when… |
| --- | --- |
| `COPY` / `ADD` | the step before was reused **and** the copied files have the same contents. Docker checksums them; timestamps don't matter. |
| `RUN` | the step before was reused **and** the command text is identical. |
| Everything else | the step before was reused **and** the line is identical. |

That `RUN` rule surprises people. Docker never looks at what a command would do; it only compares the text.
`RUN apt-get update` stays cached for months, even as new package versions ship.

## One miss rebuilds everything after it

Each step's cache is tied to the exact layers beneath it. Once one step misses, every step after it is building on a

## Order your Dockerfile for the cache

`npm ci` only needs `package.json` and `package-lock.json`. Copy those first, install, then copy the rest of your
source:

<Code lang="dockerfile" file="Dockerfile">{`
FROM node:22-slim
WORKDIR /app

# Dependencies change rarely: install them first.
COPY package.json package-lock.json ./
RUN npm ci

# Source changes all the time: copy it last.
COPY . .
CMD ["node", "src/index.js"]
`}</Code>

Now editing your code only invalidates the final `COPY`. Dependencies only reinstall when the <Term t="lockfile">lockfile</Term> changes, which is
exactly when they should.

The same rule works for any language: copy the dependency manifest (`requirements.txt`, `go.mod` and `go.sum`,
`Cargo.toml`), install, then copy the source. Order steps from **least often changed** to **most often changed**.

<Aside title="Going further: cache mounts">
  Even with good ordering, changing one dependency re-downloads all of them. A cache mount keeps npm's download cache
  between builds without putting it in the image: `RUN --mount=type=cache,target=/root/.npm npm ci`. You'll use this
  in 07.05 when builds move to <Term t="ci">CI</Term>.
</Aside>

## Common mistakes

<Mistakes>
  <ul>
    <li>**Copying all the source before installing dependencies.** Every code change reinstalls everything.</li>
    <li>**`RUN apt-get update` on its own line.** That layer stays cached and stale while later installs change. Keep them in one step: `RUN apt-get update && apt-get install -y curl`.</li>
    <li>**No `.dockerignore`.** `COPY . .` then picks up `node_modules` and `.git`, so unrelated changes bust the cache. More in 02.03.</li>
    <li>**Deleting files in a later step to shrink the image.** The earlier layer still contains them, so the image doesn't get smaller. Delete in the same `RUN` that created them, or use a multi-stage build (02.04).</li>
  </ul>
</Mistakes>

## Recap

<Recap>
  <ul>
    <li>An image is a stack of layers. `RUN`, `COPY` and `ADD` add them.</li>
    <li>`COPY` is cached by file contents. `RUN` is cached by command text only.</li>
    <li>One cache miss rebuilds every step after it.</li>
    <li>Order your Dockerfile from least to most often changed. Dependencies before source.</li>
  </ul>
</Recap>

## Interview questions

<InterviewCard
  q={{ q: "Every code change re-runs npm install during the Docker build. Why, and how do you fix it?", level: "Mid", frequency: 3, importance: "Must-know", kind: "Debugging" }}
  followUps={["What if package-lock.json changes on almost every commit?", "How would you keep the npm download cache between builds in CI?"]}
>
  <p>The Dockerfile copies the whole source before installing. `COPY . .` is cached by file contents, so any code change makes it miss, and every step after a miss rebuilds, including the install.</p>
  <p>Fix the order: copy only the dependency manifest and lockfile, run the install, then copy the source. Now the install layer is only invalidated when the lockfile changes. A `.dockerignore` keeps `node_modules` and `.git` from busting the cache too.</p>
</InterviewCard>

<InterviewCard
  q={{ q: "A teammate removes a 300 MB file with RUN rm in the last step, but the image is the same size. Why?", level: "Mid", frequency: 2, importance: "Good to know", kind: "Debugging" }}
  followUps={["How does a multi-stage build avoid this?", "How would you find which layer is large?"]}
>
  <p>Layers only add. The layer that created the file still contains it; the later `rm` just adds a layer that hides it. The image is the sum of all layers, so nothing shrinks.</p>
  <p>Delete the file in the same `RUN` that creates it, or build in one stage and copy only the output into a clean final stage. `docker history` shows the size of each layer.</p>
</InterviewCard>
