## The core idea

On your laptop, the build cache lives in Docker and persists between builds. A <Term t="ci">CI</Term> runner is usually a fresh virtual
machine every time: **no cache at all**, so every build installs every <Term t="dependency">dependency</Term> from scratch. The fix is to **export**
the cache somewhere that outlives the runner at the end of a build, and **import** it at the start of the next.

<Analogy>
  **An exam in an empty hall.** Your laptop is your desk at home, covered in notes from last time. A CI runner is an exam hall where you start at an empty desk every single time. Exporting the cache is taking your notes with you and laying them out before you begin.
</Analogy>

## Simulate a fresh CI runner

A buildx builder that runs in its own container (`--driver docker-container`) has its own cache. Deleting and
recreating it is a good stand-in for a fresh runner:

<Terminal>{`
$ docker buildx create --name cibuilder --driver docker-container
$ docker buildx build --builder cibuilder --cache-to type=local,dest=./bcache,mode=max -t notes-api:ci .
$ du -sh bcache
 91M
$ docker buildx rm cibuilder && docker buildx create --name cibuilder --driver docker-container
$ docker buildx build --builder cibuilder --progress=plain --cache-from type=local,src=./bcache -t notes-api:ci .
#10 [build 2/7] WORKDIR /app
#10 CACHED
#11 [build 4/7] RUN npm ci
#11 CACHED
#13 [build 6/7] COPY src ./src
#13 CACHED
#16 [build 7/7] RUN npm run build
#16 CACHED
`}</Terminal>

Output trimmed. A brand-new builder, and every step is `CACHED`, because the cache came from the exported folder. Timed
on this machine:

| Fresh builder | Time |
| --- | --- |
| no cache | 40 s |
| with the imported cache | 27 s |

Both include about 15 seconds of starting the builder and fetching the base image. For a real app, with hundreds of
dependencies or a compile step that takes minutes, the cached build is minutes faster.

## Where to keep the cache

| `--cache-to` / `--cache-from` | Stored | Good for |
| --- | --- | --- |
| `type=gha` | <Term t="github-actions">GitHub Actions</Term>' cache service | GitHub Actions; the simplest option |
| `type=registry,ref=…:buildcache` | a separate tag in your registry | any CI; shared between pipelines |
| `type=local,dest=…` | a folder | CI systems that persist folders between jobs |
| `type=inline` | inside the image itself | very simple setups; final stage only |

**`mode=max`** exports the layers of **every** stage, including the build stage where `npm ci` happens. The default,
`mode=min`, only exports the final image's layers, which for a multi-stage build misses the expensive part.

## In GitHub Actions

The project's workflow (<L id="07.06" />) uses the GitHub Actions cache:

<Code lang="yaml" file=".github/workflows/notes-api.yml">{`
      - name: Build for scanning
        uses: docker/build-push-action@v7
        with:
          context: \${{ env.CONTEXT }}
          load: true
          tags: notes-api:scan
          cache-from: type=gha
          cache-to: type=gha,mode=max
`}</Code>

Its first two real runs on this repo:

<Terminal>{`
run 1 (empty cache)       Build for scanning: 30s
run 2 (source changed)    Build for scanning: 19s
  #10 importing cache manifest from gha:1130349528686026853
  #13 [build 4/7] RUN npm ci
  #13 CACHED
`}</Terminal>

Run 2 changed `server.ts`, so the source copy and compile ran again, but `npm ci` came straight from the cache.

## Cache mounts: the other cache

The layer cache is all-or-nothing: change one dependency and the whole `npm ci` layer reruns, downloading every
package again. A **cache mount** keeps a directory between builds without putting it in the image:

<Code lang="dockerfile" file="Dockerfile">{`
# syntax=docker/dockerfile:1
RUN --mount=type=cache,target=/root/.npm npm ci
`}</Code>

npm's download cache in `/root/.npm` survives between builds, so after a <Term t="lockfile">lockfile</Term> change only the new packages are
downloaded. It works for any package manager: `/root/.cache/pip`, `/go/pkg/mod`, `/var/cache/apt`. Cache mounts live in
the builder, so on CI they share the same "fresh runner" problem; layer-cache export is the bigger win there.

<Mistakes>
  <ul>
    <li>**`mode=min` with multi-stage builds.** The expensive stage isn't cached.</li>
    <li>**Expecting the local cache on CI.** Runners are fresh; export and import it.</li>
    <li>**Caching secrets.** Never put credentials in a cache mount or a layer; use secret mounts (<L id="07.02" />).</li>
  </ul>
</Mistakes>
