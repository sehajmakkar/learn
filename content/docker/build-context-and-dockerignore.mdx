## The core idea

The `.` at the end of `docker build -t notes-api .` is the **build context**: a folder whose files the builder is
allowed to see. `COPY` and `ADD` can only read from it. Everything in that folder is a candidate to end up in your
<Term t="image">image</Term>, unless a **`.dockerignore`** file says otherwise.

<Analogy>
  **Packing a suitcase.** `docker build .` packs the whole folder into a suitcase and sends it to the builder, who unpacks only what the Dockerfile asks for. Without a `.dockerignore`, you're packing everything in the room: the heavy things you never use, and the envelope with your passwords. `.dockerignore` is the list of things to leave at home.
</Analogy>

## Why the builder needs a context

The builder (<Term t="buildkit">BuildKit</Term>) isn't necessarily your machine. With Docker Desktop it runs inside a VM; in <Term t="ci">CI</Term> it might be a
remote server. So `docker build` sends the files it needs from your folder over to the builder, and that transfer is
the "transferring context" line you saw in the last two lessons.

Without a `.dockerignore`, the notes API sends this:

<Terminal>{`
$ docker build -t notes-api .
#5 transferring context: 26.18MB 0.2s done
$ du -sh node_modules dist src
 26M	node_modules
4.0K	dist
4.0K	src
`}</Terminal>

Nearly all of it is `node_modules` from your own `npm install`, which the image doesn't even want: it runs `npm ci`
itself, for its own platform.

## .dockerignore

A `.dockerignore` sits next to the Dockerfile and uses patterns like `.gitignore`:

<Code lang="bash" file=".dockerignore">{`
node_modules
dist
.git
.env
*.log
Dockerfile
.dockerignore
`}</Code>

The same build, from a clean cache:

<Terminal>{`
$ docker build -t notes-api .
#4 transferring context: 3.88kB done
`}</Terminal>

From 26 MB to under 4 kB, and the `COPY . .` <Term t="layer">layer</Term> shrinks from 26.9 MB to 32.8 kB.

That quiz isn't hypothetical. With the first Dockerfile and no `.dockerignore`:

<Terminal>{`
$ echo "SECRET=hunter2" > .env
$ docker build -t notes-api .
$ docker run --rm notes-api cat .env
SECRET=hunter2
`}</Terminal>

Once an image with a <Term t="secret">secret</Term> is pushed, rotating the secret is the only real fix. Deleting the file in a later layer
doesn't remove it from the earlier one (<L id="02.02" />).

## What to put in .dockerignore

| Ignore | Why |
| --- | --- |
| `node_modules`, `vendor`, `.venv` | The image installs its own, for its own OS and CPU. |
| build output: `dist`, `build`, `target` | The image builds its own; stale copies cause confusion. |
| `.git` | Large, and it changes on every commit, which busts the cache. |
| `.env`, keys, credentials | Secrets must never enter a layer. |
| `Dockerfile`, `.dockerignore`, `*.md`, tests | Not needed at runtime; changing them shouldn't invalidate `COPY . .`. |

You can also flip it around: ignore everything, then allow only what you need.

<Code lang="bash" file=".dockerignore">{`
*
!package.json
!package-lock.json
!tsconfig.json
!src/
`}</Code>

This allow-list style is stricter: a new secret file in the project can't leak by accident.

>
  <p>Build the notes API without a <code>.dockerignore</code> and note the "transferring context" size. Add the file above, prune the build cache, build again, and compare. Then add a <code>.env</code>, build, and confirm with <code>docker run --rm notes-api ls -a</code> that it's no longer in the image.</p>
</Checkpoint>

<Mistakes>
  <ul>
    <li>**Assuming `.gitignore` applies.** Docker ignores `.gitignore` entirely. It only reads `.dockerignore`.</li>
    <li>**Putting `.dockerignore` in the wrong place.** It must be in the root of the build context.</li>
    <li>**Using a broad context like your home directory.** `docker build ~` sends everything in it to the builder.</li>
  </ul>
</Mistakes>


## Recap

<Recap>
  <ul>
    <li>The build context is the folder `docker build` sends to the builder; `COPY` can only see it.</li>
    <li>`.dockerignore` keeps dependencies, build output, `.git` and secrets out.</li>
    <li>A secret copied into any layer is in the image for good. Rotate it.</li>
  </ul>
</Recap>

## Interview questions

<InterviewCard
  q={{ q: "What is the Docker build context, and why does .dockerignore matter?", level: "Junior", frequency: 2, importance: "Must-know", kind: "Concept" }}
  followUps={["Does .gitignore affect Docker builds?"]}
>
  <p>The build context is the set of files sent to the builder, usually the directory passed to `docker build`. Only those files are visible to `COPY` and `ADD`.</p>
  <p>`.dockerignore` excludes files from the context. That makes builds faster (less to transfer), keeps the cache stable (unrelated changes like `.git` don't invalidate `COPY . .`), keeps images smaller, and stops secrets like `.env` files from being baked into layers.</p>
</InterviewCard>

<InterviewCard
  q={{ q: "Someone pushed an image that contains a .env file with production credentials. What do you do?", level: "Senior", frequency: 2, importance: "Must-know", kind: "Scenario" }}
  followUps={["How do you pass secrets to a build safely?"]}
>
  <p>Treat the credentials as leaked: rotate them first, because anyone who pulled the image has them and deleting the tag doesn't remove copies. Then delete the image and tag from the registry, add `.dockerignore` (ideally allow-list style) and rebuild.</p>
  <p>Going forward, pass build-time secrets with BuildKit secret mounts (`RUN --mount=type=secret`), which never land in a layer, and pass runtime secrets as environment or mounted files when the container starts.</p>
</InterviewCard>
