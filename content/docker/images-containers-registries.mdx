## The core idea

Almost everything in Docker is one of three things:

- An **image** is a read-only template: a stack of filesystem layers plus settings like which command to run.
- A **container** is a running (or stopped) instance of an image, with a thin writable layer of its own on top.
- A **registry** is a server that stores images so you can push and pull them, like Docker Hub or GitHub's GHCR.

If you write code, a familiar comparison helps: an image is like a class and a container is like an object. You can
create many containers from one image, and changing one container doesn't change the image or its siblings.

## Images: layers plus settings

An image has two parts:

- **Layers**: read-only snapshots of files. Each step of a Dockerfile that changes files adds one (<L id="02.02" />).
- **Config**: environment variables, the working directory, the default command, exposed ports.

Every image has a **digest**, a SHA-256 hash of its contents, like `sha256:4c0fdaa8b6341bfdeca5f18f7837462c80cff90527ee35ef185571e1c327beac`.
Change one byte and the digest changes. That makes it the only name that always means exactly the same image.

## Containers: an image plus a writable layer

When you start a container, Docker stacks a small **writable layer** on top of the image's read-only layers. Anything
the container writes, creates or deletes goes into that layer. The image underneath never changes.

This is why starting a container is nearly instant and nearly free on disk: nothing is copied. It's also why the
writable layer is temporary. Delete the container and its changes are gone, unless they were in a volume
(<L id="04.01" />).

## Registries and image names

A registry stores images in **repositories**, and each repository holds many **tags**. A full image name tells Docker
exactly where to look:

  title="Reading an image name"
  parts={[
    { text: "ghcr.io", label: "registry" },
    { text: "/" },
    { text: "sehaj/api", label: "repository" },
    { text: ":" },
    { text: "1.2.0", label: "tag" },
  ]}
  caption="Leave out the registry and Docker assumes Docker Hub. Leave out the tag and it assumes latest."
/>

So the short name you type most often expands to something longer:

| You type | Docker reads it as |
| --- | --- |
| `nginx` | `docker.io/library/nginx:latest` |
| `node:22-slim` | `docker.io/library/node:22-slim` |
| `ghcr.io/sehaj/api:1.2.0` | exactly that |
| `nginx@sha256:4c0f…` | that exact image, by digest |

Tags are **movable labels**. `nginx:1.27` today may point at a different image next month after a patch release.
Digests never move. That's why production deploys often pin by digest; more in <L id="02.06" />.

  <p>Start two containers from the same image, write a file in one, and ask Docker what changed in each.</p>

...
$ docker diff b
...
`}</Terminal>

  <p>Output trimmed. <code>A</code> means added, <code>C</code> changed, <code>D</code> deleted. Only <code>a</code> has the new file. Clean up with <code>docker rm -f a b</code>.</p>
</Checkpoint>

<Mistakes>
  <ul>
    <li>**Reading `latest` as "newest".** It's just the default tag name. It points wherever whoever pushed it last decided.</li>
    <li>**Storing data in the container's writable layer.** It's deleted with the container. Use volumes for anything you want to keep.</li>
    <li>**Mixing up `docker rm` and `docker rmi`.** `rm` removes containers; `rmi` removes images.</li>
  </ul>
</Mistakes>

## Recap

<Recap>
  <ul>
    <li>Image: read-only layers plus config. Container: an image plus its own writable layer.</li>
    <li>Many containers share one image's layers; their changes stay separate.</li>
    <li>Image names are registry/repository:tag. Tags move; digests don't.</li>
  </ul>

## Interview questions

<InterviewCard
  q={{ q: "What is the difference between a Docker image and a container?", level: "Junior", frequency: 4, importance: "Must-know", kind: "Concept" }}
  followUps={["Where does a container's data go when you write a file?", "What happens to it when the container is removed?"]}
>
  <p>An image is an immutable template: read-only filesystem layers plus configuration such as the default command and environment. A container is a runtime instance of an image: Docker adds a thin writable layer on top and starts a process with its own namespaces and cgroups.</p>
  <p>Many containers can run from one image. Their writes go to their own writable layers, which are discarded when the container is removed.</p>
</InterviewCard>

<InterviewCard
  q={{ q: "Why would you deploy an image by digest instead of by tag?", level: "Mid", frequency: 2, importance: "Must-know", kind: "Scenario" }}
  followUps={["How do you find an image's digest?", "What's the downside of pinning digests?"]}
>
  <p>Tags are mutable: anyone with push access can move `api:1.2.0` to a different image, and base images like `node:22` move on every patch release. A digest is a hash of the image content, so it always refers to exactly the same bytes. Pinning by digest makes deploys reproducible and protects against a tag being replaced.</p>
  <p>The cost is that you don't get updates automatically, so you need tooling (like Renovate or Dependabot) to bump digests when security patches land.</p>
</InterviewCard>
