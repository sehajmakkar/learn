## Sequence: `<Sequence>`

Messages in order, top to bottom. `reply` draws a dashed response, `fail` a lost message, and notes sit over one or
more participants. With `walk`, readers step through one message at a time and see each one's `explain`.

<Sequence
  title="A retry with an idempotency key"
  walk
  participants={[{ id: "c", label: "Client" }, { id: "api", label: "Payments API" }, { id: "db", label: "Database" }]}
  messages={[
    { from: "c", to: "api", label: "POST /charges  key=a1", explain: "The client sends a charge with a key it made up." },
    { from: "api", to: "db", label: "insert key, charge", explain: "The API saves the key and the charge together." },
    { from: "api", to: "c", label: "201 Created", reply: true, fail: true, explain: "The reply is lost on the way back." },
    { note: "client times out", over: ["c"] },
    { from: "c", to: "api", label: "POST /charges  key=a1", explain: "The client retries with the same key." },
    { from: "api", to: "db", label: "find key a1", explain: "The API sees it has handled this key before…" },
    { from: "api", to: "c", label: "201 (saved reply)", reply: true, explain: "…and returns the first answer instead of charging twice." },
  ]}
/>

## Real systems: `<SeenInProduction>` and `<Seen>`

Two to four cards per concept lesson. Every card links to the company's own write-up, paper or postmortem, and
ends with our one-line takeaway.

<SeenInProduction>
  <Seen
    company="Discord"
    system="Message storage"
    year={2023}
    href="https://discord.com/blog/how-discord-stores-trillions-of-messages"
    source="How Discord stores trillions of messages"
    found="Hot partitions, not total size, were what hurt; they fixed them by coalescing duplicate reads in front of the database."
  >
    Moved message storage from Cassandra to ScyllaDB and put a Rust data service in front that merges identical
    requests for the same channel into one database query.
  </Seen>
  <Seen
    company="Stripe"
    system="Payments API"
    year={2017}
    href="https://stripe.com/blog/idempotency"
    source="Designing robust and predictable APIs with idempotency"
    found="Retries are only safe when the server can recognise a request it has already handled."
  >
    Clients send an `Idempotency-Key` header with each charge. The server stores the key with the result, so a retry
    after a timeout returns the first result instead of charging twice.
  </Seen>
</SeenInProduction>

## Design exercise: `<DesignIt>`

Opens every design lesson. The notes and rubric ticks are saved in the reader's browser, keyed by `id`.

<DesignIt
  id="styleguide-snip"
  minutes={30}
  levels={["junior", "mid"]}
  patterns={["caching", "ID generation", "read-heavy"]}
  rubric={[
    "State that reads outnumber writes by about 100 to 1, and design for reads",
    "Pick how short codes are made (counter + base62, hash, or random) and say what each costs",
    "Put a cache in front of the database for redirects",
    "Choose 301 or 302 and explain what it does to click counting",
    "Record clicks without slowing the redirect down",
  ]}
>
  Design a URL shortener. Users paste a long URL and get a short one like `snip.link/x7Kp`; anyone opening the
  short URL is redirected. Assume 10 million new links a month.

  - Short links never expire unless the owner deletes them
  - Owners can see how many times each link was opened
</DesignIt>
